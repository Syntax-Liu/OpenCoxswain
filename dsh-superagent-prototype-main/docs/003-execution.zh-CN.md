# 003 执行

> 本文是 [003 Execution](003-execution.md) 的中文译文，供阅读参考；如有出入，以英文原文为准。

本文跟踪一个已被接受的工单，经过执行、交付和恢复的过程。它建立在 [001 领域模型](001-domain.md) 和 [002 授权](002-authorization.md) 之上。

## 工单阶段

每个存活工单处于一个阶段，由其正在等待的内容决定。自上而下阅读此表；第一个匹配的行胜出。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器 Session 投递输入失败；2 秒后重试，之后延迟逐次翻倍直到一分钟；一次成功、新的派工或工单结束会清除它 | 输入未送达 |
| person / answer | 它有一个待人工决定 | 等待回答 |
| person / review | 最新报告是 `ready` | 等待评审 |
| person / blocked, failed | 最新报告是 `blocked` 或 `failed`，且此后没有人的消息抵达该工单 | 受阻 · 失败 |
| working / queued | 没有派工，或派工处于待启动 | 排队中 |
| idle | 最新报告是 `waiting`，或派工已结束 | 等待触发 |
| working | 其他一切情况 | 执行中 |

`person` 阶段意味着没有人的输入工单就无法继续。新的人工消息会把 `blocked` 或 `failed` 的工单释放给它的执行器，于是它移动到下一个匹配的阶段，通常是 `working`。

`idle` 工单已完成本轮工作，且没有悬而未决的问题。已订阅线程上的一个触发可以让它继续。

## 执行器

每个工单都有一个名为 `worker-<工单 id>` 的执行器 Session，以及一个以工单短名命名的目录。目录创建在配置的执行根目录下，默认是 `<stateDir>/work`。

执行器 Session 以操作者的操作系统用户身份运行命令，无需审批。它们的 `dsh-superagent-worker` 预设包含工作所需的工具，并在 5 秒后把前台 shell 命令移到后台任务。这样 worker 可以在下一步就接收新消息，而不必等待一条长命令结束。

主 Session 使用 `dsh-superagent-router`，同样有 5 秒的 shell 与任务等待上限，但用于路由的工具集更小。Session 会保留创建时选中的预设。Worker 的子 agent 使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与 worker 槽位

当一轮结束时仍有 shell 任务或子 agent 在运行，工单会保留其 worker 槽位并保持执行中状态。它不会报告为等待，主 Session 也不会收到等待报告。一个完成的任务或子 agent 会带着结果在同一槽位唤醒执行器。一旦某一轮结束时没有任何后台工作，执行器就会正常报告等待。

每一轮结束后，后台工作最多有 30 分钟完成。达到该上限时，shell 任务会被终止，工单报告为等待。报告包含执行器最后的说明，以及哪些任务被终止、哪些子 agent 仍活跃。子 agent 允许继续运行。执行器在下一轮读取被终止任务的结果。

移交给一个人会立即释放槽位，并让报告保持生效。这适用于 `ready` 报告或提问之后（除非此后有新的输入抵达），以及任何 `blocked` 或 `failed` 报告之后。

移交时，子 agent 停止。shell 任务（例如为评审提供的服务器）可以继续运行直到派工结束。它们不占用槽位，也不受 30 分钟上限约束，包括在之后的轮次中。它们的完成不会唤醒执行器；执行器在下一轮读取结果。

人也可以直接在执行器 Session 中写入来开启一轮。它的后台工作遵循同样的规则。

派工结束时，其 shell 任务在不再唤醒 Session 的情况下被终止。其子 agent 被释放，它们唤醒的任何完成轮次都会被丢弃。替代的派工及其等待中的输入会在该关闭过程完成后才开始。

在 DeepSeek Harness 进程内停止或重启插件走同一条关闭路径。尚未被纳入 Session 历史的输入会保留。关闭时最多等待每个 worker 的后台工作 10 秒；进程重启会直接终结这些工作。在忙碌时被打断的派工会带一条恢复说明重新开始。

Worker 的子 agent（包括嵌套的）使用 DeepSeek Harness 的 `standard` 预设，并继承 worker 的权限。它们只保留 worker 被允许的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令在 60 秒后转入后台。子 agent 结束时其任务会被终止。

### 准备工单目录

在第一次派工之前，如果工单目录不存在，prepare 命令会在执行根目录下用 `sh` 运行一次。它必须在十分钟内完成。没有 prepare 命令时，worker 从空目录开始。

命令失败会使工单失败并记录其输出。重试、或有人在工单的某个线程上发消息，都会再次尝试准备。典型的命令用 `git worktree` 创建检出。当 PR 分支路径的最后一段与工单短名匹配时，该 PR 属于这个工单。

### 并发

从启动开始（包括准备阶段），或从唤醒其空闲执行器的那次投递开始，工单就持有一个 worker 槽位。在整个活跃轮次中它也同样持有该槽位。

配置的并发上限适用于这些槽位，另外为人的消息或状态请求保留一个额外槽位。正常槽位已满时，这类唤醒可以使用额外槽位，并在新启动之前占用下一个空闲槽位。因此新工作无法阻止人继续某个已有工单。

其他输入（例如 CI 结果）要等待正常槽位。启动在获得槽位之前会在 `working / queued` 中等待。各次启动并发运行，所以一条较慢的 prepare 命令只会延迟它自己的工单。

### 执行变量

prepare 命令和执行器指令会收到相同的执行变量。命令读取环境变量；执行器在其提示词中读取这些变量的值和描述。它们都不包含凭据。

| 变量 | 注册者 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`、`DSH_SUPERAGENT_NAME`、`DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源监听的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`、`DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | agent 账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`、`DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 启动该工单的 Issue 或 PR，以及当它是 PR 时其 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`、`DSH_SUPERAGENT_FEISHU_CHAT` | Feishu | 机器人和启动该工单的群 |

工单专属的值来自其目录和原始触发。其他值来自当前部署设置。只有面板能更改执行环境设置；发给主 Session 的文本无法更改已配置的 shell 命令。

Worker 通过 agent 账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问 Feishu。被禁止的命令按名称调用时会失败。

这些包装脚本和目录建立的是默认值，不是安全边界。worker 仍然可以通过绝对路径执行程序。

## 合并

自动合并由 **交付要求** 提示词管辖。宿主没有专门的合并决策逻辑。

默认情况下，执行器绝不以 agent 账号启用自动合并：GitHub 会把合并归到启用它的人名下。交付要求必须指定另一个账号的 CLI 用于合并。没有的话，就由人来合并 PR。

默认指令只允许对为本工单开启的 PR 启用自动合并，且需满足：它已就绪、所需批准覆盖了 head 提交、增删总行数少于 200 行。在推送另一版次之前，执行器会撤回自动合并。

没有正文的评审（例如批准）也会作为触发抵达，并可能唤醒一个等待评审的执行器。这些指令约束的是 agent，而不是 GitHub 的合并规则。要强制批准，请在分支保护中要求批准并忽略过期批准。省略合并 CLI 或删除自动合并那一段，就要求手动合并。

## 工单如何结束

- **就绪但没有 PR：** `ready` 报告以“已完成”结束工单。
- **无事可做：** 发现没有需要人处理的工作（例如请求无法复现或已被取代）的执行器报告 `dropped`。除非匹配的规则要求发消息，工单不附带任何消息地结束；之后有人在其线程上发消息会使其恢复。
### Pull request

执行器报告之后，工单开始关注启动它的那个 PR。它同样会关注从其分支开启的每个 PR（由执行器报告或被 GitHub 来源发现后）。重新开启的 PR 会再次被关注。

当它开启的 PR 都不再处于打开状态时，工单就完成了。如果它没有开启任何 PR，则它关注的所有 PR 都必须已关闭。随后它以最近一次相关关闭的结果结束，并保留订阅，以便之后有人评论时恢复。

恢复、重试或恢复性处理的工作尚未完成时，关闭不会结束工单。如果执行器确认或回答了它拥有的一条跟帖，但此后既没有给出非进展报告，也没有在读到该消息后结束一轮，那么它同样要等待。在满足同样的 PR 完成规则后，之后的一份 `ready` 报告会结束工单。

聊天渠道会收到一条关于 PR 结果的最终通知。GitHub 本身已在 PR 上显示结果。移除工单对某个 PR 的订阅，也会让它不再关注该 PR。

因此，“等待评审”指的就是一份带 PR 的 `ready` 报告。

### 跟帖与上下文线程

执行器决定其工单自有线程上的人工跟帖。它处理范围内的请求，并把超出范围或属于其他工单的请求交回。一旦没有执行器拥有该消息，它就成为一个供主 Session 处理的候选。主 Session 对跟帖唯一能做的其他操作，是应人的要求停止工作。

输入在 Session 把它纳入某一步骤并随后作出报告或结束一轮之后，才算已读。工单结束时，未被确认、回答或交回的未读消息会回到评估，如 [002 授权](002-authorization.md) 所述。读到后未采取行动的（例如道谢）不会回到评估。

仅为上下文而跟随的线程仍会投递消息，但不会让工单拥有人工跟帖的所有权，也不会使已结束的工单恢复。这些消息可以被独立研判。

只要存在存活工单在订阅，并在最后一个触发和订阅工单结束这两者中较晚者之后的两周内，来源会轮询已订阅的线程。此后，消息只能通过普通入口进入：GitHub 通知或 Feishu 实时事件。

## 失败与恢复

### 执行器受阻或失败

当执行器 Session 报告 `blocked` 或 `failed`，或启动失败、出错（记作 `failed`）时，工单不再接收任何自动输入。

模型提供方或网络的一次瞬时失败（HTTP 408、429 或 5xx，或被拒绝、被重置、超时的连接）会先重试，共三次并逐步延长退避：一次启动重新运行，一轮失败的 worker 被要求继续；失败的 prepare 命令不会重试。

一旦失败，CI 和机器人的消息会被记录在上面，但不会投递，也不会唤醒 Session。

它的工具仍然可用，因此人可以直接在 Session 中继续。

启动失败不会自行重试。

人的消息、之后一份既非 `blocked` 也非 `failed` 的报告，或一次重试，都会解除该挂起状态。

该状态由已存储的报告和输入推算而出，所以重启后仍然保留。
### 重试

当存活工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：新的派工会重新启动其 worker 并接收等待中的输入，这就是对每种情况的对策。

一旦人的消息抵达受阻或失败的工单，执行器就拥有了该消息，因此工单显示为执行中（若失败的启动重新开始时则显示为排队中），并且不再提供重试——除非投递那条消息本身失败了。

重试会结束当前派工，并在同一执行器 Session、目录、分支和 PR 中启动新的派工。

执行器模型只在创建 Session 时生效；已有 Session 保持其模型。
### 重启

正在运行的派工以“host restarted”结束，新的派工带着一条恢复说明启动，说明要求执行器在重复任何外部操作之前检查其目录、git 历史和 GitHub，并从最旧的工单开始。

处于等待、就绪、受阻或失败状态的派工保持不变，除非在其报告之后有输入抵达；这种情况下它们也会重新启动。

Session、目录、订阅、待处理消息和下文所述已存储的工作都能在重启后保留；每个执行器 Session 把哪些消息纳入其历史的记录也同样保留。一个步骤在领取这些消息之后、调用模型之前会做这个记录：被重启切断的那一轮所取走的消息，在随后出现报告或一轮结束时计为已读；而一个步骤已领取、但在写入历史之前被取消或出错切断的消息计为未读。

重试或重启会把投递给被替换派工、但其执行器 Session 未取走的消息（可能因取消或步骤被切断而被丢弃）重新交给新的派工；仍在 Session 中等待的副本（由重启保留或跨崩溃持久化）会在新派工的第一条消息之前被取出，因此新的投递是唯一的副本。
### 已存储的工作

dsh-superagent 在某个决定之后所做的一切（例如把候选、跟帖或报告转发给主 Session、启动派工或投递输入）都先存储，再执行。

转发或投递失败（例如无法联系到其 Session）会在 2 秒后重试，之后延迟逐次翻倍直到一分钟；而启动失败会使工单失败，除非如前所述属于瞬时失败。

每一类工作只有在连续三次失败之后，才会在总览的系统问题中报告错误；输入投递失败则改在其工单上显示。

发往主 Session 的转发保持顺序，通知也是如此；一条失败的转发会挡住同类中较晚的项。
### 来源失败

GitHub 来源分别读取每个 Issue、PR 和线程：一次失败的读取会把错误保留在其线程上，在下次轮询时重读，并计入来源的错误——默认在连续三次轮询失败后报告；任何一次成功的轮询都会重置计数。

当 agent 失去对私有仓库的访问权限时，GitHub 也会返回 404，因此 404 会重试。

一个已通知的 Issue 或 PR，如果其读取持续失败，会在首次失败读取的一天后丢弃；若 GitHub 报告它已删除则立即丢弃。此后它不再使轮询失败，其线程保留错误，来源状态中会列出它。

它的读取位置保持不变，因此之后的通知或对其线程的轮询会读到失败读取所漏掉的内容。

Feishu 事件消费者会报告每次失败，对已订阅话题的轮询也会把每个失败保留在其线程上。

GitHub 列表或 Feishu 页面中格式错误的项会被跳过，来源状态会统计它们。
### 渠道失败

外发消息作为已存储的工作被存储并发送，以 5 秒起、翻倍至 300 秒的退避重试。

工单发往同一会话的消息按排队顺序发出，因此它的确认会早于其后来的回答或结果：当同一工单发往同一会话的较早消息尚未发出时，后面的消息会等待，直到那条连续失败三次并被标记为问题。

其他工单的消息，以及不属于任何工单的消息，不会因此等待。

有失败尝试的消息在发出或被撤回之前一直是一个系统问题。

只有当来源不再监听该会话，或来源答复该会话永远无法接收它时，消息才会被丢弃；来源关闭期间，它会等待。

GitHub 对已删除的 Issue 或已锁定的会话、Feishu 对已撤回的消息或 Feishu 上已找不到的消息，都会给出这种答复。

对已不存在的评审评论的回复会改为发到该 PR 的会话中。

被丢弃的消息保留其记录，包括丢弃时间和原因以及所属工单，因此它绝不会再次排队；被丢弃的确认按“已丢弃”而非“已发送”呈现。
### 暂停处理

停止派发、新的评估、评估超时、输入投递和回复；已经开始的一次启动会等到处理恢复。

来源继续记录触发，正在执行的一轮不会被打断。

人对已结束工单的消息会等待：暂停后的第一轮会在授权届时仍成立的情况下恢复该工单。

进行中的评估在暂停期间不会过期；其截止时间会按暂停时长顺延。
### 无效配置

已存储的、被其类型拒绝的来源配置会禁用该来源实例。
