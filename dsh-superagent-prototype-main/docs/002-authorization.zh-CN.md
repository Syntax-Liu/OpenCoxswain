# 002 授权

> 本文是 [002 Authorization](002-authorization.md) 的中文译文，供阅读参考；如有出入，以英文原文为准。

授权决定谁可以发起工作，以及该工作可以包含什么。本文建立在 [001 领域模型](001-domain.md) 之上。

宿主强制执行允许名单、规则和授权。消息、评论和引用的文档只是决策的输入；它们无法改变这些权限。

## 一个触发的两条路径

### 评估：决定是否开始工作

来源记录一条消息是否指向 agent：`mention` 表示提及机器人或 agent 账号，`direct` 表示私信。准入检查发送者和来源的策略：

- 在名单上且指向 agent 的人构成明确请求。
- 有人在已有工单的线程上跟帖时，遵循下文规则。
- 其他人的消息按其所处接收范围查准入表。
- 来源机器人名单上的机器人可以产生推断候选，但永不构成明确请求。其他机器人不予准入。

### 订阅：延续已有工作

已订阅线程上的每条消息都会作为上下文抵达其订阅的工单，包括来自机器人和 CI 的消息。这种投递绕过准入，并且不授予任何新权限。每个工单仍受其授权约束。

人的消息出现在某个工单自己的线程上时，由该工单的执行器决定。主 Session 把一条消息挂到某个工单上时也是如此。当执行器拥有该消息期间，它不进入评估，也不产生决定。每个执行器要么在其工单范围内处理该请求，要么把它交回以便路由到别处。

只要工单还存活，所有权就持续存在，即使有人移除了它的订阅。所有权同样覆盖一个未被人员停止、且有消息在等待使其恢复的已结束工单。

主 Session 会收到跟帖通知。当执行器拥有该消息时，主 Session 只能按人的要求停止工作；接受、挂接、忽略和重新排队都会被拒绝。停止操作仍需经过准入，强度见下文所述的跟帖强度。

### 交回与释放跟帖

执行器在遇到超出工单范围的请求，或该消息属于另一个工单时，交回一次。工单保留其订阅。如果被挂接的线程确实无关，执行器交回它在该线程上持有的消息。

只有当不再有任何工单拥有某条消息时，它才会进入新的评估。其候选会包含执行器给出的理由。准入把它当作该线程上的普通消息来判断，主 Session 可以接受它、把它挂到别处，或忽略它。交回一条工单并不拥有的消息（例如机器人的消息，或某人已经送进评估的消息）不会排队任何东西。

工单结束时会释放其执行器没有读到或没有接手的跟帖。这些包括从未投递给执行器的消息，以及在它最后一次报告或轮次结束之后才投递的消息，前提是执行器既未确认、未回答，也未交回它们。只要没有其他工单拥有该消息，每条被释放的消息都会进入评估。停止只结束被停止工单的工作。

被停止的工单不会把它那条停止消息再次送进评估，除非另一个工单把它交回了。执行停止的主 Session 可以把该消息的其余部分当作新工作接受。

人可以在面板上把被拥有的跟帖送进评估。如果主 Session 随后把它挂回一个存活工单，执行器会再次收到它。当没有生效的判断覆盖该消息时，面板还会提供重新评估。

### 仅作上下文的订阅

执行器可以为获取上下文而跟随一个相关线程，例如另一个 Issue 或 PR。该线程的消息会抵达工单，但不授予权限，也不带来跟帖强度。除非主 Session 把来自该线程的消息挂到工单上，否则那里的人的消息不会使已结束的工单恢复。主 Session 关于其他工作的说明同样只是上下文。

未抵达任何工单的人的消息（包括工单已被人员停止的线程）走评估路径。机器人的消息无论是否投递给订阅的工单，都会独立地走该路径。

## 强度

| 强度 | 情形 |
| --- | --- |
| 明确（explicit） | 名单上的人指向 agent，或在已有工单的线程上跟帖；准入表某格设为明确请求 |
| 推断（inferred） | 不在名单上的人在已有工单的线程上跟帖，除非其对应的准入格是明确请求；准入表某格设为推断候选；来源机器人名单上的机器人发出指向 agent 的消息，或出现在来源接收全部消息的地方 |
| 不准入 | 任何其他机器人的消息、准入表忽略的一切，以及接受模式为 `off` 时的所有推断情形 |

对于名单外的人，即使线程上已有工单，明确的准入格也优先，并且在任何接受模式下都有效。否则其跟帖为推断，在 `off` 模式下不予准入。仅作上下文跟随的线程上的消息使用准入表，而不是跟帖强度。

## 准入

每个来源的策略都有一张准入表。它的行是接收范围：

- **Feishu：** 每个已配置的群、机器人收到提及的其他群，以及私信。只有在 Feishu 卡片上 **其他群** 设为 **仅 @** 时，其他群才会被接收。
- **GitHub：** 新 Issue、新 PR、评论和默认分支的 CI。

一行最多有三个格。每格决定一条消息成为明确请求、推断候选，还是什么都不成为：

| 格 | 选项 | 默认 |
| --- | --- | --- |
| 在名单上，未指向 agent | 推断、忽略 | 推断 |
| 不在名单上，指向 agent | 明确、推断、忽略 | 忽略 |
| 不在名单上，未指向 agent | 推断、忽略 | 忽略 |

未指向 agent 的格只在该来源接收全部消息的地方可用，例如设为 **全部消息** 的 Feishu 群，或开启了接收全部开关的 GitHub 范围。CI 结果没有发送者，因此其行只提供最后一格。机器人的消息使用机器人名单，而不用这些格。

把“名单外但指向 agent”这一格设为明确，会让该范围内任何人通过 @ agent 来请求工作。这对专门的客服群可能有用。推断候选仍取决于接受模式。跟帖通常绕过该表，但明确格仍会授予明确强度。

准入表是策略版本的一部分。削弱某一格不会立即停止按它接受的在途工单。当这些工单在恢复前被重新校验时，其授权可能会因此被撤销。

### 机器人与自动评审者

宿主把 GitHub App、以 `[bot]` 结尾的登录名以及 Feishu 机器人识别为机器人。来源可以列出 `dependabot[bot]` 这样的机器人，其消息可以成为推断候选。它们必须要么指向 agent，要么发布在接收全部消息的范围内。它们不能发出明确请求或停止工单。

使用普通账号的自动评审者对宿主而言算作一个人。它的评论会抵达订阅的工单并产生跟帖通知。团队提示词必须把这类账号标记为自动评审者。

## 路由候选

主 Session 用 `orchestrator_route` 路由明确候选。一次调用可以包含多个接受、挂接、停止或忽略决定。每一项独立处理：被拒绝的项或缺失的字段不会妨碍其他项执行。

推断候选通常需要完整研判。有一个捷径：如果它的卡片明显不涉及任何已启用的规则，例如闲聊或无关讨论，主 Session 可以直接忽略它。决定会记录 `ignoredFromCard`，以便与规则研判区分。主 Session 在其策略提示词部分读取已启用的规则。

接受推断候选始终需要研判。直接接受会拒绝准入未认定为明确的触发。

## 接受模式与规则

接受模式是策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断情形都不成为候选，例如未指向 agent 的消息、机器人的消息，或名单外人员的跟帖 |
| `observe`（默认） | 对推断候选进行研判；正面研判记录为带“本会接受”标记的忽略，且不会接受任何内容 |
| `auto` | 推断候选的正面研判会被接受 |

明确请求在任何模式下都有效。从 `observe` 开始，在审阅已记录的决定之后再切换到 `auto`。每次研判都会把每条已启用的规则恰好判断一次，无论是否匹配。主动接受至少需要一条匹配的规则。

每条规则描述一类主动工作。工单的授权会记录匹配的规则，其执行器会收到这些规则的名称和说明。

对于该工单，规则中的流程和沟通要求会覆盖默认值。一条静默规则可以抑制确认；一条评审规则可以指定评审人以及合并前所需的批准。适用于所有工单的要求应改放在团队提示词部分。

## 策略版本

规则、接受模式和每个来源的策略共同构成策略版本。每个授权都会记录它被接受时所处的版本。

版本变更会丢弃正在运行的评估并重新排队其触发。它还会向每个受影响且存活的工单发送一条策略变更输入。该输入会说明：

- 某条匹配的规则发生了变化（包括其新文本），或不再适用；
- 请求者可能已无权发起工作；或
- 主动工作不再被接受，例如因为模式从 `auto` 改掉了。

不受影响的工单不会收到通知。该变更不会立即撤销存活工单的授权。

来源配置与策略相互独立。它控制系统接收什么：读取哪些群，以及某个范围是接收全部消息还是仅接收提及。授权记录其来源和接收范围。恢复要求该来源仍在监听该线程，但不要求它仍然接收那里的每一条消息。

来源关闭期间其回复会等待；如果来源不再监听其目的地，回复会被丢弃。

关于执行器可以如何处理自己结果的某个条件（例如什么时候可以合并），并不决定谁可以授权工作。它属于 agent 的指令，不属于策略。

## 恢复与停止

已结束的工单保留其授权。有人在它自己的线程上发消息，可以在没有新评估或新决定的情况下恢复同样的工作，无论发送者是谁。机器人和 CI 不会唤醒已结束的工单。执行器判断该请求是否符合范围，不符合就结束这一轮。

只有三种操作会改变授权：接受会创建它，人的停止会撤回它，校验失败会撤销它。被人停止的工单保持结束，不再收到任何内容。在那里请求工作需要新的接受。

### 恢复前的校验

来源必须仍在监听原线程。其余检查取决于授权的依据：

- 明确的跟帖授权直接通过。
- 推断授权需要 `auto` 模式，并且其匹配的规则仍然启用。
- 通过准入表格被接受的授权，必须按今天的表和发送者成员关系仍能获得至少原强度的准入。因此，把发送者从名单中移除，可能会撤销通过“名单上发送者”格接受的授权。
- 机器人的授权要求该机器人仍在来源的机器人名单上。推断的表格授权和机器人授权同样需要 `auto` 模式和已启用的匹配规则。
- 其他授权要求发送者仍在来源的允许名单上。

校验失败时，工单保持结束，不接收任何等待中的消息。每条消息都被视为未抵达任何工单；如果没有其他工单拥有它，它就进入评估。主 Session 不会被告知它已抵达某个执行器。暂停处理后也是如此。挂接到该工单会被拒绝，后续工作需要新的接受。

- **人在线程里说“停止”是一个普通触发，** 由评估决定停止。执行器不能声明有人让它停止。
- **在面板上停止是一条命令。** 它直接作用于工单，并记录为手动停止。
- **等待类条件属于来源。** 例如“N 小时无 assignee”这样的条件会是一个自行等待并再次检查的来源；评估永不等待。

## 评估未完成时

时限从候选抵达主 Session 时开始计时。等待投递的时间不计入，未投递的候选永不过期。

过期的评估会把它的触发排队重试。连续两次重试之后，第三次过期记录为 `unavailable`。研判失败也记录为 `unavailable`；之后的一个触发可以启动新的评估。策略变更或基于过期策略做出的决定记录为 `unavailable`，并立即按当前版本重新排队该批次。

`evals` 健康项报告过去一小时内未解决的 `unavailable` 决定。`scripts/dsh-superagent status` 会包含该错误。

只有当 `unavailable` 决定不足 24 小时、仍是其线程上的最新决定、尚未被忽略，且该线程既未排队也不在评估中时，面板才会请求人处理。人可以再次评估该触发，或忽略这个问题。
