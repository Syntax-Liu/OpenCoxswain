# 附件（拖入 / 粘贴 / 选择）

> 三种方式把文件交给 Agent。**图片走多模态通道，文本直接注入上下文。**

---

## 三种入口

| 方式 | 操作 |
| --- | --- |
| **拖入** | 把文件拖进输入框区域，出现"松手添加附件"提示 |
| **粘贴** | 截图后直接 `Ctrl+V`——最高频的方式 |
| **选择** | 点输入框左下角的 `＋` |

三种方式可以混用，附件会累积。

---

## 三类文件三种处理

| 类型 | 处理 | 说明 |
| --- | --- | --- |
| **图片**（png/jpg/webp/gif/bmp） | 转 data URL，走多模态通道 | 单一上限 5MB |
| **文本/代码**（ts/py/json/md/log…） | 读内容**注入上下文** | 超 200KB 截断 |
| **其它二进制** | 只带文件名和大小 | 读不出内容，但让它知道有这个文件 |

文本文件是**直接注入内容**的——比让它自己 `search_files` 更快，
而且你明确知道给了它什么。

---

## 模型不支持图片时会怎样

**这是设计上最需要说清的一点。**

因为允许自定义模型，不能假定所有模型都能看图。所以：

```
附件进输入框
   ↓
当前绑定模型的 supportsImages 为 true？
   ├─ 是 → 图片走多模态内容块（image_url）
   └─ 否 → 图片降级成一行文字："〔图片 xxx.png：当前模型不支持读取图片〕"
```

**关键取舍**：不支持时**不拒绝用户拖入**，而是降级并明确提示。

理由：直接拒绝会让人不知道"为什么不能发图"；
降级提示让人立刻明白"该换个支持看图的模型"。

`supportsImages` **默认 false**。没声明支持的模型一律按不支持处理——
因为"发了图片被端点 400"比"降级成文件名"更糟：
后者用户看得懂，前者只是一句"发送失败"。

## 为什么要改数据库

图片要落库，否则**刷新页面就看不到自己发过的图**。

这带来一次 schema 升级（**v7 → v8**）：

```sql
ALTER TABLE message ADD COLUMN images TEXT;   -- JSON 数组；NULL = 没有附件
```

老库自动迁移，老数据 `images` 为 NULL，不影响回放。

---

## 安全约束

| 约束 | 原因 |
| --- | --- |
| 只接受 `data:image/` 开头的内联数据 | 不接受外部 URL——否则等于开了"让服务端去抓某个网址"的 SSRF 口子 |
| 非法 URL 返回 **400** | 显式拒绝，不静默跳过 |
| 单文件大小上限 | 一张 20MB 的图会让整个请求超时 |

## 实现过程中踩的坑（值得记）

**图片在入库前就丢了，而且每一层看起来都"对"。**

链路是：`HTTP → userSays → inbox → recordUser → SQLite`。
实际排查发现**四层各有一处漏**：

1. **DTO 没返回** `images` —— 存进去了但界面拿不到
2. **SQL 没写** `images` 列 —— 根本没存
3. **schema 没有这一列** —— 需要 v8 迁移
4. **`inbox.push` 构造 InboxItem 时漏了 `images`** —— 数据在这一步就没了

第 4 个是最隐蔽的：类型上 `images` 是可选的，漏传不会报错。

**所以加了测试专门守这条**（`purity.test.ts`：图片附件会被带上）。

教训：**穿越多层的可选字段，每一层都要有测试或真实端到端验证**，
否则任何一层漏了都不会报错，只会表现为"功能就是不生效"。

## 验收记录

真实应用里验证过：

```
＋ 按钮: true
placeholder: 发消息或创建任务，/ 调用指令，@ 文件或对话（可拖入文件）
拖入结果: chips=1 thumb=1      ← 拖入后出现缩略图
气泡图片数: 1                  ← 历史消息里的图片能显示
```

HTTP 层验证：

```
带图片的消息数: 1
 - 文本: "看看这张图"
   图片: test.png
空请求: 400        ← 没有文字也没有图片
恶意 URL: 400      ← 非 data:image 的外部 URL
```
