# 第一轮：能力面

## 结论

**我们的"骨架"不落后，缺的是"器官"。**

- **架构方向是对的**：最有说服力的发现是——**11 个系统里，没有一个导入
  通用 agent 框架**，全靠手写循环。我们"零依赖自研"的路线和整个行业一致。
- 但当时只实现了 7 个子系统里的 3 个，缺的 4 个（上下文压缩、Skill、
  沙箱、LSP）都是"真用起来才会痛"的地方。

## 行业基准：7 个标准子系统

| # | 子系统 | 行业做什么 | 我们的状态 |
| --- | --- | --- | --- |
| 1 | **循环 (Loop)** | 异步循环，轮次/步骤状态机 | ✅ |
| 2 | **工具 (Tools)** | 注册表 + 执行流水线 + 权限拦截 | ✅ |
| 3 | **上下文管理** | 压缩、剪枝、token 计量 | ✅ v0.24.0 双层压缩 |
| 4 | **安全 (Safety)** | 审批、沙箱、权限预设 | ✅ v0.28.0 命令级沙箱 |
| 5 | **编排 (Orchestration)** | 子 Agent、并发、生命周期 | ✅ 强（我们更细） |
| 6 | **扩展面 (Extension)** | Skill、MCP、插件、hook | ✅ Skill + MCP + hook |
| 7 | **协议 (Protocol)** | MCP / ACP / SKILL.md | ✅ MCP + SKILL.md |

## 6 项缺口的处理

| # | 缺口 | 版本 | 说明 |
| --- | --- | --- | --- |
| 1 | 上下文压缩 | v0.24.0 | 双层策略：工具结果剪枝 → 折叠历史 |
| 2 | `edit` 工具 | v0.24.0 | 精确替换 + 缩进容忍 + CRLF 保持 |
| 3 | Skill | v0.25.0 | SKILL.md，按需加载（实测省 70% 目录 token） |
| 4 | MCP | v0.26.0 | stdio 传输，真实子进程验证 |
| 5 | 代码导航 | v0.27.0 | find_symbol / list_symbols |
| 6 | 命令沙箱 | v0.28.0 | 命令级静态检查 + 重定向识别 |

## 我们领先的地方（当时就有，现在更强）

1. **四层编排**：多数 harness 是"一个 Agent + 子 Agent"，我们是显式的四层。
2. **跨项目写冲突检测**：11 个系统里一个都没有。两个项目同时改同一份
   共享文件，别人不管你，我们拦。
3. **验收复核**：D 说完成，系统真的跑命令验证，不看它自己怎么说。
   论文的 29 个模式里没有对应项。
4. **批次机制**：大部分 harness 是单 Agent，压根没有"并发派活"这个概念。

# 第二轮：单 Agent 交互

## 来源

| 来源 | 是什么 | 为什么可信 |
| --- | --- | --- |
| [Developer Experiences with Cursor AI-native IDE](https://arxiv.org/abs/2610.20618) | 14714 条官方论坛帖、跨两年多的纵向研究 | 大规模真实用户抱怨，不是问卷 |
| [Design for agents（Microsoft Learn）](https://learn.microsoft.com/en-us/agents/design-guidelines/overview) | 微软的 Agent 设计指南 | 平台方的一手规范 |

那篇 Cursor 研究最值钱的结论：

> 讨论**71% 集中在工作流关键机制**（上下文索引、模型路由、Agent 工作流），
> 而这些既是价值来源，也是挫败来源。负面体验集中在
> **可用性、价格、可靠性**——安装设置、用量限制、崩溃、延迟。

**判断**：用户抱怨的不是"功能不够"，而是**"功能在关键时候不好用"**。

## 当时的 5 项缺口（全部已补）

| 优先级 | 项 | 版本 | 不做的后果 |
| --- | --- | --- | --- |
| **P0** | 等待状态说清楚在等什么 | v0.36.0 | 用户以为卡死 |
| **P0** | 错误卡片保留 + 三分类 | v0.37.0 | 出错了不知道怎么办 |
| P1 | 在跑时提示"可以继续说" | v0.38.0 | 用户不敢发 |
| P1 | 侧栏批次分组 | v0.38.0 / v0.46.0 修正 | 分不清哪几个是同一批 |
| P2 | 上下文用量可视化 | v0.34.0 | 不知道何时该开新会话 |

## 一个自我审视

做完 9 项易用性改进后回看，**没有一项该删**，但两项的形态调整了：

| 项 | 调整 |
| --- | --- |
| 全文搜索 | 还没真正用起来，等会话多了才知道效果 |
| 首次引导 | 从"空对话框才显示"改成"没看过就显示"——老用户更需要 |

## 不该抄的

| 做法 | 为什么不做 |
| --- | --- |
| Chat-first 极简界面 | 我们是任务指挥软件，不是聊天软件 |
| 自动重试不告诉用户 | 静默重试会让用户以为"变快了"，实际是掩盖问题 |
| 隐藏在设置里的关键开关 | 用户找不到等于没有 |

# 第三轮：多 Agent 编排的失败模式

## 方法

不靠猜。去翻**别人真实踩过的坑**——竞品的公开 issue 比任何综述都准。
然后逐条核对我们有没有同样的问题，有就真跑一遍确认，再修。

## 两个一手证据

| 来源 | 问题 |
| --- | --- |
| [Codex #31178](https://github.com/openai/codex/issues/31178) | 子 Agent 的工作流感觉是串行的，因为父线程的追问被排队，**被中断的子 Agent 结果没有浮出来** |
| [Codex #37827](https://github.com/openai/codex/issues/37827) | 并行会话因为**重复的审批提示**而变得不可用 |

## 第一个问题：被中断的 Agent，结果浮不出来

### 我们有，而且是两层问题

**问题 1：取消时不通知 Assistant**

`finishExecutor` 只改状态。用户按停止后，Assistant 可能还在等这个 Agent，
或者在下一轮里把"还在跑"当成事实。

**问题 2：被中断时"进展"是空的（更隐蔽）**

`summary` 只在创建时设为 `null`，**运行过程中从不更新**。

所以"取消时保留阶段性结论"这个设计**是空承诺**——根本没有东西可保留。

### 修法（v0.47.0）

1. 取消时发内部通知，说清"已被用户停止"+ 停之前做到哪了
2. runner 每轮文本输出都回调 `onPartialText`，存进 summary

**一个刻意的取舍**：取消通知**只发事实，不催它立刻汇报**。
用户自己按的停止，他知道发生了什么，Assistant 追着念一遍反而吵。

### 真实验证

```
停止前: "两种方式都得到 12 个文件。现在检查目录结构…"
停止后: cancelled
保留的 summary: 同上 ✓

Assistant 收到:
【Agent 结算】Agent「清点项目内所有 .tex 文件」已被用户停止，没有跑完。
它停之前完成的部分：两种方式都得到 12 个文件…
```

**Codex 那个 issue 说的问题，我们没有。**

## 第二个问题：并行会话被审批搞到不可用

### 场景存在，但我们比 Codex 好一半

先确认场景真的会发生。派两个会触发删除的任务后：

```
同时挂起 2 条，来自 2 个不同 Agent:
  exe_mweostx723oxj | delete | Remove-Item
  exe_mweot6ahqe6oq | delete | Remove-Item
```

**两条都是 `delete / Remove-Item`，界面上完全分不清是谁要删。**

### 我们没变成"不可用"的原因

审批是**并排显示的面板**，不是逐个弹窗阻塞。
Codex 的"不可用"是弹窗堆叠导致的，我们的交互形态天然避开了。

但**缺了"是谁"这个信息，用户无法判断该不该批**。

### 修法（v0.48.0）

`executorId` 本来就在数据里，只是界面没显示。审批面板加一行：

```
列出并清理 build/ 下的临时文件  想执行这个动作
[删除] Remove-Item  8 分钟后自动拒绝
会删除文件或数据，删掉通常找不回来（也不进版本库）。
```

## 顺带查证但**没问题**的

| 项 | 核对结果 |
| --- | --- |
| 用户连发会不会串行 | **不会**。`executorInputs` 队列按步注入，Assistant 不阻塞 |
| 多条审批会不会互相阻塞 | **不会**。面板并列显示，各自有独立超时 |
| 审批有没有超时兜底 | **有**。`approvalTimeoutMs`，超时自动拒绝 |

## 还没查证的多 Agent 失败模式

**已于 2026-11-13 全部验证完毕**，结果如下。

### 1. 多个 Agent 同时改同一个文件会怎样 ✅ 安全

派两个任务改同一个 `conflict-test.txt`。

**系统层**：写域正确声明为 `["conflict-test.txt"]`，`Gate` 检测到相交会串行准入。

**实际发生的是另一件事**：Assistant 收到第二条指令后，**没有新开 Agent**，
而是用 `message_executor` 把新指令投给正在跑的那个。

它的原话：

> 指令已改投给正在跑的 Agent-A，没有另开新 Agent——
> **同一文件两个 Agent 会互相覆盖，这点我按规矩避开了**

最终文件内容正确（Agent-Supervisor 的内容，20 字节，逐字节校验通过）。

**一个要记下的边界**：这个保护**是 Assistant 判断的，不是系统强制的**。
写域互斥只在"真的创建了两个 Agent"时生效。
如果 Assistant 判断失误，两个 Agent 还是会被创建——
那时 `Gate` 会拦（串行），但**不会告警说"你可能派重了"**。

### 2. 有依赖关系的任务会不会被正确排序 ✅ 安全

派一个两段任务：数 `.txt` 数量写进 `dep-a.txt`，再读它建 N 个星号的 `dep-b.txt`。

**结果完全正确**：

- Assistant 只派第一段，明确说"**第 2 件我先不动手**，等结算拿到确切的 N 再派"
- 第一段结算后（N=1），Assistant 派出第二段
- `dep-b.txt` 内容 = `*`（1 个星号），与 N 一致

**正确的原因**：Assistant 有"等结算再决定下一步"的自觉，
而不是把两件事并行发出去。这和组织纪律一致——依赖的任务不该并行。

### 3. 并发占满时用户追问会不会被饿死 ✅ 安全

派 5 个慢任务占满槽位，然后立即追问"现在在跑什么"。

- `POST /say` 返回 **202，耗时 2ms**——不阻塞
- Assistant 回复用了 **14 秒**——正常，远没有饿死
- 回复内容准确列出了 5 个 Agent 的 id 和状态

### 4. 多条结算同时到达会不会乱序汇报 ✅ 安全，而且有防抖

5 个慢任务自然形成了两波结算：

    17:17:57  任务1 结算  →  17:18:08  C 单独汇报这一条
    17:18:08  任务2/3/4/5 同时结算  →  17:18:19  C 汇总成一条

**4 条同一秒到达时，Assistant 合并成一次汇报**（"5 份报告结论一致…"），
而不是刷 4 条。

**这是正确的防抖行为**：信息不丢（都进上下文了），但不会把用户淹没。

## 四个假设的总结

**四个全部安全**，系统在多 Agent 并发下的表现比预期好。

但验证过程暴露了一个**能力边界的模糊地带**：

| 项 | 谁在保证 |
| --- | --- |
| 同文件不互覆盖 | **Assistant 的判断**（系统只在真派两个时才拦） |
| 依赖任务不并行 | **Assistant 的纪律**（系统不强制） |
| 追问不被饿死 | 系统（不阻塞） |
| 结算不乱序 | 系统（防抖） |

前两项**依赖 Assistant 的判断质量**，而不是系统保证。

这不是 bug——把判断交给模型是合理的设计。但要记下：
**如果换一个判断力更弱的模型，这两个保护可能会失效。**

# 三轮共同的教训

## 1. 竞品的 issue 是最好的调研材料

比综述文章具体、比竞品对比表真实。**每一条都是有人付了代价换来的**。

以后每轮调研的第一站就应该是：翻主流 Agent 产品的公开 issue，
按"close 的 / 抱怨最多的 / 涉及并发的"排序读。

## 2. "设计上做了"和"实际有数据"是两回事

`finishExecutor` 的签名里有 `summary` 参数，注释写着"保留原 summary"。
读代码会觉得"这个考虑到了"。

但实际上 **summary 永远是 null**——因为没人更新它。

**这类问题的共同特征**：参数存在、注释合理、代码路径正确，
只是**数据从没被填进去**。类型检查抓不到，测试也抓不到（没测过中断场景）。

## 3. 并发场景要主动构造，不能等它自己出现

正常开发时不会同时派两个会删文件的任务。
**必须刻意构造**才能看到"两条审批长得一模一样"这个问题。

## 4. "方案做完了"和"能用"是两件事

第一轮补完 6 个能力缺口后，按功能清单看已经"完整"了。
但真正的交互问题（等待状态、错误展示）一个都没解决。

**能力面齐了 ≠ 用户会觉得好用。**
