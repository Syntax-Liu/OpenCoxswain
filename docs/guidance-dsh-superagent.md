> 定位：**作为本项目的指导方案之一**，和 `competitor-gap.md`、`ui-spec.md` 同级。
> 记录时间：2026-11-12

---

## 零、为什么要抄它的思路

它不是竞品——它是同赛道团队把"主动型 Agent 该怎么设计"写成了一整套
带**被否决概念表**的文档。这类文档最值钱的地方不是它做了什么，
而是它**明确写了什么不做、以及为什么**。

---

## 一、最该抄的四条

### 1. 「概念要少」——这条直接对我们有约束力

> 一个业务需求要么成为其中之一的一个属性，要么成为 agent 遵循的提示词。
> 设计不为此新增概念。

我们的四层（User / Supervisor / Assistant / Agent）已经是四个概念。
**从现在起，任何新需求先问：能不能作为现有概念的属性？**

反例警惕：
- 想加"项目组"？→ 可能是 `Project` 的 `tags` 属性
- 想加"任务队列"？→ 可能是 `Executor` 的状态
- 想加"工作流"？→ 大概率是提示词，不是新实体

### 2. 「注意力成本」——唯一的度量

> 尽可能少地占用人的注意力，尽可能多地交付价值。
> 每一项都必须给出多于这份消耗的价值，否则就会被去掉。

这条对**界面和通知**直接适用。我们最近做的九项易用性改进，每一项都应该
过一遍这个筛子：它是不是在帮用户更快做决定，还是只增加了信息量？

已经暴露的问题：会话搜索跳转、上下文用量百分比、状态栏 4 个指标——
**是不是有些只是"看起来专业"而没帮用户做决定？** 这是个待审视项。

### 3. 授权 ≠ 上下文（这条我们目前混着）

> 消息、评论和引用的文档只是决策的输入；它们无法改变这些权限。

DSH 把 **Mandate（授权）** 和 **Subscription（上下文）** 严格分开：
- 订阅扇出上下文时，**不检查发送者、不授予权限**
- 相关性只增加上下文，**永不决定路由**

**对我们的启发**：Supervisor 把跨项目的相关信息转给某个 Assistant 时，
那些信息应该被标记为「仅上下文」，不带权限、不唤醒任务。

我们现在没有这个概念——所有注入的消息看起来都一样。这是要补的。

### 4. 收尾条件用外部信号，不用自评

> 工单结束条件是外部信号——关注的 PR 全部关闭才结束。

我们已经有"验收复核"（D 说完成，系统真的跑命令验证），方向一致。
但 DSH 更彻底：**完成条件绑定在外部状态上**（PR merged/closed），
而不是"跑了一个命令成功了"。

## 二、值得直接抄的机制

| 机制 | 我们的对应物 | 差距 |
| --- | --- | --- |
| **优先级阶段表**（自上而下第一个匹配赢） | 无，状态是枚举 | 可以借鉴：`Executor` 的阶段由"在等什么"推导 |
| **人专用槽位**（并发满时给人留一条通道） | 无 | 值得做：用户的消息永远不被 Agent 挤占 |
| **先存储后执行**（动作先入持久化队列） | 副作用台账（执行前落 pending） | **已有，方向一致** |
| **单写入者 per 状态** | 部分 | 可以做成一页表，避免多处写同一状态 |
| **错误码表**（`UserError(code, values)`） | 纯文本错误 | 可做：界面按语言配词 |
| **入站卡片截断预算** | 有 `maxOutput` 但非分类 | 可细化：报告 600 字、确认 100 词 |
| **策略即数据 + 版本哈希** | 权限档位（固定的四档） | 是否要做成可配置规则？**暂不做**，等有需求 |
| **观测模式**（先跑"本会接受"再切自动） | 权限 `auto` 档 | 可以加一个 `observe`：记录但不执行 |

## 三、和我们冲突、需要判断的

| DSH 主张 | 我们现状 | 我的判断 |
| --- | --- | --- |
| 只有 2 个 Session（主 + worker） | 我们有 4 层 | **不跟**。四层是我们已验证的差异化（跨项目冲突、批次） |
| 主 Session 不做技术决策、不等待 | Supervisor 目前就是只路由不干活 | **已一致** |
| 策略收紧不撤销在途工单 | 我们改权限是立即生效 | 折中：在途不中断，但**续跑时按当前权限重新校验** |
| 提示词工具描述锁在代码里 | 我们的工具描述也在代码里 | **已一致** |
| 外部文本永不改规则 | 我们有注入风险（MCP、附件内容） | **要检查**：MCP 返回的内容会不会被当成指令 |

## 四、四条我特别想记住的话

> 「目标是：在正确的时间给出正确的帮助，其他任何时间什么都不给。」

> 「工单结束不会结束授权：只有人的停止才会撤回它。」

> 「外部文本：它是数据，永不改变规则或授权。」

> 「文档按编号串行，读者永不需要未介绍的概念。」

最后一条对我们的 `docs/` 也适用——但这批文档已经太多了（30+ 份），
**下一步该合并而不是新增**。

---

## 五、这份文档怎么用

不是读完就算。它应该**改变做决定的默认值**：

1. 加新功能前问：能不能是现有概念的属性？
2. 加新界面元素前问：它帮用户做决定了吗，还是只增加了信息？
3. 处理跨层信息传递时问：这是上下文还是授权？
4. 判断"完成"时问：有没有外部信号可以绑定？
