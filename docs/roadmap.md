### A4 的实际做法（2026-11-11 完成）

**验收给结论，台账给证据。**

四类副作用：

| 类别 | 举例 | 可补偿 | 去重 |
| --- | --- | --- | --- |
| `fs.write` | `write_file` | ✅ | ✅ |
| `fs.delete` | 命令里的 `rm` / `del` | ✅ | ✅ |
| `proc.exec` | `run_command` | ❌ | ❌（跑两次就是两次） |
| `net.send` | `git push` / `curl -X POST` | ❌ | ✅ |

| 关键决策 | 理由 |
| --- | --- |
| **执行前就落 `pending`** | 等执行完再记，进程崩在中间就什么都没留下。用户该看到"它尝试过" |
| **被审批拒绝记 `rejected`，不是 `failed`** | "没执行"和"执行了但失败"是两件完全不同的事 |
| **命令里的删除/外发归到更具体的类别** | 台账里"删了文件"比"跑了命令"更有审计价值 |
| **读操作不进台账** | 否则清单被噪音淹没，关键记录反而看不见 |
| **幂等键 = sha256(执行者 + 工具 + 排序后参数)** | 同一次派活重复写同一文件只记一条；但命令不去重 |

**验收**（`ledger.test.ts`，17 条）：
- [x] 写两个文件 → 台账两条，参数可读
- [x] **被审批拒绝的动作记为 `rejected`**，并留下拒绝原因
- [x] 重复写同一文件只记一条；同一条命令跑两次记两条
- [x] 读操作不产生记录
- [x] 参数顺序不影响幂等键

**数据迁移**：新增 `side_effect` 表，schema v5 → v6。

**线 A（让产品可信）到此完成。**

### A3 的实际做法（2026-11-11 完成）

**核心原则：只采信系统自己复核出来的证据，不采信 D 的自述。**

三类验收标准：

| 类型 | 怎么验 | 谁说了算 |
| --- | --- | --- |
| `command` | 系统在项目目录里**独立重跑** | 退出码 |
| `diff` | 系统统计工作区相对基线的改动 | 有无改动、增删行数 |
| `human` | 需要人看 | 人 |

三档策略（对齐 legacy）：`auto` / **`unverified_only`（默认）** / `always_human`。

| 关键决策 | 理由 |
| --- | --- |
| **复核失败直接判 failed，不允许人工覆盖** | 否则"验收"形同虚设——人一被催就会点通过 |
| **复核命令同样过危险动作闸门** | 否则 D 可以在验收标准里写 `rm -rf .`，验收时真的执行，等于绕过 A2 |
| **没声明标准时 `acceptance` 为 `null`** | 不伪装成"通过"。界面显示"未声明验收标准"，而不是绿色对勾 |
| **验收标准解析失败就拒绝派活** | 一个拼错的验收标准如果被静默忽略，等于没有验收 |

**验收**（`acceptance.test.ts`，17 条）：
- [x] `diff` 标准检出「工作区没有任何改动」→ **D 声称完成但没做，判失败**
- [x] D 确实改了文件 → `diff` 通过
- [x] `command` 失败 → failed，且 `needsHuman=false`（不允许覆盖）
- [x] 复核命令被审批拒绝 → failed 而不是放行
- [x] 没声明标准 → `acceptance: null`，不伪装成通过
- [x] 非法验收标准（缺 check / 类型错 / id 重复）直接拒绝

**数据迁移**：`executor` 表新增 `criteria` / `policy` / `acceptance` 三列，schema v4 → v5，老库自动升级且默认值安全（`[]` / `unverified_only` / `null`）。

### A2 的实际做法（2026-11-11 完成）

**五类不可逆动作**在执行前拦下：`delete` / `push` / `publish` / `pay` / `external_send`。

| 关键决策 | 理由 |
| --- | --- |
| **执行前冻结，不是执行后通知** | 删掉的文件不会自己回来。"先做了再让你确认"等于没有把关 |
| **超时自动拒绝（默认 10 分钟）** | 用户可能一直不在，执行者不能无限挂起。到点判 `expired`，D 收到原因后可以换做法 |
| **拒绝原因回灌给模型** | D 看到"用户拒绝了 rm -rf（理由：那是测试夹具）"才能调整；只说"失败"没有意义 |
| **只读任务不经过审批** | 它本来就写不了，在更早的只读拦截处就挡掉了 |
| **收紧正则，不误伤** | 旧实现 `\bpay\b` 会把 `grep pay`、`checkout_payment.ts` 当成付款并挂起——用户会烦到关掉这个功能 |

**顺带修掉的一个真实缺陷**：`run_command` 在 Windows 上跑的是 **cmd.exe**，但工具描述和提示词
却建议用 `Get-ChildItem` / `Remove-Item` 这类 PowerShell 命令——在 cmd 下根本不识别。
现在工具描述和提示词都明确说明了 shell 环境，并给出 `powershell -NoProfile -Command "..."` 的写法。

**验收**（`approval.test.ts`，14 条）：
- [x] 识别五类危险动作
- [x] **不误伤** 10 条常见安全命令（含回归 `grep pay`）
- [x] `git push --dry-run` 不拦（无远端副作用）
- [x] 批准后动作真的执行（断言文件被删掉）
- [x] **拒绝/超时后文件仍在**（断言"没批准的动作绝不能被执行"）
- [x] 只读任务不产生审批记录
- [x] 重启后残留的 pending 审批自动作废

**复用来源**：legacy `packages/core` 里 `mandate.ts`、`side-effect.ts`、`acceptance.ts` 都有可用实现（不含测试共 46KB、14 个文件）。这是**移植**而不是重写。

### A1 的实际做法（2026-11-11 完成）

**最初的设计是错的**：我原本打算按可配置单价折算美元并做预算硬停。
用户指出这没有意义——不同模型单价不同、厂商随时调整、软件离线无法获取实时价格，
而且用户本来就能在服务商后台看到真实账单。**估算出来的金额只会误导人。**

改为：**只呈现运行指标 + 一个纯 token 的止损线**。

| 做 | 不做 |
| --- | --- |
| 记录轮次、步数、输入/输出 token、缓存命中、耗时、上下文占用 | ~~估算金额~~ |
| 展示吞吐（tok/s）与缓存命中率 | ~~单价换算~~ |
| `tokenGuard`：单任务 / 每日 token 上限，超了**真停** | ~~美元预算~~ |

**为什么还保留止损线**：token 是模型**自己报告**的真实数字，不需要任何假设。
一个失控的执行者（死循环、反复重试）可能在几分钟内烧掉大量额度，
用户需要一条线，超了就停，而不是等账单出来才发现。

**实现要点**：
- `RunMetrics` 存进 `executor` 表（schema v3，带迁移）；
- 每轮模型返回后回调 `onProgressMetrics`，累计超标立即 `abort()`；
- 派活前检查日上限，超了**直接拒绝**而不是排队（排队会让用户以为等会儿能跑）；
- 中止后落「待决策」汇报，写明"这是止损线，不是计费"。

**验收**（`guard.test.ts`，16 条）：
- [x] D 每轮记录 token，落 `executor` 表
- [x] 项目可设 token 上限
- [x] 运行中累计超限 → 立即中止并出「待决策」
- [x] 超限后拒绝派出新执行者，原因可读
- [x] 测试：模拟烧 token 的 D，断言到阈值被停掉
- [x] 界面显示轮次/步数/吞吐/token/缓存/上下文，沿用"—"表示"未报告"

**复用来源**：legacy `packages/core` 里 `mandate.ts`、`side-effect.ts`、`acceptance.ts` 都有可用实现（不含测试共 46KB、14 个文件）。这是**移植**而不是重写。

**为什么放在最前面**：A1 和 A2 直接决定"敢不敢用"。其余所有功能都建立在"用户信任它"之上。

## 3. 建议的推进顺序

```
线 A  让产品「可信」                    ✅ 全部完成（A1 / A2 / A3 / A4）
第 1 步  B1 记忆自动提炼                ✅ 已完成
第 2 步  B4 界面细节                    ✅ 已完成（虚拟滚动除外，见 T5）
第 3 步  C1 IM 通道（Telegram）          ✅ 已完成
第 4 步  C2 自动更新                     ✅ 已完成
第 5 步  C3 单实例锁 + 托盘              ← 下一步：打包体验
```

### 为什么 A 完成后转 B

1. **A 线解决了"敢不敢用"**：额度有止损、不可逆动作有人拍板、结果有独立复核、改动有台账。
   继续在 A 上堆功能收益递减。
2. **B1（记忆自动提炼）现在做正合适**。之前排在 A 之后，是因为"验收不可靠时自动记忆
   会把错误沉淀成正确"。现在验收可靠了，这个前提成立。
3. **B4（界面细节）成本低收益高**：消息复制/重发、执行者搜索、长列表虚拟滚动，
   都是天天用得到但一直没有的。
4. **C1（IM）在 B 之后**：产品本身不好用时，多一个入口只会让糟糕体验传播更快。

## 4. 明确**不**做的方向

记录这些是为了避免以后反复讨论。

| 方向 | 为什么不 | 什么时候重新考虑 |
| --- | --- | --- |
| **云端执行 / 云沙箱** | 用户要的核心价值是"本地优先、代码不出机器"。云执行把最大的差异化点抹掉了 | 除非用户明确要求"多机协同"，否则不做 |
| **向量数据库记忆** | TRAE 宝 的实践证明 Markdown + 规则检索够用，且**用户能直接看懂和修改**。向量库会让记忆变成黑盒 | 当记忆条目超过数千条、检索明显不准时再评估 |
| **依赖外部 Agent 框架** | 用户明确要求自研整套。且已经踩过 dsh 插件路线的坑（两套抽象并行漂移） | 不做 |
| **D 嵌套派活** | D 只干一件事，这让"谁先完成先报"和写域互斥都能成立。允许 D 再派 D，状态就不可控了 | 不做 |
| **自动执行定时/模板** | 这两项只能建议，不能自动开工。自动执行等于放弃"人拍板" | 不做 |
| **多租户 / 团队共享** | 本地优先的产品没有"团队"概念 | 有真实需求再说 |
| **现在上插件框架（含 Cordis）** | 插件框架是为**多来源贡献**准备的。现在能力都是自己写、一个人维护，上框架等于为不存在的问题付复杂度代价，还会动摇刚做完的可信性。**已改为先切边界**，见 [architecture.md](architecture.md) | 有第三方要贡献、或同一能力需要多种实现并存时 |
| **复制 DSH 源码** | 许可虽是 MIT，但它的插件代码深度依赖 Cordis，搬过来等于把 Cordis 搬进来——正好违背"不变成它的插件"。**只参考设计思路** | 不做 |

## 5. 每条都要回答的三个问题

后续无论做哪一项，都先回答：

### 5.1 它会不会让 C 骗人？

C 的汇报必须可核查。任何新功能都不能让 C 有"看起来完成了"的捷径。

**反例**：如果验收改为"D 说自己完成了就算完成"，那 D 的 `finalText` 就成了事实来源——它会为了结束而写"已完成"。

### 5.2 它会不会打断用户？

用户的明确要求是**连发不打断**、**不要空等**。新功能不能引入新的阻塞点。

**反例**：如果成本超限时弹一个阻塞式对话框，用户正在连发的三条消息就丢了。

### 5.3 它能不能被验证？

沿用现在的做法：**先写会失败的测试，再写实现**。特别是
"这个缺陷曾经发生过"的回归测试要写清楚原因。

**反例**：只读并行那个缺陷——`scopesConflict` 把"只读"和"未声明"混为一谈，
导致三条任务串行。修复后有 `parallel.test.ts` 守着，注释里写了当时的现象。

**一个真实的架构障碍（值得记下来）**：

界面是通过 `http://127.0.0.1:PORT` 加载的，**不是 Tauri 本地协议**，
所以前端拿不到 Tauri IPC、调不到 Rust command。

两条路：

1. 把窗口改成 `tauri://localhost` 并开远程域 IPC —— 要动整个加载链路，风险大；
2. 壳把检查结果落成 JSON 文件，运行时读出来透给界面 —— 风险小，界面无感。

**选了 2**。代价是更新检查由壳触发而不是界面直接发起，对用户没有区别。

**踩过的坑**：`tauri signer generate` 在 `--ci` 模式下**会忽略密码**生成无密码密钥，
但构建时如果设了 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 就会报
`Wrong password for that key`。要么都用密码、要么都不用，别混。

### C1 的实际做法（2026-11-11 完成）

**为什么先做 Telegram 而不是飞书**：API 极简、不需要企业认证、长轮询天然适合本地软件
（不用公网 IP、不用 webhook 回调）。飞书要企业自建应用 + 公网回调，重得多。

**核心约束：IM 不是第二个入口，是同一入口的另一个通道。**

| 关键决策 | 理由 |
| --- | --- |
| 手机消息走**同一个** `userSays(projectId, text)` | 和 Web 端一字不差，不新建会话、不分叉 |
| 审批按钮**复用同一套审批记录** | 手机上点和网页上点效果相同，不会出现"手机通过了但电脑还挂着" |
| 第一个对话**自动绑定** | 省掉让用户手动去查 chat id 的痛苦 |
| 未绑定的对话**一律拒绝** | 机器人被陌生人找到时不会把内容灌进项目 |
| token **绝不回传界面** | 只告诉界面"有没有配"，避免截图泄漏 |
| token 保存前**先验证** | 存一个错的 token，之后会一头雾水 |

**一个被测试抓到的真 bug**：`saveConfig` 之后本地 `config` 引用没更新，
自动绑定的分支还在读旧值，导致第一次发消息反而收到"没有绑定"。
测试直接暴露了它，已修。

**验收**（`im.test.ts`，17 条，**全部脱网**，用假 fetch 模拟 Telegram API）：
- [x] 手机消息进入 **C 的同一个会话**（断言历史里有那条 user 消息）
- [x] 第一个发消息的人自动绑定；第二个未绑定的被拒绝，且内容**不进** C 的会话
- [x] 手机点"批准"后，**同一个存储**里查到的是 `approved`
- [x] **`offset` 用 `maxUpdateId` 推进**（回归：用条数推进会重复处理消息）
- [x] 畸形数据不抛异常

**没有验证的部分（诚实说明）**：真实 Telegram 网络连通性。
测试全部脱网，只用假 fetch 验证了解析与业务路径。

### B1 的实际做法（2026-11-11 完成）

**核心风险：自动记忆会把错误的东西沉淀成"正确的做法"。**

三条硬规则：

| 规则 | 做法 | 理由 |
| --- | --- | --- |
| 提炼出的是**候选**，不是记忆 | 候选不参与检索、不进提示词 | LLM 判断"值得记"不等于真的值得记 |
| 候选**同样过写入门槛** | 复用 `checkCandidate`：临时指令 / 模糊偏好 / 密钥三条照旧生效 | 自动提炼不能成为绕过门槛的后门 |
| 用户拒绝过的**不再提出** | 按归一化正文比对 `dismissed` | 否则每次提炼都弹同样的东西，用户会关掉这个功能 |

**验收**（`extract.test.ts`，16 条）：
- [x] **含「这次先用 axios 顶一下」的对话，提炼结果里不含它**（核心断言）
- [x] 模糊偏好、疑似密钥被拦下，并记录拒绝原因
- [x] 与已有记忆重复的不提；用户拒绝过的不再提
- [x] 候选**不自动生效**——采纳前记忆文件为空，采纳后才写入
- [x] 模型调用失败时安静返回空，不影响主流程
- [x] 最多 3 条，宁缺毋滥
