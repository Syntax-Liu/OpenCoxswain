## 1. 核心论点

### 1.1 一句话主张

> 主从双 Agent 的体验上限，不由「开了几个 Agent」决定，而由三件事决定：**主管是否永不进入执行循环、工单是否独立即时汇报、验收与冲突是否需要人做二次翻译。**

「并行」只是表象。多开几个会话也能并行，单会话派 subagent 也能并行；真正的分水岭是**谁决定「什么时候把结果还给人」**，以及**出事时谁持有全局视图**。

### 1.2 推演链（六步，逐步标注性质）

| 步 | 主张 | 性质 | 说明 |
| --- | --- | --- | --- |
| 1 | 多开 Agent ≠ 主管 | C | 手动多开会话把调度、监控、冲突判断全部退回给人；单会话 subagent 只有一个出口 |
| 2 | 差异首先是控制权 | A/B | 执行中的 Agent 没有「闲着等指令」的状态；停 = 全停。主管不占执行循环，才能随时接话 |
| 3 | 差异其次是结果时序 | A（有反例） | Cursor 的后台结果仍作为父 run 的后续轮次返回，证明「结果出口绑会话」不是假设，是现状 |
| 4 | 结果时序决定反馈延迟 | C | 完成到被看见之间的时间，就是错误没有修正入口的时间 |
| 5 | 冲突与验收是延迟的下游 | C | 冲突在合并时才暴露；不懂代码的人没有「该检查哪里」的信息前提 |
| 6 | 所以价值 = 早发现偏航 + 不用人做二次翻译 | C/D | 前者是质量账，后者是可用性账；两者都不是「多几个人干」 |

第 4 步是整条链的支点。它把「并行」从吞吐问题改写成**时间问题**：多开一个 worker，不是多一份产出，而是多一条「从完成到你看见」的延迟链；延迟越长，错误在被发现前传染的分支越多。

### 1.3 哪些是判断，哪些只是推测

| 结论 | 级别 | 依据 | 怎么用 |
| --- | --- | --- | --- |

### 1.4 边界条件：什么情况下值得做

源文第 8 轮给的不是「值得 / 不值得」，而是三个不同答案：

- **有没有必要推进**：有，但推进的是**两到三周的验证**，不是立项、不是招人、不是插件市场。
- **值不值得做**：**条件式值得**——只在你手里有一个长期泡着的垂直场景、能把「合格 / 不合格」写成规则时成立。
- **是不是开创性**：概念与架构不是，运行时原语不是，技术发明不是；**产品形态的完整实现是**（常驻永不忙 + 工单级独立上报 + 汇报与审批分道 + 证据链自动打回 + 冲突判定理由 + 面向看不懂代码的人）。

必须接受的现实：**形态三个月内可抄**。抄不走的是验收规则和项目记忆，不是界面和功能。因此「立刻停」的信号很明确：开始讨论插件市场、员工商店、自建协议、多模型路由面板——说明价值锚点滑回了调度层，而那一层已经不属于我们。

## 2. 对主从双 Agent 体验的影响

### 2.1 用户注意力是怎么被消耗的

#### 2.1.1 四种税

| 税种 | 触发点 | 为什么会累 | 设计对策 | 我们的落点 |
| --- | --- | --- | --- | --- |
| **切换税** | 从自己的事切到审 AI 的产出 | 上下文重建成本远高于判断本身 | 减少切换次数，但不把判断攒成大块 | 待决策收件箱（已有，但只收根任务，见 G1） |
| **重建税** | 看到 diff / 日志 / 术语，要先读懂才能判断 | 非工程用户读不懂，只能盲签 | 给「改了什么 / 为什么 / 验过什么 / 还有什么风险」四句话 | 验收单缺结构化说明（G2） |
| **等待税** | 不知道还要多久、卡在哪、在等谁 | 不确定感比等待本身更耗人 | 显式阶段视图 + 已等待时长 | `computeStage` 有 8 种原因，但缺「等审批」与「等恢复」（C4 / G5） |
| **返工税** | 早该发现的问题拖到最后才发现 | 延迟 × 并行分支数 = 返工半径 | 完成即入队，不攒批 | 子任务完成不进收件箱，且验收动作被根任务锁住（G1） |

这四种税不是相加，而是**互相放大**：攒批会让切换税和重建税同时翻倍；不可读的验收单会让返工税在最后一刻集中爆发。

#### 2.1.2 「即时汇报」不等于「实时打扰」

这是源文没有展开、但由它的逻辑直接推出的一条设计约束，必须写进实现：

| 粒度 | 行为 | 评价 |
| --- | --- | --- |
| **事件级流式** | 每个工具调用、每条日志都推给人 | 错。这是把执行过程当汇报，噪声淹没信号 |
| **工单级即时** | 工单完成 / 阻塞 / 需要人决策时，立即进收件箱 | **对**。审核单元 = 工单，不跨工单攒批 |
| **批次级汇总** | 等所有兄弟任务完成，一起端上来 | 错。这就是「A 压 37 分钟」的来源 |

所以正确的规则是：**同一工单内部的证据可以聚合，跨工单绝不合并**。3 分钟完成的工单 3 分钟入队；40 分钟的工单继续跑；两者互不等待。

#### 2.1.3 可观测的注意力指标

建议至少记录三个量，否则「注意力预算」只是修辞：

- **决定密度**：每小时需要人做的决定数（按收件箱入队事件计）。
- **审核延迟**：`finished_at → first_viewed_at → decided_at`，给出 p50 / p95。
- **单次判断耗时**：`first_viewed_at → decided_at`，用于判断验收单是否可读。

### 2.2 什么时候双 Agent 反而比单 Agent 更糟

| # | 条件 | 为什么单 Agent 反而更好 | 对应机制 |
| --- | --- | --- | --- |
| 1 | 主管在忙或在等审批，worker 结果只能挂起 | 单 Agent 至少结果直接回到你面前，不会隔一层 | 汇报通道与审批通道分离 |
| 2 | 完成不即时上报，等兄弟任务一起结算 | 单 Agent 是流式的；攒批让人一次面对 N 份产出 | 工单级独立上报 |
| 3 | 子任务需要人二次翻译（diff、日志、术语） | 单 Agent 的产出至少是你熟悉的形态 | 决策说明，不是 diff 审阅器 |
| 4 | 多分支写同一片区域，冲突到最后才爆发 | 单 Agent 串行写，冲突在写入时就暴露 | 单一写入 gate + 派发前写域互斥 |
| 5 | 权限全开但不可观测（烧钱、外发、看不见） | 单 Agent 的破坏半径小，且你全程在场 | 逐轮成本可见 + 外发逐次审批 |
| 6 | 任务本身不可分解或强耦合（一个文件、一次改完） | 单 Agent 少绕三四道，体感更好 | 主管应能判断「不值得拆」，直接自己做或拒绝拆 |
| 7 | 发现子任务理解偏了，却不能直接改子会话 | 单 Agent 你说一句就改 | 主管可 steer 单个 worker，不重启其余 |
| 8 | 无人值守时空转、循环、重复提问 | 单 Agent 至少你在场能按停 | 空转检测 + token 硬上限 + 超时必问人 |

**一个可用的判断式（推演，C 级）**：

```
并行净收益 ≈ Σ(节省的等待时间) − (切换 + 重建 + 验收 + 返工 + 冲突成本)
```

任务越短、越耦合、验收越依赖人，右边第二项越大。**当净收益为负时，双 Agent 不如单 Agent。** 这不是说主从结构不好，而是说主管必须有权说「这件事不拆更快」——只会拆、不会不拆的主管，是负资产。

### 2.3 信任与可控性怎么建立

#### 2.3.1 六个机制

| 机制 | 用户担心什么 | 做法 | 反例 |
| --- | --- | --- | --- |
| **可达性** | 「它跑了，我插不上话」 | 主管永不进执行循环；插话不打断正在执行的 worker | 主管自己也在跑任务，消息排在它后面 |
| **通道分离** | 审批阻塞结果回流 | 汇报走汇报队列，审批走审批队列；审批 pending 时结果仍可见 | 所有消息进同一个队列，先到先处理 |
| **授权随工单** | 「它凭什么做这件事、能不能自己扩权」 | `TaskMandate` 绑任务不绑会话；扩权必须开新单；默认 observe 影子模式 | 一次授权永久有效，越做越大 |
| **证据打回** | 不敢信「已完成」 | 证据链缺一项就不算完成，自动打回返工 | 员工自报 passed 就算过 |
| **成本可见** | 不敢开权限 | 逐轮 / 逐任务用量可见，超预算硬停 | 积分不透明，空转烧钱 |
| **决策可读** | 非工程用户无法判断 | 四句话 + 证据折叠区 + 冲突判定理由 | 甩一份 diff 让人自己看 |

#### 2.3.2 信任是阶梯，不是开关

源文第 1 轮给的四条用法，本质是一套信任升级路径，值得直接产品化：

1. **先问再派**：让它概括项目现状并标注信息来源；答得空洞，说明记忆底子不够，不放权。
2. **严格划界**：全局层只管方案 / 规范 / 调研；项目层只管当前仓库；切仓库主动切上下文。
3. **第一次只读**：整理现状、不许改文件、不许提交；看清读得准不准再放权。
4. **硬规矩写进记忆**：例如「改动前必须先给方案、等我确认再动手」。

对应到产品，就是四级信任：

| 级别 | 主管能做什么 | 升级条件 |
| --- | --- | --- |
| L0 只读 | 读代码、出方案、给建议 | 默认起点 |
| L1 建议 | 生成任务单与 diff 预览，不落盘 | 连续 N 次方案被采纳 |
| L2 执行 | 在隔离 worktree 改代码、跑测试，产出证据 | 证据链连续 N 次无缺项 |
| L3 合并 | 满足自动放行分级的改动可直接合并 | 该类型改动历史返工率低于阈值 |

**不要跳过 L0 直接给 L3。** 「完全访问」在 TRAE 宝那里等于关掉沙箱和审批，这正是用户不敢开权限的原因。

#### 2.3.3 可控性的最低要求

用户不需要「能控制每一步」，只需要三件事：

1. **随时能停**：停的是单个 worker，不是整棵树。
2. **停能保留**：已完成的产物不丢，半成品可续。
3. **停能解释**：为什么停、停在哪、下一步建议是什么。

三条缺一条，「可控」就是假的。

### 2.4 失败与中断时，用户是什么感受

| 场景 | 用户感受 | 设计含义 | 我们的落点 |
| --- | --- | --- | --- |
| 审批卡住，worker 完成却看不到结果 | 「它是不是没干活？」 | 结果与审批分通道；卡审批时结果仍可见，只是不能自动继续 | 缺 `person/approval`（C4） |
| 子任务理解偏了，但只能回去跟主管重说 | 「转述一遍又歪了」 | 主管必须能直接 steer 指定 worker，不重启其余 | 已有 `/inputs`，但无「只改这个 worker」的定向语义（G6） |
| 前台子代理被强杀 | 「刚才那半小时白干了」 | 前台转后台不能杀进程；进度要能续 | 建议纳入 G5 恢复分级 |
| 无人值守空转 / 烧钱 | 「我不知道它在烧钱」 | 空转检测 + 预算硬停 + 逐轮成本 | 已有监察与预算，但缺「为什么烧」的可读解释（G7） |
| 崩溃 / 重启 | 「现场还在吗？」 | 区分「可自动续跑 / 需人确认 / 不可恢复」，不要一律 blocked | 当前一律 `blocked`（G5） |
| 失败只给日志 | 「所以到底哪错了？」 | 失败也要四句话：改了什么、为什么失败、验过什么、建议怎么办 | 失败报告是自由文本（G7） |
| 合并时才发现冲突 | 「我根本不知道有冲突」 | 冲突要在发生时区被发现，并给出判定理由 | 有 `merge_conflict`，无判定理由（G2） |

最后一条最容易被工程视角忽略：**对不懂代码的人，「冲突」不是一道待解题，而是一次「整件事作废重来」**。他不知道该检查哪里，也不知道两边各自为什么这么改。所以冲突处理的第一产出不是「已解决」，而是**「这两处为什么冲突、我为什么这样合、你要不要否决」**。

### 2.5 设计建议（合并去重后分三层）

#### A. 结构级：不做就不成立

| # | 建议 | 可验证标准 |
| --- | --- | --- |
| A1 | 主管无执行工具 | 主管进程不产生任何 shell / 写文件调用；只有 dispatch / check / steer / cancel / accept |
| A2 | 工单 ≠ 会话，完成即报 | 子任务完成后 1 个事件周期内进入待决策收件箱，不等兄弟任务 |
| A3 | 单一写入 gate | 所有 worker 的文件变更过同一道门；同文件并发串行化并显式提示，不静默覆盖 |
| A4 | 冲突四档处置 | 文本级自动解；语义级主管解并附判定理由；架构级挂起待人；意图级派活前就问人 |
| A5 | 证据三件套 | 任何「完成」必须附 diff、执行过的命令、原始输出；缺一项自动打回 |
| A6 | 授权绑任务 | `TaskMandate` 不可自扩；扩权开新单；默认 observe |
| A7 | 审批与汇报分道 | 审批 pending 时，已完成结果仍在汇报区可见 |
| A8 | 并行上限 3 | 默认并发 2，允许到 3；超过 3 必须显式确认 |
| A9 | 熔断三件套 | 循环检测 + token 硬上限 + 超时必问人 |
| A10 | worker 不点对点 | 所有跨 worker 协调走主管，避免路径数 n(n−1)/2 与全局视图碎裂 |

#### B. 交互级：决定「能不能用」

| # | 建议 | 可验证标准 |
| --- | --- | --- |
| B1 | 审核单元 = 工单 | 同一工单内证据可聚合；跨工单绝不合并 |
| B2 | 四句话决策说明 | 改了什么 / 为什么 / 验过什么 / 还有什么风险；缺任一字段不能提交 |
| B3 | 证据折叠区 | 默认收起，可点开看命令、diff 统计、原始输出、冲突判定理由 |
| B4 | 「在等谁」阶段视图 | 等人回答 / 等人验收 / 等人审批 / 等人处理阻塞 / 等依赖 / 执行中 / 排队中 |
| B5 | 自动放行分级 | 纯文档、单向新增、有完整测试的改动可自动通过；签名变更、数据迁移、权限、删除必须人审 |
| B6 | 失败也给四句话 | 失败任务能读出「下一步怎么办」，不是一堆日志 |
| B7 | 反馈延迟可观测 | `finished_at / first_viewed_at / decided_at` 可回放，p50 / p95 可查询 |
| B8 | 等待时长可见 | 收件箱每条显示已等待多久；超阈值置顶 |

#### C. 明确不做

- **不做 worker 之间的点对点通信**：全局视图会碎。
- **不做「CEO / CTO / 工程师」十几个角色的公司模拟器**：产出不如单 Agent 直接干。
- **不做纯对话式主管**（待问卷 H21 决定）：引入 Router LLM 会带来成本、延迟与不可审计。
- **不先做插件市场 / 员工商店 / 多模型路由面板**：价值锚点会滑回调度层。
- **不为并行而并行**：主管必须能判断「这件事不拆更快」。

### 3.2 需要改的设计

#### G1 工单级汇报被攒批，且验收动作被根任务锁住（已完成，v0.14.0）

- **现状**：
  - `settleRoots` 要求 `children.every(SETTLED)` 才结算根任务；根任务 `awaiting_review` 之前，子任务的验收无法提交。
  - `decideAcceptance` 第一行就要求 `root.parentId === null && root.status === 'awaiting_review'`，**子任务即使已完成也不能单独验收**。
  - `Inbox` 只看 `root.status === 'awaiting_review'`，子任务 `awaiting_review` 不进收件箱。
- **改什么**：
  1. 允许 `decideAcceptance` 接受任意处于 `awaiting_review` 的任务（子任务或根任务）；根任务仍负责最终收口。
  2. `Inbox` 纳入 `children` 中 `awaiting_review` / `blocked` / `failed`，按完成时间排序；根任务显示「汇总中（2/3）」而不是等齐才出现。
  3. `settleRoots` 保持「等齐再结算根」不变；根任务进度由快照里的任务状态派生（收件箱显示「汇总中 N/M」），不新增事件类型。
- **落点**：[steward.ts](file:///d:/Users/37632/Products/OpenCoxswain/apps/daemon/src/steward.ts#L507-L515)、[Inbox.tsx](file:///d:/Users/37632/Products/OpenCoxswain/apps/desktop/src/components/Inbox.tsx#L30-L37)、[scheduler.ts](file:///d:/Users/37632/Products/OpenCoxswain/apps/daemon/src/scheduler.ts#L467-L491)。
- **验收**：两个子任务，先完成一个；它必须在 1 个事件周期内出现在收件箱并可单独验收，不等第二个。根任务在全部结算后仍能正确收口。

> 这一条比上一版文档写的「只改呈现层」更深：**验收入口也被根任务绑住了**，必须同时改 `decideAcceptance` 的守卫条件。

#### G2 验收单不是决策说明（已完成，v0.14.0）

- **现状**：验收单是「交付物 + 证据摘要 + 标准 + 验收人 + 结论」；没有结构化的「改了什么 / 为什么 / 验过什么 / 风险」；冲突只有 `merge_conflict` 错误，没有判定理由。
- **改什么**：新增 `DecisionBrief`：`changed`、`why`、`verified`、`risks` 四个必填字段 + `evidenceRefs` + `conflictReason`；由员工包 / 计划生成，`steward.summary` 汇总，工作台渲染成卡片，证据折叠在下方。
- **落点**：[types.ts](file:///d:/Users/37632/Products/OpenCoxswain/packages/shared/src/types.ts#L23-L40)（新类型）、`steward.ts`（`summary` / `decideAcceptance` 前置校验）、`TaskTree.tsx`、员工包 `acceptanceDefaults`。
- **验收**：非工程用户只看卡片即可判断是否通过；缺任一字段不能提交验收。

#### G3 反馈延迟不可观测（已完成，v0.14.0）

- **现状**：只有任务与运行时间戳，没有「完成 → 人看到 → 人决定」的链路。
- **改什么**：增加 `finished_at`、`first_viewed_at`、`decided_at`；派生 `review_lag_p50/p95`；超过阈值（建议 30 分钟）在收件箱标「已等待」。
- **落点**：`store.ts`（事件 / 查询）、`steward.snapshot`、`Inbox` 展示等待时长。
- **验收**：任一任务可回放三个时间点；周报能给出 p50 / p95。

#### G4 审批与汇报混排，缺阻塞影响

- **现状**：`Inbox` 把「任务单待确认 / 验收 / 危险动作 / 阻塞失败」混在一个列表，没有「它挡住了什么」。
- **改什么**：分成「需要你决定」与「刚刚完成（FYI）」两区；每条标注 `blockingScope`（挡住哪个任务 / 整个项目 / 只是通知）。
- **落点**：[Inbox.tsx](file:///d:/Users/37632/Products/OpenCoxswain/apps/desktop/src/components/Inbox.tsx)、`approvalSummary` 返回值补字段。
- **验收**：审批 pending 时，已完成任务的结果仍在「汇报」区可见，且不抢占审批的视觉优先级。

#### G5 中断恢复不分级

- **现状**：重启后运行中一律 `blocked` + 提示。
- **改什么**：分三档：`resume`（可自动续跑）、`confirm`（需人确认）、`unrecoverable`（不可恢复，给四句话说明）；`blocked` 只在 `confirm` 档使用。
- **落点**：`scheduler.recover`、`stage.ts` 增 `person/recover` 原因、工作台提示文案。
- **验收**：三类场景各一个用例；可续跑的不打扰人，需确认的给出原因，不可恢复的给出建议。

#### G6 主管「可插话」只到按钮

- **现状**：有 `assistant` 资料与消息表，但人通过确认 / 退回 / 重派 / 暂停等按钮操作；`/inputs` 只能给正在运行的任务追加文本。
- **改什么**：先做「指令面板」：自然语言输入 → 映射到已有动作（重派、暂停、加约束、改验收标准、只改某个 worker）→ 显示将要执行的动作再确认；**不做自由对话式总管**。
- **落点**：`api-rest.ts`（指令解析端点）、`apps/desktop` 输入框、`steward` 动作层。
- **验收**：输入「把校验换成更严格的模型」能生成一条待确认动作，而不是直接执行；输入「只让第二个员工改接口」不会重启其余 worker。

#### G7 失败报告是自由文本

- **现状**：失败只落错误信息与工作日志。
- **改什么**：失败也产出 `DecisionBrief` 的失败版：改了什么、为什么失败、验过什么、建议怎么办。
- **落点**：复用 G2 类型；`scheduler.fail` 组装。
- **验收**：失败任务在收件箱里能读出「下一步怎么办」，不是一堆日志。

#### G8 交付最后一公里没有分级（已完成，v0.15.0）

- **现状**：系统不修改用户主分支；任务完成后产物在分支 / worktree 里，需要用户自己合并。对工程师合理，对不懂代码的人是断点。
- **改什么**：增加「交付说明 + 一键合并（需确认）」：列出分支、改动文件、验证结果、回滚方式；自动合并只对 B5 允许的类型开放，且必须二次确认。
- **落点**：`steward` 汇总、`apps/desktop` 任务详情、`worktrees` 服务。
- **验收**：非工程用户能从「完成」走到「作品可用」，不需要命令行。
- **实现**：交付说明复用 `DecisionBrief` 四段，风险由系统按交付物类型 / 删除行数 / 副作用计算；只有全部子任务为 document、无删除行、无 `fs.delete` / `net.send`、无未决审批与冲突时才判低风险并显示「一键合并（需确认）」，需再点「确认合并」且 `planHash` 一致；系统合并失败自动 `git merge --abort` + `git reset --hard` 回滚。高风险只展示分支与手动处理指引。

#### G9 产物 diff 是整块、任务树不可审计（已完成，v0.16.0）

- **现状**：产物只有整块 `diff.patch`，人要么全看要么全信；任务树只显示状态，失败或被打回时看不出卡在哪一步，事件只能去时间线里翻。
- **改什么**：把 diff 拆成按文件明细（可展开 / 折叠、新增 / 删除 / 重命名、增删行数，二进制与大文件显式提示）；任务树节点变成可展开的审计对象（负责人、分支、阶段、验收结论、关键事件）。
- **落点**：`steward` 的 `diffReview`、`diff-review` 解析器、`apps/desktop` 验收单 / 交付说明 / 产物面板、`task-tree` 插件。
- **验收**：人能先读四段说明，再按需下钻到具体文件；失败 / 阻塞节点不用翻时间线就能看出卡点。
- **实现**：逐文件明细挂在决策说明「改了什么」下，不另起叙述；根任务汇总子任务并对同一路径合并提示；大文件截断与二进制都带提示，不静默省略。任务树审计块复用快照里的负责人与事件，卡点优先取阶段详情，取不到时明说「系统未记录原因」。DAG 仍只表达依赖，不加装饰图形。

#### G10 第一次用不起来，多项目会串（已完成，v0.17.0）

- **现状**：首次启动只有一张接入表单，没有把「接入仓库 → 生成任务单 → 确认开工」讲清楚；接入失败只抛错误码或笼统的「不是 git 仓库」；多个仓库只能在顶栏切换，没有接入第二个项目的入口，切换后审阅与交付上下文可能停在旧项目。
- **改什么**：首次启动给出三步清单并随进度勾选，完成后自动隐藏；接入失败区分路径不存在、不是文件夹、没有权限、不是 git 仓库、git 不可用与空仓库；左栏增加项目面板，支持切换与接入新项目，最近项目本地记忆，切换时清掉上一个项目的审阅与交付上下文。
- **落点**：`inspectRepo` / `steward.createProject`、`apps/desktop` 的 `Setup` / `ProjectForm` / `guide` 插件 / `projects` 插件、`App` 的当前项目状态。
- **验收**：新用户不读文档也能从安装走到「确认开工」；接入失败能直接看懂下一步该做什么；两个仓库同时接入时任务树、事件、消息与项目配置互不串扰。
- **实现**：`RepoInspectError` 携带可展示的中文原因，`POST /api/projects` 返回 400；三步清单与项目面板都经 UiRegistry 注册，不改 App 具体实现；多项目沿用存储层按 `project_id` 过滤，e2e 用两个仓库断言隔离，默认并发与验收放行规则不变。

#### G11 模板看起来省事，却让人不知道授权了什么（已完成，v0.18.0）

- **现状**：同类任务每次都要重写目标、验收和写入范围；即使沉淀成模板，如果只显示「修缺陷 / 写文档」，用户签的仍是模糊授权，事后也说不清模板到底放宽了什么。
- **改什么**：模板在选中时就把默认交付物、验收方式、写入范围、是否允许一键合并，以及继承自项目的联网 / 外发权限一起摊开；套用只预填任务单，仍停在「待确认」；模板不能把验收策略改成 `auto`，不允许合并的模板在交付阶段直接拦住。
- **落点**：`template.registry` 插件与 `TemplateRegistry`、`steward.createPlan` 的模板展开、`delivery` 的模板闸门、`conversation` 插件的模板选择与预览。
- **验收**：不选模板也能照常建单；选模板后任务单所有默认值都能在确认前看到；套用后仍是待确认；`docs` 模板写入范围只含文档路径，`bugfix` 模板不允许一键合并。
- **实现**：模板随 `WorkbenchSnapshot.templates` 下发，预览不另开面板；服务端固定 `acceptancePolicy = unverified_only` 并写入 `template_id` / `allow_auto_merge`，默认并发与人工验收规则不变。

## 6. 结论摘要

### 最值得采纳的三条

1. **工单级即时入队，而且要让子任务可单独验收。** 这是投入最小、收益最大的一条：我们已经有独立工单、独立 worktree、独立证据，但 `Inbox` 只看根任务、`decideAcceptance` 只收根任务，等于把最好的能力锁在最后一步。改完后，「谁先完成谁先汇报」才真正成立。
2. **验收单改成决策说明。** 四句话（改了什么 / 为什么 / 验过什么 / 还有什么风险）+ 证据折叠区 + 冲突判定理由。这是我们与 TRAE 宝、Cursor 最直接的体验差异，也是非工程用户能不能用的分水岭。
3. **把反馈延迟做成可观测指标。** 记录「完成 → 看到 → 决定」三个时间点，给出 p50 / p95，并对超时任务标注等待时长。没有这个指标，「双 Agent 更早发现偏航」就只是一句叙事；有了它，才能验证或证伪 H17 / H18。

### 最需要警惕的三条

1. **不要把「主管常驻」做成聊天机器人。** 源文的判据是「可达」，不是「能对话」。引入对话式主管会带来 Router LLM 的成本、延迟与不可审计，和我们已有的「总管不进执行循环」优势相冲。
2. **不要在验收闭环和呈现层未补齐时提高并发或自动放行。** 源文说得很直白：验收只能由人做时，多一个 worker 就多一条待验队列。我们已经有系统复核，但 rubric / human 仍 100% 交人；先把 G1–G3 做完，再谈并行度与自动合并。
3. **不要把「即时汇报」做成「实时打扰」。** 正确的粒度是**工单级**：同一工单内证据可聚合，跨工单绝不合并。事件级流式推送会把切换税和重建税同时放大，最后用户会选择关掉通知——那就等于回到了攒批。

### 需要你拍板的冲突

| 冲突 | 选项 A | 选项 B | 我的建议 |
| --- | --- | --- | --- |
| 主管形态（C1） | 对话式常驻总管（需 Router LLM） | 服务式总管 + 指令面板 | **B**；除非问卷 H21 显示「想直接说话」> 50% |
| 「结果好了、卡审批」是否单列阶段（C4） | 进 v1.1，`person/approval` + `idle/waiting_approval` | 沿用现有 `blocked`，只改文案 | **A**；改动小，但能消除「审批挡住汇报」的错觉 |
| 是否接受验收说明层的工作量（C3） | v1 就做 `DecisionBrief` | 先做 G1 / G3，说明层放 v1.1 | **A**；说明层是差异点，晚做会让 v1 继续像 diff 审阅器 |
| 是否做「一键合并」（C6） | v1 做交付说明 + 一键合并（需确认） | 保持只给分支，用户自己合 | **A**；但自动合并只对低风险类型开放，且必须二次确认 |
