# 自进化能力调研

> 2026-11-13，v0.48.1
> 问题：**我们的产品距离"半自动自进化"还差多少？**

---

## 零、先把定义钉死

这是**我们自己的定义**，不是行业通用术语。记在这里作为判据。

### 半自动自进化

> 手动使用我们的产品，更新迭代它本身。
> 但**我们只管提需求，不管技术细节**。
> 我们只参与**重大决策与方向决定**。

拆成三个可检验的条件：

| 条件 | 含义 |
| --- | --- |
| S1 | 人只提需求（自然语言），不写代码、不做技术选型 |
| S2 | 产品自己完成：调研 → 设计 → 实现 → 测试 → 交付 |
| S3 | 人只在**重大决策**介入（方向、取舍、风险确认） |

### 全自动自进化

> 部署到长期在线终端，软件自动调用自己内部的 AI，循环：
> 调研（业务+技术）→ 方案/文档设计 → 开发实现 → 测试验证 → 上线交付 → 反馈复盘 →（下一轮）

额外要求：

| 条件 | 含义 |
| --- | --- |
| F1 | 长期在线运行，无需人启动每一轮 |
| F2 | 自己决定"下一轮做什么"（调研产出需求） |
| F3 | 完整闭环，包括**上线交付**和**反馈复盘** |
| F4 | 自己调用自己内部的 AI（不是在外部 IDE 里跑） |

---

## 一、结论

**距半自动自进化：还差 2 个关键能力。**

**距全自动自进化：还差得很远**，不只是能力问题，还有安全与信任问题。

| | 当前 | 半自动 | 全自动 |
| --- | --- | --- | --- |
| 完成度 | 约 60% | 目标 | 差距大 |

**最诚实的一句话**：我们现在能"自己改自己的代码"，但**改得对不对、该不该改**这两件事还得人判断。

---

## 二、逐条件核对

### S1：人只提需求 —— ✅ 基本成立

我们已经能：用户说一句话，四层编排把它拆成任务、派给 Agent 执行。

**已验证**：这一轮开发过程中，我自己就在用这套流程改这个项目
（虽然是通过 DSH 界面，但底层机制是同一套）。

**差的部分**：需求从哪来。现在是"用户想到了什么就说什么"，
全自动要求"软件自己调研出该做什么"（F2）。这一条半自动不需要。

### S2：产品自己完成全流程 —— ⚠️ 差最关键的一环

| 环节 | 我们的能力 | 状态 |
| --- | --- | --- |
| 调研（技术） | MCP 接入、web_fetch 类能力 | ⚠️ 需要确认 |
| 调研（业务） | 无用户数据、无反馈渠道 | ❌ 做不到 |
| 方案/文档设计 | 能写文档 | ✅ |
| 开发实现 | 四层编排 + 12 个工具 | ✅ |
| **测试验证** | 能跑 `pnpm test`，能看结果 | ⚠️ **能跑不能判断** |
| 上线交付 | 能构建、能 git push | ⚠️ **需要人确认** |

**最关键的是"测试验证"这一格。**

Agent 能跑测试、能读到"843 passed"，
但它**判断不了一个测试挂掉意味着什么**——是代码错了，还是测试本身过时了。

这一轮开发中，我自己遇到过好几次：测试失败了，我得看具体断言才知道
"是测试的预期过时了"还是"实现真的写错了"。这个判断目前没有被产品化。

### S3：人只参与重大决策 —— ⚠️ 部分成立

我们有：

- **权限四档**（仅可查看 / 手动审批 / 自动审批 / 完全权限）
- **危险动作审批**（删除、推送、发布、付款、外发）
- **验收复核**（D 说完成，系统真的跑命令验证）

**但"重大决策"的边界没有定义。**

现在审批是**动作级**的（"要不要删这个文件"），不是**决策级**的
（"用方案 User 还是方案 B"）。半自动自进化要求的是后者。

---

## 三、全自动的四个条件，逐条看

### F1：长期在线 —— ❌ 完全不具备

| 问题 | 现状 |
| --- | --- |
| 进程管理 | 桌面应用，用户关掉就没了 |
| 断点续跑 | 有会话恢复，但没有"每 X 小时醒一次"的调度 |
| 崩溃恢复 | 有，但需要人重新打开 |

我们有**定时任务**（`checkSchedules`），但设计是"提醒你，不自动派活"。
这是当时有意的选择——现在要重新评估。

### F2：自己决定下一轮做什么 —— ❌ 完全不具备

这是**业务调研**能力。需要：

- 从哪获取"该做什么"的信号（用户反馈、issue、使用数据、竞品变化）
- 怎么判断"这个值得做"
- 怎么排序

我们**没有任何用户数据收集**。连"用户点了哪些按钮"都没记录。

### F3：完整闭环含上线交付 —— ⚠️ 能构不能发

| 环节 | 状态 |
| --- | --- |
| 构建 | ✅ `pnpm app:build` 能跑 |
| 签名 | ✅ 自动 |
| 上传发布 | ⚠️ 有脚本，但没人会自动决定"这一版能发了" |
| 反馈复盘 | ❌ 没有反馈渠道，无从复盘 |

### F4：调用自己内部的 AI —— ✅ 具备

产品本身就是 Agent 运行时。理论上它可以接待自己。

**但有个根本问题**：它改的是**正在运行的自己**。
改到一半崩了，谁来恢复？这是个没解决的问题。

## 四、按"距半自动"排序的差距

### 差的第一件：测试失败的判断能力

**现状**：Agent 能跑测试、能读到结果，但判断不了失败意味着什么。

**实测发现一个更具体、更严重的问题**：

    全量测试输出      34685 字符 / 1312 行
    run_command 上限    4000 字符

**只保留前 11%，而测试失败的信息在末尾——被完全截掉了。**

实测对比（模拟 400 条通过 + 末尾 1 条失败）：

| 检查项 | 修复前 | 修复后 |
| --- | --- | --- |
| 断言详情能读到 | ✗ | ✓ |
| 失败计数能读到 | ✗ | ✓ |

Agent 看到的是一堆通过的测试，**失败那条它根本没见过**。
这不是"判断能力弱"，是它没有可判断的输入。

**已修（v0.49.1）**：截断改成保留头 30% + 尾 70%，
并在截断处告诉 Agent "要完整输出就重定向到文件再用 read_file"。

**还要做的事**：
- 让 Agent 读具体的断言失败信息，而不是只读 "1 failed"
- 建立"这个测试守的是什么"的知识（我们已经在测试里写了症状注释）
- 区分三类失败：实现错了 / 测试过时了 / 环境问题

**工作量**：输出截断已修（小）。剩下的判断逻辑是中。

### 差的第二件：决策级的介入点

**现状（修前）**：审批是动作级（"要不要删这个文件"），不是决策级（"选方案 User 还是 B"）。

**更具体的问题**：`needsUser` 字段存了、能过滤、全局概览会统计，
但**对话流里没有任何视觉区分**。Assistant 说"需要你决定"时，
它和一条普通进度汇报长得一模一样。

用户得自己从几十条消息里认出"哦，这条是在问我"——
而那恰恰是**唯一需要他动脑的地方**，却埋得最深。

**已修（v0.50.1）**：

- 对话上方新增"待决策"面板，固定显示、不随滚动消失
- 每条一行摘要，点开看全文
- "我来回答"把正文带进输入框；"不需要决定"标记已处理
- **没有"全部已读"**——这些是决策，不是通知

配套加了 `POST /api/reports/:id/ack`，只改 `acked_at`，**不删记录**：
用户可能要回头查"当时我是怎么决定的"。

**还没解决的遗留问题**（实测中发现的）：

真实数据里 5 条待决策有 3 条其实**不是决策**——
"Agent 未完成"、"结论：这个项目是……" 这类也被标了 `needsUser`。

这是**过度打扰**，和面板的目的相反。面板再好，如果里面混着噪音，
用户很快就会学会忽略它。~~下一步要给 `needsUser` 加判据。~~

**已于 v0.50.2 修**：判据统一到 `recordReport` 一处，
只有「卡点标记 / 用量中止 / 明确请求用户做事 / blocked / 显式要」才算。
真实数据验证：6 条待决策 → 1 条真卡点，噪音全部过滤。

### 差的第三件：交付环节的人工确认

**现状**：能构建能推，但"这一版能不能发"要人判断。

**为什么是第三件**：人确认发布本身是合理的（这确实是重大决策），
但**验收标准应该系统化**，而不是"我看差不多可以了"。

**已修（v0.50.3）**：`scripts/release-ready.mjs`，五条判据：

| 判据 | 对应的事故 |
| --- | --- |
| 测试全过 | 基本要求 |
| 改动有测试 | 快照功能 9 个测试全过，但传参漏了——测试没覆盖真实调用路径 |
| 工作区干净 | 改一半发了，用户拿到的和仓库不一致 |
| 版本号已更新 | 忘了 bump，推送被拒 |
| 没有新增 TODO | 半成品不该发 |

已接进 `publish-release.mjs`：**判据不满足，发布直接中止。**

**实测输出**：

    可以发布
    ✓ 测试全过         929 个测试全过
    ✓ 改动有测试       改了 1 个源文件，同时改了 1 个测试
    ✓ 工作区干净       没有未提交的改动
    ✓ 版本号已更新     0.50.2 → 0.50.3
    ✓ 没有新增半成品   没有新增 TODO/FIXME

**一个自己踩的坑**：第一版调用 pnpm 失败，输出里没有测试汇总行，
结果显示"✓ 0 个测试全过"——**比不检查更糟**。

已修：测试数为 0 直接判失败，并写明"测试命令可能失败了，不能当通过"。

## 五、一个更根本的观察

**我们现在最缺的不是能力，是"判断"的可产品化。**

这三个差距的共同点：

| 差距 | 缺的 |
| --- | --- |
| 测试失败的判断 | 判断"这次失败意味着什么" |
| 决策级的介入 | 判断"这算不算重大" |
| 交付确认 | 判断"可以发了吗" |

**都是判断，不是执行。** 执行能力我们已经很够了。

这也解释了为什么这一轮开发中有 6 个 bug 是"测试全绿但功能不工作"——
**执行从来不缺，判断才是瓶颈**。

## 六、一个诚实的警告

即使把上面三件都补上，"半自动自进化"也有个前提没解决：

> **产品自己改自己，改错了谁发现？**

这一轮开发里，我自己犯过一个错：改排序时正则误匹配了 `listProjects`，
把项目列表也改成了倒序。**测试没抓到，是我打印上下文才发现的。**

如果这个改动人不管技术细节，那个 bug 会一直留着。

### 已修（v0.51.0）：自检扫描

`apps/runtime/src/selfcheck/scan.ts` + `scripts/self-check.mjs`，
扫出"测试全绿但功能不工作"这一类风险。

**针对的是这一轮真实踩过的 6 个 bug**，它们共同的原因是
"测试都在测函数本身，没测真实链路"：

| bug | 为什么不报错 |
| --- | --- |
| 快照传参漏了 `runExecutor` 那一环 | 可选字段，类型检查不回推 |
| `edit_file` 没进台账 | 没测过"台账里有没有记录" |
| 管道吞掉退出码 | 没测过"命令带管道时的失败" |
| `git status` 被判成写操作 | 没测过"只读任务里跑 git" |
| `needsUser: !ok` 制造噪音 | 测了字段，没测"什么该标" |
| 侧栏批次位置错乱 | 测了函数，没测"倒序输入时" |

目前三类检查：

- **静默吞错**：空 catch 且没有注释（快照那次就是被吞了，查了六七轮）
- **可选字段传递**：同一字段在同一文件被传多次时提示确认有没有漏的构造点
- **建议改成必填**：不确定就该让类型检查兜住

真实扫描结果（108 个源文件）：

    自检发现 5 处值得确认的地方
    └─ 全部是可选字段传递，其中一项正是 snapshots 那几个构造点

**没有静默吞错**——说明代码里的 catch 都写了说明。

**这个能力仍很弱**：它只能扫静态模式，发现不了"逻辑写错了但类型对"。
真正的自检还远，但至少先把"这一轮踩过的坑"变成了可自动检查的东西。

## 七、路线建议

| 阶段 | 内容 | 目标 |
| --- | --- | --- |
| 1 | 测试失败的判断能力 | 让"自己验证"真的成立 |
| 2 | 决策级介入点 | 让人只参与重大决策 |
| 3 | 交付验收的标准化 | 让"能发了吗"有客观判据 |
| 4 | 自检能力（发现自己的错误） | 补上根本前提 |

前 3 步达成 = **半自动自进化**。
第 4 步与 F1/F2（长期在线、业务调研）一起 = 全自动的前置。

---

## 八、目前状态的诚实总结

**60% 这个数字可能还偏乐观。**

我们有的：
- 完整的执行链（需求 → 拆分 → 执行 → 验证 → 报告）
- 可观测性（轨迹、台账、撤销）
- 安全边界（审批、沙箱、权限档位）

我们缺的：
- **判断能力**（测试失败意味着什么、什么算重大决策）
- **自己发现问题**（业务调研、自检）
- **长期运行**（离线调度、自我恢复）

一句话：

> **我们能干活，但还不会判断活干得对不对。**
