# 架构：能力边界与「万物皆插件」的路线

## 结论先说

| 问题 | 结论 |
| --- | --- |
| 要不要做成插件架构？ | **要，但不是现在** |
| 现在做什么？ | **切边界**（能力接口化），成本极低 |
| 要不要用 DeepSeek Harness 的代码？ | **不用**。只参考设计思路 |
| 会不会变成 DSH 的插件？ | **不会，也不可能**：运行时零第三方依赖，有测试守着 |

---

## 一、为什么现在只切边界，不上插件框架

DSH 的「万物皆插件」建立在 **Cordis** 框架上（依赖注入、服务隔离、生命周期、Loader YAML 方言）。

它这么做是**有正当理由的**：DSH 要支撑官方插件市场、第三方 UI 插件、多人跨团队贡献。
所以要付出这些复杂度代价。

**我们的情况完全不同**：

- 所有能力都是自己写的；
- 只有一个人维护；
- 还没有第三方要接进来。

现在上插件框架，等于**为一个还不存在的问题付复杂度代价**。更糟的是，
刚做完的 A 线（用量止损、危险动作审批、验收复核、副作用台账）都依赖现有调用链，
换框架会动摇它们。

### 正确的顺序

```
现在：切边界          → 每个能力有明确接口，核心只认接口
将来：实现变插件       → 只需写新适配器，业务代码不动
```

**反过来（先上框架再补边界）返工量很大**，因为框架会逼你按它的形状设计接口，
而你还不知道真实用例长什么样。

## 二、边界具体切在哪

`apps/runtime/src/capabilities/index.ts` 定义了五类能力的**纯类型契约**：

| 能力 | 契约 | 当前实现 | 将来可能是 |
| --- | --- | --- | --- |
| `ExecutorCapability` | 给目标、写域，跑一个 Agent | `executor/executor.ts` | 换执行后端、外部 Agent |
| `MemoryCapability` | 读写删记忆 | `memory/store.ts` | 换向量库、云端同步 |
| `NotificationCapability` | 汇报、审批推送 | IM 桥接 + 事件 | 加飞书、邮件、桌面通知 |
| `ModelCapability` | 模型是否可用 | `llm/settings.ts` | 多模型路由 |
| `GuardCapability` | 执行前检查 | `security/classify.ts` | 细粒度策略 |

### 一条硬规矩

> **`capabilities/` 里不许 import 任何具体实现，只有类型。**

一旦这里 import 了 `runExecutor`，核心就再也换不成别的实现了。
这条规矩由 `test/boundary.test.ts` 强制，不是靠自觉。

---

## 三、四道防线（都有测试）

`boundary.test.ts` 守四件事：

1. **能力接口层只允许 import 类型**，不许碰实现；
2. **运行时零第三方依赖**（验证过：`dependencies` 必须为空数组）；
3. **不依赖 DSH 的任何包**（扫全部源码的 import 说明符）；
4. **接口层不许有值导入**（保证是纯类型层）。

> 我特意做了反向验证：故意在 `capabilities/index.ts` 里加一行
> `import { runExecutor } from '../executor/executor.js'`，
> **两条测试立刻失败**。它不是摆设。

## 四、关于参考 DSH

### 允许

- 参考**架构分层与命名**（哪些概念该拆开）；
- 参考**界面信息密度与布局**（状态怎么呈现）；
- 阅读源码**理解设计**，然后用自己的实现。

### 不允许（自己定的，比 MIT 更严）

- **不复制源代码**。MIT 允许复制，但 DSH 的插件代码深度依赖 Cordis，
  搬过来等于把 Cordis 搬进来 —— 正好违背"不变成它的插件"这个目标。
- **不依赖它的运行时包**。由第 3 条测试守着。

### 许可事实

DSH 确为 MIT 许可（[仓库 LICENSE](https://github.com/deepseek-ai/deepseek-harness/blob/9873240390c4fb2d04ccd553a1620b01f0dce357/LICENSE)）。
MIT 允许商用与闭源分发，唯一义务是保留版权声明。
**我们选了比法律要求更保守的做法**：只学思路，不搬代码。

## 五、什么条件下才真的上插件框架

满足**任一**即可开做：

- [ ] 有第三方想贡献能力（哪怕一个）
- [ ] 自己要在不改主仓库的情况下加能力
- [ ] 同一能力需要**多种实现并存**（例如两套执行后端切换）
- [ ] 需要运行时热插拔

**在那之前，加能力就是加一个文件 + 在装配处接一根线**，
这比插件框架简单得多，也更不容易设计错。
