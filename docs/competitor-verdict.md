# 竞品再判定：他们到底是不是我们？

> 日期：2026-11-11（第二轮调研，修正 `market-scan.md` 的结论）
> 触发：用户质疑"这些产品是真正意义上的竞品吗？还是普通 Agent 软件？功能上和我们完全一样吗？"
> 结论：**质疑问对了。上一轮把"能力有重叠"错当成了"竞品"，其中一半以上根本不是同一类产品。**

---

## 0. 先给答案

| 问题 | 答案 |
| --- | --- |
| 他们是真正意义上的竞品吗？ | **只有 1 个是**（TRAE 宝）。其余是"相邻品类"或"我们可消费的上游" |
| 还是普通 Agent 软件？ | 大部分连"普通 Agent 软件"都不是——它们**根本不跑 Agent**，只是启动 Claude Code / Codex 的外壳或看板 |
| 功能上和我们完全一样吗？ | **没有任何一家完全一样。** 最大的差异见 §3 |

---

## 1. 关键区分：谁真的有自己的 Agent？

这是上一轮漏掉的最重要一维。**很多产品自己不实现 Agent 循环，只是调度别人家的 CLI。**

| 产品 | 自己有 Agent 循环吗 | 实际做法 |
| --- | --- | --- |
| **TRAE 宝** | ✅ 有 | 字节自家模型 + 自家 Agent 运行时，闭源 |
| **Multica** | ❌ **没有** | 本地 daemon 扫描 `PATH`，侦测你机器上的 `claude` / `codex` / `gemini` / `cursor-agent` 等 CLI，注册为 runtime，任务分派给它们执行 |
| **Vibe Kanban** | ❌ **没有** | 同上，是套在 10 种 coding agent CLI 外面的看板 UI |
| **Paperclip** | ❌ **没有** | 同上，`Bring Your Own Agent` 是它的核心卖点，"用你已有的登录和订阅" |
| **Cursor 3** | ✅ 有 | 自家闭源 Agent |
| **我们（`apps/runtime`）** | ✅ **有** | 自研 LLM tool-calling 循环，可对任意 OpenAI 兼容端点 |

Multica 源码分析原文可直接佐证（[Multica 指南](https://agentpedia.codes/zh/blog/multica-guide)）：

> "agent CLI 只是九个可插拔 provider 之一，daemon 是一个独立的 Go 进程……将 Multica 称为 'a Claude Code wrapper' 忽略了团队实际构建的成果。"

注意这段是**为 Multica 辩护**，但它恰好确认了：**Multica 的能力上限被第三方 CLI 锁死**。我们的 Agent 是自己的。

**这条差异是产品级的，不是实现细节**：我们改了提示词、加了验收闸门、加了写域互斥，这些都是运行时内部能力；Multica/Vibe Kanban/Paperclip 只能在外围加一层 shell——它们**管不了 agent 内部怎么想**。

## 2. 逐个判定

### 2.1 TRAE 宝 —— 唯一真正的竞品

**判定：真竞品，同品类同形态。**

证据（[官方文档](https://docs.trae.cn/ide_personal-assistant)）：

- 两个角色：全局助理 + 项目助理，与我们 B/C 同构；
- 交互入口一致：点项目栏进入"项目专属·TRAE 宝"，即 C；
- 项目助理职责原文："围绕一个具体的项目工作……拆解复杂需求，调度子任务并行推进，完成联调与汇总"；
- 有自己的 Agent 运行时（字节自家模型）。

**差异**：闭源、绑字节系模型、无本地白盒记忆、**审批只有一个"完全访问"总开关**（关掉全部沙箱与检查），没有分级审批。

### 2.2 Multica —— 不是同一品类

**判定：团队协作看板 + Agent 调度器。不是我们的品类。**

原文定位（Multica 创始人）：

> "把人和 agent 放进同一个团队空间"
> "我们创建了 ChatGPT 工作区智能体的开源版本"

实际形态：Linear 式看板（issue/project/评论/状态流转），agent 是绑定 runtime 的持久化 profile。**任务单位是 issue，不是"项目负责人"**。

关键：**它没有"一个项目一个 C 常驻"这层。** 它的"项目"在源码里甚至**还没绑定仓库 URL**——"当同一个工作区有多个仓库时，智能体可能会选错，回退到工作区的第一个仓库"（issue 反馈）。这类细节说明它的抽象还停在 issue 层。

另有中文批评文《An Indictment of Multica: Human Bureaucracy Wearing an AI Skin》，标题就点出它的争议：**用人类官僚流程套了 AI 的皮**。

**关系**：我们**可以**接入它（像 Vibe Kanban 那样调我们的 CLI），但它是我们的**渠道**，不是竞品。

### 2.3 Vibe Kanban —— 已停运，且本来就不是同类

**判定：公司已关闭。**

[官方公告](https://www.vibekanban.com/blog/shutdown)（2026-04-10）原文：

> "Today we're shutting down bloop, the company behind Vibe Kanban."
> "Thousands of software engineers use Vibe Kanban every day to ship more with coding agents, **but the vast majority are free users and we couldn't find a business model that we could get excited about.**"

**这条比 star 数重要得多**：2.56 万 star 的产品找不到商业模式。它说明**"帮开发者同时盯多个 agent"这个需求真实但付费意愿弱**。见 §5 的推论。

顺带：Paperclip 自己的文章提到 **Conductor Cloud 2026-11-20 关停，本地版 2027 年初退场**。这个赛道已经在挤泡沫。

### 2.4 Paperclip —— 品类相邻，但打法直接威胁上一轮结论

**判定：最接近我们的"上层"，但不是同类。**

它自称同时做两层（[原文](https://paperclip.ing/blog/coding-orchestrator-vs-control-plane/)）：

- **orchestrator**：并跑 Claude Code / Codex / Cursor / Gemini CLI / OpenCode；
- **control plane**："每个任务一个 owner、Review 阶段、预算、org chart"。

**必须承认**：这正是我上一轮说的"可核查可信度"缝隙。Paperclip 已经在卖这个卖点，而且文献准备得比我们充分（有 governance checklist、budget、approval、audit trail 的完整叙事）。

但它的差异也明确：

- **不拥有 Agent**，靠你自己的 Claude/Codex 登录跑；
- 形态是**公司模拟**：org chart、招聘、"hire AI agents like employees"、甚至给 agent 开银行账户；
- 服务对象是**团队**（多玩家、per-user secrets），不是单个开发者。

**关键洞察**：Paperclip 的"control plane"讲的是**组织治理**（谁批准、花多少钱、谁负责），我们讲的是**执行可信度**（这一行代码是不是真改对了）。**这两件事不一样**——见 §3。

### 2.5 Cursor 3 / Claude Code / Windsurf —— 上游执行器

**判定：是我们的 D 的潜在实现，不是竞品。**

Cursor 3 的 Agents Window 是"一个人在多个仓库上并跑 agent"；`/best-of-n` 是同一任务多模型并行。它是 IDE，不是"项目负责人"层。真比起来，**它们更像可以塞进我们 D 位的东西**。

### 2.6 OpenAI Symphony / Anthropic Claude Managed Agents / ChatGPT workspace agents

**判定：框架与托管运行时，不是产品竞品。**

它们提供多 agent 编排的**能力**，会被上面这些产品消费。对我们的意义：**验证了四层结构是行业共识方向**，不构成直接竞争。

## 3. 真正的差异：我们和他们的本质不同在哪

把上面的判定收敛，差异只有三条，但每条都很硬：

### 差异一：我们拥有 Agent 内部（别人只是外壳）

| | 别人 | 我们 |
| --- | --- | --- |
| Agent 循环 | 调第三方 CLI | 自研 |
| 能约束 agent 内部行为吗 | 只能在外围拦截 | 可以在循环内做：独立复核、写域互斥、危险动作前置拦截、副作用台账 |
| 换模型 | 受 CLI 支持列表限制 | 任意 OpenAI 兼容端点 |

**这条决定了"验收"能不能做真。** 一个只管启动 CLI 的外壳，agent 说"我做完了"它只能信；我们能在 agent 结束前自己重跑命令、比对 diff。

### 差异二：单位不同 —— "任务有主人" vs "项目有负责人"

| 产品 | 抽象单位 | 谁负责"这个项目整体推进" |
| --- | --- | --- |
| Multica | issue | 没有人，人自己看板 |
| Vibe Kanban | workspace | 人 |
| Paperclip | task + owner | 有 owner，但是**单据级**，跨任务协调靠 org chart |
| TRAE 宝 | 任务 | 项目助理 |
| **我们** | **项目（C 常驻）** | **C 负责到底，包括主动推进卡点** |

"谁在事情卡住时主动想办法"这个职责，在 Paperclip 那里是 org chart 里的上级 agent；在 Multica/Vibe Kanban 那里是**人**；在我们这里**是 C**。

### 差异三：Paperclip 的 control plane ≠ 我们的可信度

这一条必须写清楚，否则会误判自己很安全。

| | Paperclip control plane | 我们的执行可信度 |
| --- | --- | --- |
| 解决什么 | **治理**：谁能批、花多少、谁负责 | **正确性**：改动是否真的达成目标 |
| 机制 | owner / review 阶段 / 预算 / audit trail | 系统独立重跑命令 / diff 复核 / 失败不许人工覆盖 |
| 谁来判定 | **人** review | **系统**先判，人只决定系统判不了的 |
| 前提 | 信 agent 的自述，人把关 | **不信** agent 自述 |

**关键区别**：Paperclip 的 Review 阶段是"agent 提交 → 人看"。我们的验收是"agent 说完了 → 系统自己复算一遍 → 失败直接判 failed，人不许覆盖"。

一个是**让把关更容易**，一个是**把关不依赖人**。后者才真正省注意力。

## 4. 修正上一轮的结论

| 上一轮说 | 修正 |
| --- | --- |
| "方向不是蓝海" | **仍然成立**，但理由要换：不是"很多同类产品"，而是"**TRAE 宝已经把这套形态产品化**"。其余多数家根本不在这个品类 |
| "存在可核查可信度的窄缝隙" | **部分不成立**。Paperclip 已经在做治理层叙事，把"可信度"当卖点。真正的缝隙要收窄成：**"系统独立复核、不采信 agent 自述"**——这一格 Paperclip 明确不给（它要人 review） |
| "开源阵营体量惊人" | **要加注**。Vibe Kanban 已关停，Conductor 在关停。**star 数不等于市场验证** |

**新的判定**：

> 我们不在一个空白市场里，但我们的位置比"又一个多 agent 编排器"更窄也更稳：
> **别人做"让 agent 干活"，我们做"让 agent 干的活可被独立核验"。**
> 这个位置上，TRAE 宝有产品形态但没有（公开的）验证机制；Paperclip 有治理但没有系统复核；Multica/Vibe Kanban 连 Agent 都不是自己的。

## 5. 从关停事件里得到的教训

Vibe Kanban 关停的理由不是技术不行，是**"绝大多数是免费用户，找不到商业模式"**。

> **前提变更（2026-11-11）**：本项目**不以盈利为目标**——目标是自己用一个好产品，并尽可能推进开源社区与 agent 产品的发展。
> 因此本节原有的"往团队/企业治理走才有预算"建议**已撤回**。下面是适用于"不赚钱"前提的读法。

### 5.1 这个关停事件对我们的真实含义

它**不**说明这个需求是假的，也不说明项目不该做。它只说明三件事：

1. **"有大量免费用户"≠"产品没价值"**——Vibe Kanban 被数千工程师每天使用，是真实需求。
2. **VC 资助的公司必须有商业模式，我们不需要。** 它死于缺少收入来源，不是缺少用户。
3. **但"项目能否长期活下去"仍然是个问题**，只是约束条件换了：不再是"有没有人付钱"，而是**"有没有人愿意维护它"**。

### 5.2 「不赚钱」改变什么，不改变什么

| | 有商业化目标 | 无商业化目标（本项目） |
| --- | --- | --- |
| 谁来用 | 付得起钱的团队 | 自己和愿意用的人 |
| 成功标准 | 收入、留存、增长 | **自己用得上** + 别人愿意一起用 |
| 该往哪走 | 企业治理、多租户、审计合规 | 单人体验、可改可扩展、社区协作 |
| 最大的失败模式 | 找不到付费者 | **项目无人维护而烂尾** / 没人知道它存在 |

**关键**：上一轮建议"往团队/企业治理走"，在无商业化前提下是**纯粹的成本**——多玩家、权限、per-user secrets、预算审批都不该做。那会让单人产品变重，而没有任何回报。

### 5.3 那"推进开源社区"到底靠什么

不是靠 star 数，也不是靠功能多。三个具体支点，按可行性排序：

1. **能被人真的跑起来。** 目前项目**没有一个外部用户能照着跑通的路径**——这是社区的第一道门槛，比任何功能都重要。见 `docs/open-source-plan.md` 的 O1。
2. **能被人改。** 架构清晰、测试可跑、文档说得清真东西在哪。**137+ 条测试是极大的资产**，但要让人相信这些测试能跑，得先有"一条命令跑起来"。
3. **能被大厂产品无法覆盖的那部分人用上。** 我们的差异（本地、白盒、可核验、模型自选）恰好是闭源产品给不了的。**这是开源项目最自然的立足点，而且和赚钱无关。**

> 一句话：**不赚钱的项目不需要"商业模式"，但需要"可参与性"。** 一个别人跑不起来、改不动、也看不懂的仓库，star 再多也不会有人留下。

## 6. 未核实项

- **TRAE 宝是否有独立复核机制**：官方文档只字未提验收/复核，只提"完成联调与汇总"。**未提及不等于没有**，需实测。
- **Multica 的安全性批评文**（`issues/6875`）未能抓取原文，仅从标题与检索片段判断，未采信其具体指控。
- Paperclip 的 control plane 是否真的**不做**系统级自动复核（可能藏在某个 skill 里），未逐页核实。

---

## 7. 一句话总结

> **他们是竞争者吗？** 一个（TRAE 宝）是，其余是邻居和上游。
> **功能完全一样吗？** 没有一家一样。最大的不同是：**他们调度 agent，我们自己就是 agent**——而且我们不采信 agent 的自述。
