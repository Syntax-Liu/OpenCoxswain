## 六、附件功能的设计（已确认前置条件）

### 现状核查结果

我逐项查了代码，发现两个必须先解决的问题：

| 事实 | 位置 | 含义 |
| --- | --- | --- |
| `content` 是**纯字符串** | `llm/types.ts` | 协议层根本没有图片通道 |
| `supportsImages` **没有任何代码使用** | 只有 `models.ts` 声明 | 配置了也不生效 |

所以附件不是"加个拖拽上传"的小活，要**先打通协议层**。

### 设计：按模型能力自适应

你的判断是对的——**不能假定所有模型都支持多模态**。所以：

```
附件进输入框
   ↓
看当前角色绑定的模型：supportsImages 为 true？
   ├─ 是 → 图片走多模态内容块
   └─ 否 → 图片降级为"文件名 + 尺寸"，并明确提示"当前模型不支持看图"
```

**关键取舍**：不支持图片时**允许附件存在但不发送图片数据**，
而不是直接拒绝用户拖入。理由：
- 直接拒绝让人不知道"为什么不能发图"
- 允许但提示"当前模型看不了图，只传了文件名"——用户立刻明白该换模型

### 三层实现

| 层 | 改什么 |
| --- | --- |
| **协议** | `ChatMessage.content` 支持 `string \| ContentPart[]`（文本 + 图片） |
| **模型配置** | `supportsImages` 真正生效——请求前据此决定发文本还是图文 |
| **界面** | 拖入 / 粘贴 / 选择文件，缩略图预览，可删 |

### 不做的

- ❌ **不做图片压缩/裁剪**（先原样传，有问题再说）
- ❌ **不做附件持久化到数据库**（只在当次会话有效，避免存储膨胀）
- ❌ **不做 PDF 的复杂排版还原**（只提取文字）

### 文件类型处理

| 类型 | 处理 |
| --- | --- |
| 图片（png/jpg/webp） | 支持多模态就转 base64；不支持就只传文件名 |
| 文本/代码/json | 读内容注入上下文（单文件上限 100KB） |
| PDF | 提取文字（不引依赖的话只做最简解析，或让用户自己转文本） |
| 其它二进制 | 只传文件名和大小，提示"无法读取内容" |

### 验收标准

- [ ] 拖一个 png 进输入框 → 出现缩略图
- [ ] 截图后 Ctrl+V → 直接进附件
- [ ] 当前模型不支持图片 → 明确提示，不静默丢图
- [ ] 拖一个 .ts 文件 → 内容进入上下文
- [ ] 附件可以单独删除
- [ ] 发送后，Agent 真的能看到文件内容（不是只有文件名）

## 七、一件需要你决定的事

**（已确认）**：你用的 DeepSeek-Flash 支持图片，但因为允许自定义模型，
所以按「模型能力自适应」设计——不支持图片的模型降级处理并明确提示。

**发附件涉及一个前置问题**：多模态能力。

我们现在的模型配置里有 `supportsImages` 字段，但**没有任何代码真的
把图片传给模型**。要做附件，必须先确认：

1. 你用的模型（DeepSeek 系）**是否支持图片输入**？
2. 如果不支持，附件只能做"读文本内容"（PDF 提取文字、代码文件注入）——
   **不能贴图**。

如果目标模型不支持图片，那"发了图片后被拒绝"的体验比"一开始就不能发"更糟。
这个要先确认清楚，再动手。
