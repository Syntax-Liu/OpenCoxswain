# 模板检验（unslop 收尾）

> 技能要求：**如果把这个产品的名字换成别的产品，界面还成立吗？**
> 成立就说明你的方向不够用力，要在文案、视觉和签名细节上再推一把。

方法：把界面上每一处可见文案换成「一个通用 AI 编码工具」的说法，
看哪一条换得动、哪一条换不动。

---

## 换得动的（说明还不够专属）

| 现在的文案 | 换成通用工具也成立？ |
| --- | --- |
| 新会话 | ✅ 换得动，任何聊天工具都有 |
| 工作区 | ✅ 换得动 |
| 开始 / 待决策 / 改动 / 文件 | ⚠️ 「待决策」勉强专属，「开始/改动/文件」很通用 |
| 工作区文件 · 浏览会话工作区的文件 | ✅ 换得动 |
| 打开项目目录 · 在资源管理器里查看这个项目 | ✅ 换得动，几乎每个 IDE 都有 |
| 更多工具 · 设置、模型、权限 | ✅ 换得动 |
| 介绍一下这个项目 | ✅ 换得动 |
| 找出可以改进的地方 | ✅ 换得动，任何代码助手都会给这条建议 |
| 读项目文件和 README | ✅ 换得动 |

## 换不动的（真的属于这个产品）

| 文案 | 为什么换不动 |
| --- | --- |
| **Supervisor** | 四层结构里的顶层角色，别的产品没有这个位置 |
| **Agent 模式** | 和 Supervisor 并置，说明"当前是哪种模式" |
| **说明要推进的事** | "推进"是这个产品的动词——它接过一条模糊的诉求往下推 |
| **对 Assistant 说一句要推进的事，它派 Agent 去做** | 一句话说清了四层结构：你 → Assistant → Agent |
| **派一个 Agent 通读 src** | "派"是调度语义，不是"运行" |
| **两个 Agent 并行，谁先完成先报谁** | **最专属的一条**——流式汇报是这个产品的核心机制 |
| **同时做两件独立的活** | 同上 |

---

## 结论

### 换得动的占了多数

9 条里有 7 条换成任何 AI 编码工具都成立。
主要原因是：**入口区（侧栏、右栏）的文案几乎都是通用导航词**。

### 但核心机制的表达是专属的

「谁先完成先报谁」「派一个 Agent」这几条换不动，
说明产品的**灵魂在对话区，不在导航区**。

而且 `BatchBlock`（批次线）的设计注释早就写着「本产品的签名元素」——
它恰好就是这层机制的视觉表达。

### 我判断不需要再造一个新的签名细节

技能说要"推得更用力"，但硬加一个视觉装饰是**为了不同而不同**，
那是另一种毛病。现在的情况是：

- 产品的独特性已经有一个真实的落点（批次线 + 「先完成先报」的文案）
- 缺口在**入口区的文案太通用**

### 可选的改进（不动结构，只动措辞）

如果继续推，合理的下一步是**把入口区的通用词换成这个产品的说法**：

| 现在 | 可以改成 | 理由 |
| --- | --- | --- |
| 工作区文件 · 浏览会话工作区的文件 | 这次改动的文件 · 看 Assistant 动了哪些 | 工作区文件是通用词，"改了什么"才是用户关心的 |
| 打开项目目录 · 在资源管理器里查看这个项目 | 在资源管理器打开 · 直接看代码 | 说明更直接 |

**但这属于内容改动，不是视觉打磨**，需要用户确认再做——
skill 明确禁止擅自改内容和功能。
