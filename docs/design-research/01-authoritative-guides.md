## 一、自主性四级分类法

**这是做 Agent 界面最重要的一个框架。** 改编自 SAE J3016 自动驾驶分级。

### 1.1 四级

| 级别 | 名称 | Agent 做什么 | 人做什么 | 风险 |
| --- | --- | --- | --- | --- |
| **L1** | Observe & Suggest<br>观察与建议 | 监控环境、识别信号、发通知。**不能行动** | 所有决策与行动 | 低 |
| **L2** | Plan & Propose<br>计划与提议 | 制定多步策略，呈现给人，**等人批准再执行** | 审方案、改步骤、批准/拒绝 | 低-中 |
| **L3** | Act with Confirmation<br>带确认执行 | 准备好一切、暂存最终动作，**等一次 go/no-go** | 审暂存动作及其后果，确认或取消 | 中 |
| **L4** | Act Autonomously<br>自主执行 | 在预设边界内自主执行，不等逐步批准 | 设边界、审历史、处理异常 | 高 |

### 1.2 每级的设计含义

**L1 观察建议**
- 清晰、不打扰的通知
- 带严重度（信息 / 警告 / 严重）
- 容易关闭和稍后提醒——**价值是"知道"，不是"打扰"**

**L2 计划提议**
- 清晰展示每一步、理由、后果
- 能改单步、重排、增删
- 明确的整体批准/拒绝
- **主模式是 P1 意图预览**——计划摘要本身就是界面

**L3 带确认执行**
- 透明展示"将要发生什么"
- 能逐项检查细节（每封邮件、每次 API 调用）
- **清楚区分"将要发生"和"已经发生"**
- 注意：Agent 已经做了大量工作，**沉没成本会让人偏向确认**。
  设计上必须让"拒绝"和"编辑"和"批准"一样低摩擦

**L4 自主执行**
- 强活动日志：每个动作、每个理由、每个数据来源
- **随时可用的覆盖与急停**（kill switch）
- 用户定义的边界，Agent 不能越界而不升级
- 事后模式是核心：P5 审计撤销、P6 升级路径、P7 错误恢复

### 1.3 23 种 AI 任务的默认自主级别

来源：AI Interaction Atlas（Apache 2.0）

| 默认级别 | 任务 | 理由 |
| --- | --- | --- |
| **L1** | Detect 检测、Monitor 监控、Estimate 估算、Classify 分类 | 纯观察，低风险 |
| **L2** | Forecast 预测、Rank 排序、Match 匹配、Explain 解释、Plan 规划、Retrieve 检索、Segment 分群 | 分析建议，人决定 |
| **L3** | Generate 生成、Transform 转换、Translate 翻译、Synthesize 综合、Simulate 模拟、Verify 验证 | 产出物需审阅，发布后不可逆 |
| **L4** | Adapt 适应、Act 行动、Explore 探索、Cluster 聚类、Represent 表征、Regress 回归、Extract 提取 | 边界内操作 |

**重要**：这些是通用默认。**高风险领域会降级**：

| 任务 | 通用 | 高风险（医疗/法律） | 低风险 |
| --- | --- | --- | --- |
| Generate | L3 | L2（人必须审） | L4（已知模式的自动回复） |
| Classify | L1 | L3（影响创作者） | L4（垃圾邮件过滤） |
| Act | L4 | L2（机器人/物理安全） | L4（规则内改日程） |

### 1.4 对 OpenCoxswain 的直接映射

| 本项目现状 | 对应级别 | 说明 |
| --- | --- | --- |
| Supervisor 指路 | L1-L2 | 只建议，不派活 |
| Assistant 派 Agent | L3 | 派活前用户已表达意图，执行前不再逐步确认 |
| Agent 写文件 | L3-L4 | 有写域互斥，但危险动作需审批 |
| 危险动作审批 | **L3** | 删除/推送/发布前拦下 |
| 定时建议 | L1 | 到点只提醒，不自动开工 |

**结论**：本项目的自主性分布是合理的（L1~L3），但**用户看不到"我现在处于哪一级"**——
这是 [03](03-agent-ui-problems.md) 里 D3 要解决的问题。

## 二、17 条设计原则（摘要）

完整 17 条分四个主题。这里只摘**对 Agent 界面有直接影响的**。

### 主题一：人类能力、认知与意义

#### 原则 1：当委托变得毫不费力时，保留挣扎

> 当 AI 能在几秒内做完，人的理解和判断力会萎缩。

**设计含义**：不是"少用 AI"，而是**让关键环节的人参与无法被绕过**。
例如：审批不是摆设，而是真的要看一眼。

#### 原则 2：让元认知成为界面

> 用户应该知道*自己在想什么*，而不只是*AI 输出了什么*。界面要帮人建立对 AI 行为的心理模型。

#### 原则 3：把 AI 设计成透明的思考伙伴

> 不是黑箱，也不是全透明。是"该说的说清楚，细节可展开"。

### 主题二：超越屏幕与文本

#### 原则 6：为多种模态设计自适应界面

#### 原则 8：为"此刻"生成界面

> 界面不该是固定的，应该根据当前任务动态重排。

### 主题三：能动性与整合

#### 原则 10：**设计以传达局限**

> 对 AI 能做和不能做保持诚实。不假装全能。

#### 原则 11：**把同意设计成持续的，而非二元的**

> 一次性的 onboarding 同意在 AI 系统里是过时的——能力会变，场景会变。

设计指导（原文摘要）：
1. 同意是持续对话，不是一道闸门。首次做某事时问一句"我准备做 X，继续吗？"
2. **能力同意与数据同意分开**
3. 同意要收窄范围：不是"允许管理日程"，而是"允许建议会议时间"和"允许按规则自动接受"
4. **撤回应同样容易**——不需要去设置页
5. 渐进同意：从最小授权开始，按可靠性扩展

#### 原则 12：**逐刻协商能动性**

> 静态角色分配（工具/副驾/Agent）逼用户二选一：要么管一切，要么放手。

设计指导：
1. **按任务类型设自主级别**
2. 支持任务中途平滑过渡
3. 从行为中学习：用户反复覆盖某类建议 → 提议降低该类型自主性
4. **让当前自主级别常驻可见**（像文本编辑器的模式指示器）

### 主题四：责任、问责与权力

#### 原则 13：让问责可见

> "算法决定了"是现代的"这是规定"——用来结束对话的。

#### 原则 17：**把退出设计成神圣权利**

> 用户必须能随时、干净地离开。

## 三、9 个 UX 模式

按任务生命周期组织：

```
事前 ──→ 事中 ──→ 事后 ──→ 修复
 │        │        │        │
P1 意图预览  P3 可解释理由  P5 行动审计与撤销  P7 共情式错误恢复
P2 自主性旋钮 P4 置信度信号  P6 升级路径        P9 可编辑可分支输出
            P8 渐进披露
```

### 3.1 事前

#### P1 意图预览（计划摘要）

**做法**：行动前用一两句话说明"我准备做什么"。

```
我准备：
1. 在 src/auth/ 新建 login.tsx
2. 修改 App.tsx 的路由
3. 运行 pnpm test 验证

[继续] [改一下] [取消]
```

#### P2 自主性旋钮（渐进授权）

**做法**：按任务类型分级授权，而不是全局开关。

```
布局对齐      ● 自主   ○ 副驾   ○ 工具
配色建议      ○ 自主   ● 副驾   ○ 工具
字体选择      ○ 自主   ○ 副驾   ● 工具
```

### 3.2 事中

#### P3 可解释理由

**做法**：用"系统原语 → 用户语言"翻译。

```
系统内部：Logic: Cheapest_Direct_Flight
展示为：  我选这班，因为它是当天最便宜的非直达航班。
```

**关键**：把系统原语翻译成人话，而不是把原语直接摊给用户。

#### P4 置信度信号

#### P8 渐进披露（响应塑形）

**做法**：默认给摘要，细节折叠。

```
✓ 重构了登录页（改了 3 个文件）
  [展开详情]
```

不是：

```
正在执行 write_file...
write_file 完成
正在执行 read_file...
read_file 完成
...
```

### 3.3 事后

#### P5 行动审计与撤销

#### P6 升级路径

> 当 Agent 自己解决不了，必须有明确的"交给人"的通道。

### 3.4 修复

#### P7 共情式错误恢复

#### P9 可编辑可分支输出

**做法**：输出可以改、可以分叉，而不是只能重来。

## 四、反模式：Agentic Sludge（智能体淤积）

> 原文用词：Agentic Sludge。指 Agent 产出的大量低价值内容淹没用户。

**表现**：
- 每一步都播报，信息量爆炸
- 用大量文字描述本可以用一行状态说明的事
- 过度解释、重复确认

**对策**：
1. 当前步骤一行，其余折叠
2. 状态用**文字 + 颜色**而不是日志
3. 低频说明用 Tooltip 收纳

## 五、Google PAIR 与 Microsoft HAX（补充）

### 5.1 Google PAIR（People + AI Guidebook）

核心章节与 Agent 相关的内容：

| 章节 | 要点 |
| --- | --- |
| **User Needs + Defining Success** | 先确定 AI 解决什么人的什么问题 |
| **Mental Models** | 帮用户建立对 AI 能力的正确预期 |
| **Explainability + Trust** | 解释不是越多越好，是"够用就好" |
| **Feedback + Control** | 用户必须能纠正 AI |
| **Errors + Graceful Failure** | 失败时要优雅，说明发生了什么 |

### 5.2 Microsoft HAX（Human-AI eXperience）18 条

与本项目最相关的：

| # | 指南 |
| --- | --- |
| 1 | 明确系统能做什么 |
| 2 | 让系统随时间学到什么变得透明 |
| 3 | 当系统不确定时也要保持准确 |
| 4 | 在上下文中提供系统状态信息 |
| 5 | 支持高效的调用与解除 |
| 6 | 让用户容易纠正系统 |
| 9 | 处理可能出错的情况 |
| 11 | 解释系统做了什么 |
| 14 | 及时传达变化 |

## 六、AG-UI 协议（工程参考）

[AG-UI](https://docs.ag-ui.com/introduction) 是一个**开放事件标准**，用来把 Agent 后端和前端连接。

**它定义的典型事件**（对前端状态机设计有直接参考价值）：

```
RUN_STARTED        运行开始
TEXT_MESSAGE_START / CONTENT / END   流式文本
TOOL_CALL_START / ARGS / END         工具调用
STATE_SNAPSHOT / STATE_DELTA         状态快照与增量
RUN_FINISHED       运行结束
RUN_ERROR          运行出错
```

**对本项目的意义**：前端应该基于**事件类型**驱动状态显示，
而不是自己计时或猜测。这与 skill 里的铁律一致：

> "动作与状态严格真实对应……严禁用动画延迟或前端计时器伪造执行进度。"
