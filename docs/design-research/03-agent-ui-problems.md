## A. 状态呈现

### A1 · 全程一个转圈，用户以为卡死

**症状**

Agent 跑了 30 秒，界面上只有一个转圈。用户开始怀疑是不是挂了，刷新页面。

**根因**

把经典的"加载中 / 完成"两态模型套在 Agent 上。
Agent 运行有**至少七个**状态：

```
已接收 → 思考 → 工具调用 → 等待批准 → 流式输出 → 完成 / 失败 / 停止
```

**解法**

把每个状态设计成**有自己外观和文字**的独立状态：

| 状态 | 表现 |
| --- | --- |
| 已接收 | 0.1 秒内在对话里出现你的消息 |
| 思考 | 答案附近一个**平静**的指示器。不要假进度百分比 |
| 工具调用 | 用简单词汇命名这一步（"搜索文档"、"读取 3 个文件"），知道的话带上计数 |
| 等待批准 | Agent 需要许可时的**明显停顿** |
| 流式 | 显示正在到达的输出；**文字一开始就停掉思考指示器** |
| 完成 | 一句话总结改了什么，尽可能可撤销 |
| 停止/失败 | 说明发生了什么、保留了什么、怎么重试 |

**为什么有效**

> "我们看到的最常见的错误是整个运行过程中只使用了一个旋转器。
> 它隐藏了代理正在做实际工作的事实，因此人们认为它被卡住并刷新。
> **命名当前步骤几乎不需要任何成本，并且会改变等待的时间。**"

**怎么验证**

- 让一次运行持续 > 20 秒，观察界面是否有超过 10 秒的"无信息"时段
- 10 秒内必须出现"正在做什么"

**本项目现状**：有 6 个状态（`starting` / `running` / `done` / `failed` / `cancelled` / `handback`），
但**只有一行文字**，没有"当前步骤"和"第几步"。→ `UD-01`

### A2 · 假进度条

**症状**

进度条走到 80% 卡住不动，或者快速跳到底。

**根因**

系统**不知道**还要多久。任何百分比都是编的。

**解法**

- **不要显示百分比**
- 显示**已完成步数 + 当前步骤名**：

```
第 2 步 / 共 3 步 · 正在修改 App.tsx
```

- 如果步数也不确定，只显示当前在做什么：

```
正在修改 App.tsx…
```

**怎么验证**

grep 代码里有没有 `progress.*%` 或 `Math.random()` 参与进度计算。

**本项目现状**：没有进度条，✅ 天然规避。

---

### A3 · 思考过程暴露太多

**症状**

界面上刷出大段模型的内部推理（"让我想想……用户想要的是……"）。

**根因**

把模型的原始输出直接当界面呈现。

**解法**

- 默认只显示**一句话摘要**
- 摘要可以点开看详情
- 摘要要用用户视角，不是模型视角

| 模型原文 | 摘要 |
| --- | --- |
| "Let me analyze the codebase structure first, then..." | 分析代码结构 |
| "I need to check if the file exists..." | 检查文件是否存在 |

**怎么验证**

让一次运行产生大段推理，看界面是否默认展开。

**本项目现状**：轨迹页有完整记录，但**摘要层缺失**。→ `UD-02`

---

### A4 · 工具调用日志刷屏

**症状**

```
正在调用 read_file...
read_file 完成
正在调用 write_file...
write_file 完成
正在调用 run_command...
```

一条消息被几十行日志撑满。

**根因**

把**调试信息**当成了**用户界面**。

**解法**

- **当前步骤一行**
- 已完成的步骤**折叠成列表**
- 开发和高级用户可以展开看详情

原文：

> "长的工具调用日志对于调试很有用，但对于大多数用户来说却难以承受。
> 一个好的默认设置是**当前步骤的单行状态**，以及人们可以**展开的已完成步骤的折叠列表**。"

**怎么验证**

跑一个会调用 10+ 次工具的任务，数界面占了多少行。

**本项目现状**：轨迹页是独立视图（✅ 没有塞进对话），
但对话流里的阶段摘要粒度需要确认。→ `UD-02`

---

### A5 · 10 秒后用户开始怀疑

**症状**

用户在第 15 秒来看，界面和 5 秒时一模一样。

**根因**

违反了响应时间阈值。

NN/g 的三条线：

| 时间 | 用户感知 |
| --- | --- |
| 0.1 秒 | 瞬间 |
| 1 秒 | 思路不中断 |
| **10 秒** | **必须知道在做什么、大概还要多久** |

**解法**

任何可能超过 10 秒的操作，**必须在 10 秒内给出"正在做什么"的信息**。

**怎么验证**

- 计时器测：从点击到第一条"有意义的状态更新"隔了多久
- 目标：**< 1 秒**（不必等到 10 秒）

**本项目现状**：派 Agent 后立刻返回 ✅，但后续状态更新频率需要实测。→ `UD-01`

## B. 控制权

### B1 · 不可逆操作没有明确确认

**症状**

Agent 直接把文件删了 / 把代码推了 / 发出去了，用户才发现。

**根因**

把"用户已经授权 Agent 干活"等同于"用户已授权这个具体动作"。
授权的是范围，不是每一次不可逆操作。

**解法**

- 不可逆动作**执行前**拦下
- **准确说明将会发生什么**：

```
我准备删除以下 3 个文件：
  src/old-auth.ts
  src/old-auth.test.ts
  src/legacy/
这不可撤销。[确认删除] [取消]
```

**怎么验证**

制造一次删除操作，检查确认卡片是否**列出了将受影响的具体文件**，
而不只是"确定要删除吗"。

**本项目现状**：✅ 已有 `ApprovalPanel`，会拦下危险动作。

---

### B2 · 停止按钮消失

**症状**

运行时找不到怎么停。或者点"停止"后界面没反应。

**解法**

- 停止按钮**全程可见**
- 点击后必须**立即反馈**（"正在停止…"），而不是等 Agent 自己停

原文：

> "当代理人保持控制时，人们会更加信任他们。**在整个运行过程中保持停止按钮可见。**"

**怎么验证**

运行一个长任务，每秒检查一次停止按钮是否存在；
点击后测量从点击到界面出现"正在停止"的延迟，应 **< 200ms**。

**本项目现状**：✅ 有停止按钮（`Conversation.tsx` 的 `onStop`）。
需要确认的是：点击后是否立即反馈。

---

### B3 · 无法单步重试

**症状**

第 3 步失败了，只能从头再来一遍。

**解法**

- 逐步撤销 / 重试
- 不用重头开始

原文：

> "运行后，可以轻松地**撤销、编辑或重试单个步骤**，而不用重新开始。"

**本项目现状**：有 Agent 续聊（✅ 可带上下文追问），
但"从失败那一步重试"需要确认。→ `UD-03`

---

### B4 · 自主性一刀切

**症状**

要么全手动（什么都要点），要么全自动（什么都不管）。

**根因**

产品把"AI 模式"当成一个开关。

**解法**

- **按任务类型分级**
- 用户能逐任务调节（[01 的 P2 自主性旋钮](01-authoritative-guides.md#p2-自主性旋钮渐进授权)）

```
危险动作（删除/推送）  → L3 必须确认
写代码                → L3 确认一次后自主
读文件                → L4 完全自主
```

**本项目现状**：有四档权限（`PermissionPicker`）+ 危险动作审批。
但**没有按任务类型细分**，也没有"当前处于哪一级"的可见指示。→ `UD-04`

---

### B5 · 同意是一次性的

**症状**

首次启动点过"同意"，之后 Agent 能力扩展了也不再问。

**解法**（来自 [01 的 P11](01-authoritative-guides.md#原则-11把同意设计成持续的而非二元的)）

1. 首次做某事时问一句
2. **能力同意与数据同意分开**
3. 同意范围要窄
4. **撤回应同样容易**
5. 能力边界变化时重新征求

**本项目现状**：模型密钥在设置里填一次即可。
权限是持续配置（✅ 不是一次性），但没有"高影响动作首次执行时提示"的机制。→ `UD-05`

## C. 信息架构

### C1 · 长代码 / Diff 塞进消息气泡

**症状**

会话流里一个 diff 占了 5 屏，后面的对话完全找不到。

**根因**

把 Agent 的**产物**（代码、diff、日志）和**对话**当成同一种信息，塞进同一个纵向流。

**解法**

**产物与对话物理分离**（Claude Code 的做法）：

```
┌──────────────┬─────────────┐
│ 对话          │ 产物面板     │
│              │ • 改动文件   │
│ 你：...       │ • Diff      │
│ Agent：...    │ • 运行结果   │
└──────────────┴─────────────┘
```

**怎么验证**

跑一个改动 5+ 个文件的任务，统计会话流被 diff 占用的行数。
目标和：**对话流里看不到完整 diff**，只有一行摘要。

**本项目现状**：✅ 已有右栏（`RightRail`：待办/改动/文件）+ 独立改动页（`ChangePage`）。

---

### C2 · 一切平铺，没有层级

**症状**

所有信息一样重，用户找不到重点。

**解法**

**三层披露**：

| 层 | 内容 | 出现方式 |
| --- | --- | --- |
| 1 | 一句话结论 | 默认可见 |
| 2 | 关键细节（改了哪些文件、多少行） | 一行摘要 |
| 3 | 完整内容（diff、日志） | 点击展开 |

**本项目现状**：部分满足。轨迹页已有（✅），但对话流内的披露层级需要梳理。→ `UD-02`

---

### C3 · 多 Agent 并行时不知道谁在干什么

**症状**

派了 3 个 Agent，侧栏只显示一堆状态，看不出谁快谁慢、谁卡了。

**解法**

**每个 Agent 一条泳道**：

```
登录页重构    ████████░░  第 3 步 · 修改 Login.tsx
导出排障      ███░░░░░░░  第 1 步 · 分析瓶颈
测试补充      ⚠ 等待批准：要新增 12 个测试文件
```

关键要素：
- 每个 Agent 一条，视觉上可比较
- 显示**当前步骤**，不只是状态
- **需要拍板的置顶**并高亮

**本项目现状**：✅ 有 `BatchBlock`（批次块，每个 Agent 一行）+ 跑道点。
没有"当前步骤"和"进度感"。→ `UD-01`

---

### C4 · 跨会话状态丢失

**症状**

关掉软件再打开，对话没了，得从头说。

**根因**

会话状态只存在内存里，进程一退出就没了。

**解法**

**常驻会话 + 重启恢复**。

**怎么验证**

开启一段对话 → 完全退出进程 → 重新启动 → 检查对话仍在且能继续。

**本项目现状**：✅ 已做（`assistantSessionId` 持久化，有重启恢复测试）。

## D. 信任

### D1 · 不知道 Agent 的依据

**症状**

Agent 说"我改了登录逻辑"，但不知道它看了哪些文件、为什么这么改。

**根因**

只呈现 Agent 的**结论**，没呈现**证据链**。结论无法回溯 = 无法信任。

**解法**

- 显示来源：读了哪些文件、跑了哪些命令
- 可追溯：每个结论能点回到原始证据

**Perplexity 的做法**：来源与步骤是**独立层级**，与答案并列。

**怎么验证**

对任意一条 Agent 结论，应能在 1 次点击内找到它读了哪些文件、跑了哪些命令。

**本项目现状**：✅ 轨迹页有完整记录 + 副作用台账。

---

### D2 · 失败时只说"出错了"

**症状**

红字一行"任务失败"，没有更多信息。

**解法**

失败信息三要素：

| 要素 | 例子 |
| --- | --- |
| **发生了什么** | TypeScript 编译失败：`Login.tsx:42` 缺少 `useAuth` 的导入 |
| **保留了什么** | 已完成的 3 个文件改动已保存 |
| **怎么重试** | [重试] [查看完整日志] [跳过这一步] |

**本项目现状**：有错误分类展示（`errorDisplay.ts`、`ERROR_KIND_LABEL`），
但"保留了什么"和"怎么重试"的完整性需要确认。→ `UD-06`

---

### D3 · 无法知道 Agent 的权限边界

**症状**

用户不知道 Agent 现在能不能删文件、能不能推代码。

**解法**

**常驻显示当前授权级别**（像文本编辑器的模式指示器）。

来自 [01 原则 12](01-authoritative-guides.md#原则-12逐刻协商能动性)：

> "让当前自主级别常驻可见。用户应该始终知道 AI 现在被授权做什么。"

**本项目现状**：权限在设置里配，但**界面上不常驻显示**。→ `UD-04`

---

### D4 · 结果无法核查

**症状**

Agent 说"已完成"，但实际没做完 / 做错了。

**解法**

**独立验收，不采信自述**。

**怎么验证**

让 Agent 报告"已完成"但实际未完成（可用假模型模拟），
系统验收应判定为失败，而不是采信自述。

**本项目现状**：✅ 已有 `acceptance/verify.ts`（系统独立验收）。

## E. 动效与反馈

### E1 · 长循环动画累人

**症状**

转圈转了 5 分钟，越看越烦。

**解法**

- 思考态用**温和、低对比度**的循环
- 尊重 `prefers-reduced-motion`
- 减少动效时用**细微的不透明度变化**代替

来源：[WCAG 2.3.3 Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)

**本项目现状**：需要检查是否支持 `prefers-reduced-motion`。→ `UD-07`

---

### E2 · 流式输出强行拽回底部

**症状**

用户在往上翻历史消息，新内容一来就被拽回底部。

**根因**

滚动位置只有"跟随"一种策略，没有区分"用户在阅读"和"用户在等新内容"。

**解法**

基于 `distanceFromBottom` 判断：

- 用户**贴底**时 → 平滑跟随
- 用户**向上翻阅**时 → **立即冻结**自动滚动

这是 `desktop-agent-ui` skill 的 **ENG-11**。

**本项目现状**：`Conversation.tsx` 有 `scroll.atBottom` / `scrollToBottom`，
说明已经实现了跟随逻辑。需要确认"用户上翻时冻结"是否完整。→ `UD-08`

---

### E3 · 状态切换生硬

**症状**

状态从"执行中"变"完成"时，界面跳一下。

**解法**

按 [ui-dev-guide 3.6](../ui-dev-guide.md#36-动效) 的规则：

| 变化 | 时长 |
| --- | --- |
| 状态变化（颜色/文字） | `--dur-fast` |
| 元素出现/消失 | `--dur-base` |
| 面板滑入 | `--dur-slow` |

**本项目现状**：令牌已定义 ✅。需要检查实际使用是否一致。→ `UD-09`

---

### E4 · 数字跳动导致横向震颤

**症状**

token 数从 `999` 变到 `1000` 时，整行往右移一点点。

**解法**

所有动态数字加 `font-variant-numeric: tabular-nums`。

（这是 `desktop-agent-ui` skill 铁律之一）

**怎么验证**

让数字从 9 变到 10、从 999 变到 1000，观察宽度是否变化。

**本项目现状**：需要全局检查。→ `UD-10`
