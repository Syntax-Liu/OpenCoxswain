# 02 · 热门产品怎么做的

> 这一章回答：**这些原则在真实产品里长什么样。**
>
> 每个产品用同一套结构写：布局 → 状态呈现 → 典型做法 → 可借鉴点 → 不可照搬点。

拆解的目的是**提取模式**，不是抄视觉。

- ✅ 抄：状态怎么呈现、信息怎么分层、措辞怎么选

## 一、Perplexity —— 措辞与信任

> 来源：[深度拆解 Perplexity 的设计团队和产品体验](https://www.uisdc.com/perplexity-2)（优设网，2025-10）

### 1.1 产品定位

AI 搜索引擎，核心理念 **"Answer first, but verify"**（先给答案，但要能核实）。

这个定位直接决定了界面：**来源和思考步骤不是附属信息，是内容骨架的一部分。**

### 1.2 布局

```
提问框
  ↓
[搜索步骤 1] [搜索步骤 2] [搜索步骤 3]   ← 独立层级，且用"审核"一词
  ↓
答案
  ↓
[来源 1] [来源 2] [来源 3]                ← 独立层级，可与答案对照
```

**关键**：来源和步骤**与答案并列**，不是塞进答案里，也不是折叠在角落。

### 1.3 状态呈现：用颜色而非文字

语音模式的状态：

| 状态 | 表现 |
| --- | --- |
| 在听 | **橙色** |
| 在说 | **绿色** |

原文解释：

> "面对实时、快速的语音对话，Perplexity 认为反馈应该更直接、更即时。
> 因此，它选择了一种更轻量的反馈语言——颜色。
> 在听觉与视觉双通道并存的场景里，颜色是最高效的状态提示符。"

**这是"反馈成为体验的一部分，而非界面的附加物"的典范。**

### 1.4 措辞：一个词的选择

| 用了 | 而不是 | 为什么 |
| --- | --- | --- |
| **审核** | 搜索中 | "审核"传递严谨、负责的态度，提升对结果的信任预期 |

**这是本次拆解里最便宜、最可复制的改进。**

### 1.5 可借鉴点

| # | 做法 | 本项目的对应 |
| --- | --- | --- |
| 1 | 来源/步骤作为独立层级，不塞进结果 | Agent 的轨迹页已经独立，✅ |
| 2 | 用准确措辞传达态度（"审核" vs "搜索中"） | 「执行中」可以更具体 |
| 3 | 颜色编码状态，不用额外文字 | 项目已有 `--color-warn` 等语义色 |
| 4 | 为**动态**而非静态设计 | 需要状态机支持 |

### 1.6 不可照搬

- 复古未来主义品牌视觉 —— 与"夜幕指挥台"调性冲突
- 移动端移除底部导航 —— 桌面端不适用

## 二、Cursor —— 视觉化驱动

> 来源：[Cursor Design Mode](https://cursor.com/blog/design-mode)（2026）

### 2.1 核心做法

不只靠文本提示，**可以用可视化方式指定修改对象**。

```
用户在界面上点选元素 → 系统生成精确的修改指令 → Agent 执行
```

### 2.2 可借鉴点

| # | 做法 | 说明 |
| --- | --- | --- |
| 1 | 减少文字描述的成本 | 点选比打字快 |
| 2 | 指令更精确 | 避免"就是那个按钮"的歧义 |

### 2.3 对本项目的启示

本项目的 `@` 文件引用（MentionPicker）是同思路的轻量版：
**用选择代替描述**。可以扩展到：

- 在轨迹页点选某条工具调用 → 直接追问"这里为什么失败"
- 在改动页点选某个文件 → 直接问"这个改动的作用"

## 三、Claude Code —— 产物分离

> 来源：[Claude Code: Share session output as artifacts](https://code.claude.com/docs/en/artifacts)（2026）

### 3.1 核心做法

**会话产物（artifacts）与对话流物理分离**，产物可以带回会话。

### 3.2 布局

```
┌─────────────────────┬──────────────────┐
│ 对话流               │ 产物面板          │
│                     │                  │
│ 你：...              │ • 生成的页面      │
│ Claude：...          │ • 修改的文件      │
│                     │ • 运行结果        │
└─────────────────────┴──────────────────┘
```

### 3.3 为什么重要

长代码、Diff、工具输出如果全压进纵向消息气泡流：

- 对话被淹没
- 滚动位置丢失
- 想回头找产物得翻很久

### 3.4 可借鉴点

| # | 做法 | 本项目的对应 |
| --- | --- | --- |
| 1 | 产物与对话物理分离 | ✅ 已有右栏（`RightRail`）+ 改动页 |
| 2 | 产物可带回会话 | 改动页的文件能否点开追问？ |

**本项目这一点已经做对了**——右栏多页签（待办/改动/文件）就是产物分离。

## 四、v0 / ChatGPT —— 等待体验

### 4.1 核心问题

生成需要时间，但用户不能干等。

### 4.2 做法

| 阶段 | 表现 |
| --- | --- |
| 0.1s 内 | 用户消息立即上屏 |
| 思考中 | 一个平静的指示器 |
| 开始输出 | 指示器消失，文字逐字出现 |
| 完成 | 操作按钮出现（复制/重试） |

### 4.3 关键细节

**指示器和流式输出不能同时存在。** 文字一开始出现，思考指示器就该停。

原文（来自 ExodeUI）：

> "流式传输：在输出到达时显示输出；文本一开始就停止思考指示器。"

### 4.4 可借鉴点

本项目已经做了逐字增长（手动测试清单里 A1 记着"376 帧 / 237 种长度"），
但需要确认：**流式开始时，思考指示器是否真的停了。**

## 五、Linear —— 桌面质感

> 来源：[Design System: Linear](https://github.com/nousresearch/hermes-agent/blob/f578714e0ee122179ec28fecb9af989583b71baf/skills/creative/popular-web-designs/templates/linear.app.md)

### 5.1 视觉特征

| 项 | 做法 |
| --- | --- |
| 阴影 | **几乎零阴影**，用 0.5px 边框切分 |
| 圆角 | 克制（4-8px） |
| 强调色 | 全站一个 |
| 密度 | 高信息密度，但留白克制 |

### 5.2 为什么适合桌面工具

桌面软件不是移动 App。大圆角、大阴影、大留白都是移动语言。

### 5.3 与本项目的关系

本项目的 `styles.css` 顶部注释写着：

> 设计参考 Visual Studio Code：**桌面软件，不是手机 App**。

方向一致。这也是 `desktop-agent-ui` skill 里说的"页面默认平（Zero Shadow on Panels）"。

**本项目已满足**，无需改。

## 六、横向对比：状态呈现

把上面几个产品的状态呈现方式放在一起：

| 产品 | 状态粒度 | 呈现方式 |
| --- | --- | --- |
| Perplexity | 3 个搜索步骤 | 编号步骤 + "审核"措辞 |
| Cursor | 工具调用序列 | 内联展开 |
| Claude Code | 工具调用 + 产物 | 对话内 + 独立面板 |
| v0 | 思考/流式/完成 | 指示器切换 |
| **本项目** | **6 个状态** | **侧栏一行文字 + 跑道点** |

**差距在哪**：本项目的状态数量**够多**（比 Perplexity 细），
但**呈现方式太弱**——只有一行文字，没有：
- 当前在做什么（具体步骤名）
- 进度感（第几步/共几步）
- 多久了

详见 [03](03-agent-ui-problems.md) A 类。

[assistant-ui](https://github.com/simonbengtsson/assistant-ui)：TypeScript/React 的 AI 聊天组件库。

## 八、这一章的结论

**可以直接抄的三条：**

1. **措辞要准确**（Perplexity 的"审核" vs "搜索中"）—— 零成本
2. **来源/步骤是独立层级**（Perplexity）—— 本项目已做
3. **流式开始时停掉思考指示器**（v0）—— 需要确认

**需要补的：**

- 状态呈现的粒度（本项目 6 状态但只有一行字）
- 当前步骤的具体名称

**不用改的：**

- 产物分离（已有右栏）
- 零阴影桌面质感（已符合）
