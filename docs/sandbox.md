# 命令沙箱

> **这不是进程隔离。** 是命令执行前的静态检查——挡住明显的越界写操作。

---

## 为什么要沙箱

已有的三道防线，各漏一点：

| 防线 | 挡什么 | 漏什么 |
| --- | --- | --- |
| 只读拦截 | 只读任务里的写命令 | 读写任务完全不适用 |
| 写域闸门 | 改错目录 | **只作用于工具，不管 shell 命令** |
| 危险动作审批 | 删 / 推 / 发布 / 付款 / 外发 | **只认关键词，绕得过** |

一条 `robocopy C:\somewhere D:\backup` 或 `echo x > D:\important.txt`
只要没命中关键词，就真的会执行。

**审批是「事后问一句」，沙箱是「根本做不到」。**

---

## 它怎么工作

在执行命令**之前**分析命令文本：

1. 抽出命令里出现的路径
2. 判断这条命令是否**会写**
3. 如果是写命令 + 路径在项目外 → 拒绝

位置在**审批之前**：越界的写操作根本不值得惊动用户。

---

## 能挡住

| 情况 | 示例 |
| --- | --- |
| 显式引用项目外的绝对路径 | `copy a.txt D:\backup\a.txt` |
| UNC 路径 | `copy a.txt \\server\share\a.txt` |
| 跳到上级目录再操作 | `cd .. && rm -rf build` |
| **shell 重定向写到项目外** | `echo x > D:\important.txt` |
| 复合命令里的写操作 | `dir && del C:\x.txt` |
| 各种语言的删除/移动命令 | `Remove-Item`、`rm`、`robocopy`、`mv`… |

---

## 挡不住（必须知道）

| 情况 | 为什么 |
| --- | --- |
| **运行时才算出的路径** | `$p = (Get-ChildItem env:OUT).Value; Remove-Item $p` —— 命令文本里没有项目外字面量 |
| 脚本内部的操作 | `node cleanup.js` 里做什么，静态检查看不到 |
| 项目内的删除 | `rm -rf .` 是项目内，沙箱不管——**靠审批** |

**所以沙箱是纵深防御的一层，不是唯一防线。**
真正的保证仍然来自：审批 + 只读档 + 事后可查的副作用台账。

---

## 不误杀什么

**查询命令读项目外是允许的**：

```bash
dir D:\logs          # ✅ 放行
Get-Content C:\x.log # ✅ 放行
```

只有「写命令 + 项目外路径」这个**组合**才拦。这是刻意的——
读日志、查文件是常见需求，全面禁止会让工具变得难用。

---

## 放行特定目录

需要操作项目外时，明确列出目录，而不是全面放开：

```ts
createExecutorToolHost({
  rootPath,
  allowOutside: ['D:\\temp\\build-cache'],
})
```

## 一个真实的事故记录

第一版沙箱**完全没生效**，而且**测试全绿**。

原因：`isWriteCommand` 只检查命令名，而 `echo hello > file`
的命令名是 `echo`（只读命令）。

**测试没覆盖到，单元测试也测的是我想到的情况。**

发现方式是**真实跑一遍**：创建一个临时目录，让 Agent 往项目外写文件，
然后检查文件有没有真的被创建。结果文件被创建了。

修法是加上重定向识别：

```js
if (/(?<![0-9])>{1,2}(?!&|>)/.test(command)) return true;
```

修完再跑同一个验证，文件没有再被创建。

**教训**：沙箱这类安全机制，必须用「真实执行 + 检查副作用」验证，
不能只看函数返回了什么。
