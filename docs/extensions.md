# 扩展口（给 geek 的自定义点）

## 这不是插件系统

**不需要写清单、不需要注册、不需要打包。** 往一个目录里丢一个 `.js` 文件就行。

为什么这么设计：插件系统要付出生命周期管理、依赖注入、版本兼容的复杂度，
而我们现在没有第三方生态。geek 要的是「**能在不 fork 的前提下改一点行为**」，
不是「做一个生态」。

> 如果你要的是完整插件框架，见 [architecture.md](architecture.md) 里
> 「什么条件下才真的上插件框架」——到了那天再上，那时接口长什么样已经清楚了。

---

## 怎么用

把 `.js` / `.mjs` 放到：

```
~/.opencoxswain/extensions/
```

文件导出 `default` 函数，参数是 `api`：

```js
// ~/.opencoxswain/extensions/audit.js
export default function (api) {
  // 1. 拦截：返回 { veto: true } 就能阻止这次工具调用
  api.beforeTool(({ tool, args }) => {
    if (tool === 'run_command' && String(args.command).includes('sudo')) {
      return { veto: true, reason: '本机策略：不允许 sudo' };
    }
  });

  // 2. 观察：工具执行完后通知你（仅用于记录，不能改结果）
  api.afterTool(({ tool, ok }) => {
    console.log(`[audit] ${tool} → ${ok ? 'ok' : 'fail'}`);
  });
}
```

**改完重启生效。** 故意不做热加载——热加载会让「当前行为」难以复述，
排查问题时你永远不知道跑的是哪份代码。

---

## 能做什么、不能做什么

| 扩展点 | 能 | 不能 |
| --- | --- | --- |
| `beforeTool` | 否决一次工具调用，给出可读理由 | 改参数 |
| `afterTool` | 观察、记录、上报 | 改变执行结果 |

### 为什么不允许改参数

改参数会让**副作用台账记录的东西和实际发生的事不一致**。
台账是产品可信性的基础（A4：「出事时能回答它到底改了什么」），
不能为了灵活性破坏它。

---

## 安全边界（重要）

### 扩展跑在运行时进程里，和主程序同权

这意味着：

- 一个扩展可以让程序崩溃、可以读你的文件；
- **只放你信任的扩展**，就像只 `npm install` 你信任的包一样。

### 出错不会拖垮主程序

- 加载失败 → 记进 `problems`，跳过这一个，其它照常加载；
- 运行中抛异常 → 当作「不否决」，继续执行。

一个 geek 写错一个分号，不该导致软件打不开。

### 扩展**不能**绕过核心机制

这三样是硬边界，测试守着：

| 机制 | 扩展能否绕过 |
| --- | --- |
| 写域限制 | ❌ 不能 |
| 只读任务限制 | ❌ 不能 |
| 危险动作审批 | ❌ 不能 |
| 验收复核 | ❌ 不能 |

对应测试见 `apps/runtime/src/test/extensions.test.ts` 的
「安全边界：扩展不能绕过核心机制」。

> `beforeTool` 的优先级**高于**审批闸门——
> 本机策略（例如"我这台机器不许 sudo"）应该在问你要不要批准之前就拦掉，
> 而不是先弹一个审批框让你点。

---

## 生效范围

扩展作用于**运行时的全部工具调用**：派活、续聊、验收复核都会经过它。

只有界面（Web）不经过扩展——它没有工具调用。

---

## 排查

启动时如果扩展有问题，日志里会看到：

```
扩展加载失败（已跳过）：audit.js：Unexpected token '}'
已加载 2 个扩展：audit.js, notify.mjs
```

看一眼日志就知道哪个坏了、为什么坏。

## 与插件框架的差别（一句话）

| | 扩展口（现在） | 插件框架（将来） |
| --- | --- | --- |
| 加一个能力 | 改核心代码 + 丢个文件 | 装一个包 |
| 隔离 | 无（同进程同权） | 有（服务隔离、生命周期） |
| 版本兼容 | 不保证 | 需要承诺 |
| 复杂度 | 极低 | 高 |

现在选前者，因为只有一个人维护、没有第三方贡献者。
