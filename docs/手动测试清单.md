## 怎么用这份清单

每条测试项包含四栏：

| 栏         | 含义                 |
| ---------- | -------------------- |
| **触发**   | 在哪个界面、发什么话 |
| **正确**   | 应该看到什么         |
| **错误**   | 出现这些就是在 bug   |
| **为什么** | 这条测的是什么原理   |

**发消息的方式**：主界面底部输入框，回车发送。
**提示词**：直接复制「触发」里的引号内容。

# A. 基础对话与流式输出

## A1. 普通对话

**触发**：输入 `你好`

|            |                                                                        |
| ---------- | ---------------------------------------------------------------------- |
| **正确**   | 回复文字**逐字出现**（流式），不是整段蹦出来。状态栏「轮次 +1」        |
| **错误**   | ① 一次性蹦出整段 ② 弹「⚠ 更正」 ③ 界面上出现"（检测到……）"这类系统提示 |
| **为什么** | 验证 SSE 流式链路。P0 里最容易一眼看出的问题                           |
| **结果**   | 整一段一次性蹦出                                                       |

## A2. 连续追问

**触发**：先发 `1+1等于几`，等回复完，再发 `那再加3呢`

|            |                                         |
| ---------- | --------------------------------------- |
| **正确**   | 第二个回答是 5，说明记得上文            |
| **错误**   | 回答"3"（丢失上下文）或重新问你要算什么 |
| **为什么** | 会话历史拼接                            |
| **结果**   | 正确                                    |

## A3. 同一轮连发两条

**触发**：发 `第一句`，**不等回复**，立刻发 `第二句`

|            |                                                                                                                                                                                                                                                       |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **正确**   | 两条都被回应，顺序不乱                                                                                                                                                                                                                                |
| **错误**   | 只回了后一条 / 报错 / 顺序颠倒                                                                                                                                                                                                                        |
| **为什么** | inbox 排队机制                                                                                                                                                                                                                                        |
| **结果**   | 部分正确，确实能逐条回复，但是首先，它不能在我发送第一条的时候马上回复（即使不能马上回复也应该留个对话框占个位），其次，两段回复是合在一起全部一起蹦出来的，而且Assistant似乎还不能联网，它不能读取元宝回答的链接（是直接无法访问，而不是读不到内容） |

## A4. 中文与长文本

**触发**：发一段 500 字以上的中文（可以复制文章段落）

|            |                                   |
| ---------- | --------------------------------- |
| **正确**   | 正常理解并回应，不截断            |
| **错误**   | 回复说"内容被截断" / 只读到前半段 |
| **为什么** | 消息长度处理                      |
| **结果**   | 正确                              |

# B. 派 Agent（核心，P0）

> ⚠️ **这一组是重点**。历史上有过"Assistant 不肯派活、谎报已派出"的严重问题。

## B1. 第一次说就派

**触发**：在**新项目**里发 `派一个只读 Agent，统计这个项目有多少个 .ts 文件`

|            |                                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------------ |
| **正确**   | ① 调用了 `spawn_executor` ② 侧栏出现一个 Agent 卡片 ③ 状态从"启动中"→"执行中"→"已完成"           |
| **错误**   | ① 只说了"已派出"但没有 Agent 卡片 ② 出现「⚠ 更正：上一条说的已派出不成立」③ 要你重复说好几次才动 |
| **为什么** | **谎报检测 + 上下文污染修复**。撒谎的话不会进历史                                                |
| **结果**   | 正确，一次就成功派出了Agent执行，且在Agent执行完成之后，Assistant及时汇报                        |

## B2. Agent 真的干了活

**触发**：等 B1 的 Agent 完成

|            |                                                                                                                                     |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **正确**   | 点开 Agent，能看到它真实读过文件、执行过命令。结论里数字和实际相符                                                                  |
| **错误**   | 结论里的数字是编的（去数一下实际有多少个 .ts）                                                                                      |
| **为什么** | 验证 Agent 真的在执行而不是在编                                                                                                     |
| **结果**   | 待验证，Assistant的回复是：结论：排除 node_modules、dist、target 等构建产物和依赖目录后，项目共 612 个 .ts 文件；全算上是 4759 个。 |

## B3. 派活后立刻返回

**触发**：发 `派一个 Agent 分析 docs 目录下所有文档的结构`

|            |                                                                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- |
| **正确**   | Assistant **立刻**回一句（几秒内），不等 Agent 跑完                                                                       |
| **错误**   | 界面卡住几十秒才回应（Assistant 在等 Agent）                                                                              |
| **为什么** | 派活是异步的。卡住说明 await 错了                                                                                         |
| **结论**   | 正确，但是问题还是像前面说的一样，整段蹦出来，还有个问题是Agent 撞到了单轮 40 轮上限，docs 文档量大、一次全量分析太重了。 |

## B4. 多个 Agent 并行

**触发**：发 `同时派两个只读 Agent：一个统计 .ts 文件数，一个统计 .md 文件数`

|            |                                                                      |
| ---------- | -------------------------------------------------------------------- |
| **正确**   | 侧栏**同时出现两个** Agent，状态都是"执行中"，并行跑（不是一前一后） |
| **错误**   | 只出现一个 / 第二个显示"排队中"（只读任务不该排队）                  |
| **为什么** | 只读任务不参与写域互斥                                               |
| **结果**   | 正确达到预期，且分开汇报，但是还是撞到了40轮工具调用                 |

## B5. 写域冲突

**触发**：发 `派两个 Agent 同时改 src/main.ts，一个改成 A，一个改成 B`

|            |                                                                                                                                  |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **正确**   | 第二个 Agent 显示"排队中"，并说明是写域冲突                                                                                      |
| **错误**   | 两个同时改同一文件（会互相覆盖）                                                                                                 |
| **为什么** | 写域互斥保护                                                                                                                     |
| **结果**   | 不符合预期，但结果仍然正确，Assistant提示：这个我不派——不是不干，是这个派法必然出事。这也是良好的结果之一，而不是盲目派Agent修改 |

## B6. Agent 完成后汇报

**触发**：等 B1 的 Agent 跑完

|            |                                                                  |
| ---------- | ---------------------------------------------------------------- |
| **正确**   | Assistant **主动**发一条消息汇报结果（不需要你问）               |
| **错误**   | ① 只有 Agent 卡片变绿，Assistant 一声不吭 ② 汇报被「⚠ 更正」盖住 |
| **为什么** | **Trigger 唤醒 + 汇报轮不被重试打断**（v0.108 修的）             |
| **结论**   | 正确，及时汇报了，且能分开汇报                                   |

# C. Trigger 唤醒（P0）

## C1. 完成必须唤醒

**触发**：派一个 30 秒内能跑完的只读 Agent，然后**什么都不做**，盯着看

|            |                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **正确**   | Agent 变"已完成"后，**几秒内** Assistant 自动说话汇报                                                                                                                                                                                                                                                                                                                                                          |
| **错误**   | 一直没动静，要你发"跑完了吗"才回应                                                                                                                                                                                                                                                                                                                                                                             |
| **为什么** | `worker_report` 必须 `wake: true`                                                                                                                                                                                                                                                                                                                                                                              |
| **结果**   | 这轮测试的结果很奇怪，我说“在项目根目录下面创建一个hello.cpp，然后内容用C++写一个输出“Hello, I am OpenCoxswain.”，不需要编译”，然后Assistant派Agent完成任务了，Agent完成之后，Assistant也马上汇报了，但是Assistant汇报的结果是“Agent 自称写好了，但系统复核发现工作区没有任何改动”，但实际上经人工核验，Agent已经完成，且结果符合预期，Assistant说会重新派一个Agent来完成，但也没有派，这一轮Assistant出现幻觉 |

## C2. 失败必须唤醒

**触发**：发 `派一个 Agent 去读 D:\这个路径不存在\abc.txt 并总结内容`

|            |                                                                                                                        |
| ---------- | ---------------------------------------------------------------------------------------------------------------------- |
| **正确**   | Agent 失败后，Assistant 主动告诉你是失败了、为什么                                                                     |
| **错误**   | 失败了但 Assistant 不吭声                                                                                              |
| **为什么** | `worker_failed` 唤醒                                                                                                   |
| **结果**   | 符合预期，但出现了问题。Assistant及时汇报了结果，且符合预期，但是第一次它调用Agent失败了，需要我再和它说一次才调用成功 |

## C3. 开始跑**不该**唤醒

**触发**：派一个大任务（要跑几分钟的），观察它启动的瞬间

|            |                                                                          |
| ---------- | ------------------------------------------------------------------------ |
| **正确**   | Agent 开始跑时，Assistant **不会**发"它开始了"这类话（侧栏状态变就够了） |
| **错误**   | 每次 Agent 启动都蹦一句废话                                              |
| **为什么** | `worker_started` 是 `wake: false`，省模型调用                            |
| **结果**   | 符合预期                                                                 |

## C4. 取消**不该**唤醒

**触发**：派个长任务，然后点 Agent 卡片上的停止

|            |                                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **正确**   | 状态变"已取消"，Assistant 不吭声（是你自己按的）                                                                                     |
| **错误**   | Assistant 反问"为什么要取消"                                                                                                         |
| **为什么** | `worker_cancelled` 是 `wake: false`                                                                                                  |
| **结果**   | 未测试，这个测试本身就有问题，即使是用户主动取消，Assistant也需要提示用户Agent被暂停了，然后问是否需要继续，也确实不能问“为什么取消” |

# D. Eval 评估层（P1）

## D1. 客套话不触发行动

**触发**：发 `谢谢`

|            |                                                                                                                                                                                         |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **正确**   | 消息显示在界面上，但 Assistant **不回复**，也不派 Agent                                                                                                                                 |
| **错误**   | 回一大段话 / 派了 Agent                                                                                                                                                                 |
| **为什么** | `ignore`：客套话不值得花一次模型调用                                                                                                                                                    |
| **结果**   | 这项测试也有问题，用户说客套话，只需要让Assistant自己回复即可，但是实际测试之后，发了“谢谢”会卡住，进入超长时间的等待。不做ignore是因为客套话是无限多的，ignore做不完全，而且问题会很多 |

## D2. 「算了」要能停下

**触发**：派一个长任务，等它开始跑，然后发 `算了`

|            |                                                                            |
| ---------- | -------------------------------------------------------------------------- |
| **正确**   | Assistant 确认并**问你要停哪个**（或直接停掉那个唯一的），Agent 变"已取消" |
| **错误**   | 把"算了"当成新任务理解，又派了个 Agent                                     |
| **为什么** | `stop` 决定，有专门路径                                                    |
| **结果**   | 符合预期                                                                   |

## D3. 没任务在跑时「算了」不误判

**触发**：没有 Agent 在跑时，发 `算了`

|            |                                    |
| ---------- | ---------------------------------- |
| **正确**   | 正常对话回应，不会奇怪地执行"停止" |
| **错误**   | 出现"没有 Agent 可停"这种报错      |
| **为什么** | 停信号只在有任务在跑时生效         |
| **结果**   | 符合预期                           |

## D4. 长句里的"取消"不算停

**触发**：发 `取消订阅之后怎么恢复？`

|            |                     |
| ---------- | ------------------- |
| **正确**   | 当作**提问**回答    |
| **错误**   | 去停 Agent 了       |
| **为什么** | 停信号限长度 ≤12 字 |
| **结果**   | 符合预期            |

3. **预期是什么**

如果方便，再带上「右下角状态栏的轮次/步数」——能帮我判断是模型没动还是代码没接上。
