# 全网扫描：竞品格局与"蓝海"判定

> 日期：2026-11-11
> 方法：检索公开产品文档、开源仓库与媒体报道，只采信能拿到原文的结论；拿不到原文的标"未核实"。
> 前提：产品最终形态是**完全自研**的四层结构桌面软件（不依赖 dsh / TRAE 等任何外部 Agent 框架）。见 [`docs/README.md`](README.md)。
> 结论一句话：**方向不是蓝海，但存在一个真实的、尚未被占领的窄缝隙。** 见 §4。

---

## 1. 我们的方向是什么（先对齐，再比）

四层结构：**A 用户 → B 全局助理 → C 项目助理（一项目一 C，常驻） → D 执行 Agent（一事一 D，并行）**。

三个判别特征，缺一个就不算同一赛道：

1. **C 常驻于项目**，不是一次性任务执行器；
2. **用户直接跟 C 说话**是主推流程，B 只是多项目迷路时的路由器；
3. **C 派 D、D 并行、谁先完成先汇报**，C 对 D 的卡点有主动推进责任。

## 2. 竞品全景

### 2.1 第一梯队的直接对标：TRAE 宝

来源：[TRAE 官方文档 · 个人助理：TRAE 宝](https://docs.trae.cn/ide_personal-assistant)（2026-11-11 读取）

**官方原文事实**：

- "TRAE 宝由两个角色组成：**全局助理**：理解你的长期积累。它跨项目读取历史任务、对话和产物……**项目助理**：负责当前项目的执行。它可以围绕一个具体的项目工作，掌握更完整、精确的项目上下文，拆解复杂需求，**调度子任务并行推进**，完成联调与汇总。"
- **交互入口与我们一致**：点左侧导航的 TRAE 宝 → 打开的是**全局助理**；点项目栏某个项目 → 打开的是**"项目专属 · TRAE 宝"（项目助理）**的对话面板。即"用户直接找 C"这条路 TRAE 也是通的。
- **连发能力**：支持"回复某条消息追加信息"；文档描述"你也可以继续布置其他任务，无需等前一个结束"。
- **IM**：飞书（智能体应用）、微信（ClawBot 插件）都已接；手机端可派活；**电脑必须开机且 TRAE 桌面端运行**——和我们"本地执行、关电脑即停"的限制完全一致。
- **完全访问模式**：会关闭沙箱与全部审批检查，官方自己提示"请仔细评估风险"。

**判定**：TRAE 宝已经覆盖了四层结构里的 B 和 C，且交互入口与我们设想的主推流程一致。**我们不是首创。**

## 4. 蓝海判定

### 4.1 直接结论：不是蓝海

三条硬事实：

1. **形态已被验证并被占领。** TRAE 宝 2026-10-29 上线，官方文档确认它同时有全局助理与项目助理，且项目助理就是"对当前项目负责、拆解需求、调度子任务并行、汇总"。我们的 B+C+D 结构**与它同构**。
2. **开源侧体量惊人。** Multica 2.27 万 star、Vibe Kanban 2.56 万、Paperclip 6 万。这些不是小玩具——Multica 已开源可自托管、Vibe Kanban 已出 Cloud 版。
3. **大厂正在把并行能力做成标配。** Cursor 3.0 的 Agents Window 已经"跨仓库并跑多个 agent"。

**如果"蓝海"指的是"没人做"，答案是没有。** 任何"我们首创了多项目多 agent 编排"叙事都会被立刻打脸。

### 4.2 但存在一个真实的窄缝隙

把对比表横着看，会发现**没有一家同时占住下面三格**：

| 缝隙 | 谁占了一部分 | 谁都没有 |
| --- | --- | --- |
| **A. 可核查的执行可信度** | Cursor 有 Bugbot（事后 review）；我们 roadmap 的 A 线（系统独立复核 + 五类危险动作审批 + 副作用台账 + 幂等键） | 把"验收不采信 D 自述"做成**运行时强制**、且**复核失败不允许人工覆盖**——这个组合开源阵营没有 |
| **B. 本地优先 + 白盒记忆** | TRAE 宝有跨项目记忆但闭源云端；Multica 完全没提记忆 | 记忆落在项目目录的 Markdown（`rules.md` / `journal/`），用户可读可改可 git 版本化 |
| **C. 模型中立 + 自托管** | Multica 模型中立但看板门槛高；Cursor/TRAE 都锁自家生态 | 一个**聊天式**入口 + 模型完全自选 + 数据不出本机 |

**最锋利的那一格是 A。** 理由：

- Multica 创始人自己承认"产品功能或技术本身已经没有任何壁垒了"。功能软肋之外，**可信度**是所有人共同的软肋。
- 我们的 A 线已经做完并落地在 `apps/runtime`（危险动作审批、系统独立复核、副作用台账、幂等键），由 216 条运行时测试支撑——这不是画饼，是既有代码。
- 用户真正的心理门槛不是"AI 能不能写"，而是"**我敢不敢把真实项目交给它**"。审批 + 独立复核 + 台账直接回答这个问题。

**B 格（本地白盒）要打折扣地看。** TRAE 宝已有跨项目记忆，说明"记忆"不是空白；我们的差异只在"记忆是本地 Markdown、可读可改可 git 版本化"，这是**实现方式**的差异，不是能力有无的差异。它更适合做留存卖点，不适合做获客主张。

### 4.3 但要说清：缝隙不等于护城河

必须同时承认三条风险，否则缝隙会变成自嗨：

1. **大厂补这格最快。** Cursor 有 Bugbot，TRAE 只需加个复核开关。我们领先的窗口以**季度**计，不是年。
2. **"可信度"是卖点但不是痛点开箱即感。** 用户第一次用时感觉不到它，只在出事时感到。这意味着**获客不能靠它**，它只能提高留存与口碑。
3. **入口生态是硬仗。** TRAE 已接飞书 + 微信且做了手机端；我们只有 Telegram。IM 是我们明显短板。

## 5. 对项目的三条直接建议

### 建议一：改叙事，别喊蓝海

把"首创多项目多 agent 编排"从所有材料里删掉。改成**可验证的差异化**，例如：

> 别人保证 AI 干得快，我们保证**AI 干的活你验收得动**：
> 系统独立复核而不是听 AI 自述；删除、推送、外发这类不可逆动作必须先经你批准；每一次写入都留台账可回滚。

这个叙事**不怕对比**——因为它不依赖"别人没做"，而依赖"我们做进了运行时"。

### 建议二：优先级排序要动

现 roadmap 的顺序是 A 线（已完）→ 然后是成本、IM、模板等。基于本次扫描，建议调整为：

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| **P0** | 把 A 线能力**放到产品第一屏**（验收单、审批卡、台账），而不是藏在设置里 | 缝隙值是 0 如果用户看不见 |
| **P0** | 飞书接入（补 IM 短板） | TRAE/微信/飞书已成型，Telegram 在中国场景覆盖不足 |
| P1 | 白盒记忆的可视化编辑 | B 格缝隙，成本低 |
| P2 | 模板 / 定时任务 | 锦上添花，不解决生死问题 |

### 建议三：明确**不做**的战场

- **不做"无人公司"**（Paperclip 方向）：与"人拍板"的价值主张冲突。
- **不做团队协作/看板**（Multica 方向）：那是组织协同赛道，我们守单人 + 多 agent。
- **不做云端托管 runtime**：本地优先是我们的立身之本，也是与 TRAE 宝"电脑必须开机"一致的产品共识。
