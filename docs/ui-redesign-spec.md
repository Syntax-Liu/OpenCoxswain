# 界面重构设计方案

> 日期：2026-11-15
> 结论先行：**推倒重来**，旧界面保留为 `apps/web-legacy`（可回退），新界面独立重建。
> 本文是施工前的设计稿。**没有定下方向就不写代码**——上一轮边写边改的教训。

---

## 0. 先说清楚旧界面的三个真问题

不是配色不好看，是**结构错了**：

| 问题 | 现状 | 根因 |
| --- | --- | --- |
| 顶部重复 | `OpenCoxswain OpenCoxswain` 并排出现 | 品牌名与面包屑职责重叠 |
| 三栏失衡 | 右栏常驻但大多数时间是空的 | 右栏被当成"信息面板"，实际是**低频**内容 |
| 主区被挤 | 消息区两侧留白不足，行距紧 | 三栏抢空间，正文只有约 560px 可用 |
| 入口迷路 | 不知道点哪里派活、哪里看进度 | 把"导航"和"工作台"混在一列 |

**`App.tsx` 1288 行**——这是症状：所有视图分支、弹窗、开关都塞在一个文件里。

---

## 1. 产品到底是什么（决定了界面该怎么长）

这不是"聊天软件"，也不是"看板"。它的形状是：

> **你给一个项目下指令，一群 Agent 在里面并行干活，你要随时知道谁在干什么、谁卡住了、要不要拍板。**

所以界面的**主角不是对话历史，是"当前这个项目正在发生什么"**。

旧界面对话占了满屏，而"正在发生什么"被压缩成左栏一行小字 `已完成`。**这是最大的错配。**

---

## 2. 领域探索

**这个产品所处的世界**：不是编辑器，是**驾驶台 / 调度室**。
一组任务在跑，你要看的是仪表和告警，不是聊天记录。

**关键概念**（5+）：
- 项目（一个工作区、一个 C）
- Agent（一次任务一个）
- 在途 / 排队 / 完成 / 卡住
- 拍板（需要人决定的事）
- 交付物（写出的文件、改动）
- 上下文（这个项目积累的规则与记忆）

**颜色从哪来**：调度室的光。夜班值守的仪表盘——深色底、信号灯、仪表刻度的冷灰。**不是**浓郁的科技蓝，**不是**暖米色。

**签名元素**（只能属于这个产品的）：
> **Agent 跑道（Runner Lanes）**——每个正在跑的 Agent 是一条水平跑道，
> 从"派活"到"交付"用一条线贯穿，线在移动表示在跑。

这个形状只有"多个并行 Agent"的产品才有。聊天软件不需要它，看板软件是卡片不是跑道。

**要避开的默认做法**：
- ❌ 左侧导航 + 中间对话 + 右侧面板（这是 ChatGPT/Notion 的通用壳）
- ❌ 卡片网格（`rgba(0,0,0,.1)` 阴影 + 统一圆角）
- ❌ 全大写小标签 + 中点分隔的元信息
- ❌ 深色 + 单一荧光色（酸绿/朱红）

## 3. 视觉方向

### 3.1 布局：两区，不是三栏

```
┌─────────────────────────────────────────────────────────────┐
│  ◤ 项目名                    [状态灯]        ⌘K   ⚙         │  ← 单一头部
├───────────────────────┬─────────────────────────────────────┤
│                       │                                     │
│   对话（主区·宽）      │        跑道面板（可收起）            │
│                       │                                     │
│   你: 把登录页重构一下  │   ┌───────────────────────────┐    │
│                       │   │ 登录页重构     ▓▓▓▓▓░░ 70% │    │
│   Assistant: 已派 2 个 Agent   │   │ 导出排障       ▓▓░░░░░ 35% │    │
│                       │   ├───────────────────────────┤    │
│                       │   │ ⚠ 需要你拍板              │    │
│                       │   │   登录页用哪种鉴权？       │    │
│                       │   │   [ 用 JWT ] [ 用 Session ]│    │
│  ┌─────────────────┐  │   └───────────────────────────┘    │
│  │ 说点什么…        │  │                                     │
│  └─────────────────┘  │                                     │
└───────────────────────┴─────────────────────────────────────┘
```

**关键改变**：
- **取消左栏**。项目切换放头部一个下拉——大多数时间你只在一个项目里。
- **取消顶部重复**。头部只有一个项目名。
- **右栏从"信息"变成"活的状态"**：跑道 + 待拍板。它**不常驻**——没有 Agent 时自动收起，主区变宽。
- **主区宽度随状态变化**：空闲时对话区满宽（阅读优先），有任务时按 60/40 分。

### 3.2 颜色

**不是纯黑**。深色底用偏冷的石墨，让"在跑"的信号能跳出来。

| 名称 | 值 | 用途 |
| --- | --- | --- |
| `--ink-900` | `#0c0f14` | 画布（最深） |
| `--ink-800` | `#12161d` | 面板 |
| `--ink-700` | `#1a1f28` | 抬起 / 悬停 |
| `--ink-600` | `#2a313d` | 边框 / 分隔 |
| `--ink-300` | `#8b95a5` | 次要文字 |
| `--ink-100` | `#e6eaf0` | 正文 |

**信号色**（只三个，各有明确含义）：

| 名称 | 值 | 含义 |
| --- | --- | --- |
| `--signal-run` | `#00c2a8` | **正在跑**（青色，只有运行中用） |
| `--signal-ask` | `#f0a020` | **要你拍板**（琥珀，只有待决策用） |
| `--signal-stop` | `#e5484d` | **失败 / 危险** |

> **规则**：`--signal-run` 只能出现在"正在执行"的元素上。
> 青色**不能**用于普通按钮、图标、装饰——否则"在跑"这个信号就不灵了。

### 3.3 字体

**系统字体族，但把等宽用在数字上**：

```css
--font-ui: -apple-system, "Segoe UI", "Microsoft YaHei UI", sans-serif;
--font-mono: "Cascadia Mono", Consolas, monospace;
```

- 正文 15px / 行高 1.65（比现在 loose，解决"太挤"）
- 进度百分比、耗时、token 数用 mono + tabular-nums
- **不用全大写**标签

### 3.4 圆角与深度

- 圆角：`--r-sm: 6px`（输入框/按钮）· `--r-md: 10px`（面板）· `--r-lg: 14px`（浮层）
- 深度：**只用边框和明度差**，不用阴影（桌面工具感）
- 唯一例外：浮层（菜单/弹窗）用一个 `0 8px 24px rgba(0,0,0,.4)`

## 4. 信息架构

### 4.1 三个层级，别混

| 层级 | 是什么 | 在哪 |
| --- | --- | --- |
| **项目** | 一个工作目录 + 一个 C | 头部下拉切换 |
| **对话** | 你和 Assistant 的来往 | 主区 |
| **Agent** | C 派出的 D | 右栏跑道（正在跑时）或对话内嵌（历史） |

### 4.2 入口收敛

现在"派活"藏在输入框里。改为：

- **主区输入框是唯一入口**——你说话，C 决定派不派 Agent；
- **不做"新建任务"按钮**。用户不该区分"聊天"和"派活"。
- **Agent 详情**：点跑道条 → 主区切换到该 Agent 的完整轨迹（可返回对话）。

### 4.3 状态可见性

旧界面把状态压在左栏一行 `已完成`。改为：

- 每个 Agent 在跑道上始终可见；
- 跑完的收成一条细线留在跑道区底部（可展开看历史）；
- **需要你拍板的事置顶**，并且用 `--signal-ask`。

## 5. 组件清单

新组件从零写，不复用旧 CSS。复用旧组件里的**逻辑**（数据获取、状态管理）。

| 组件 | 职责 |
| --- | --- |
| `AppShell` | 两区布局 + 头部 |
| `ProjectSwitcher` | 头部项目下拉 |
| `Transcript` | 对话流（含 markdown、代码块） |
| `Composer` | 输入框（含附件、权限选择） |
| `RunnerPanel` | 跑道区：在跑 / 待拍板 / 已完成 |
| `RunnerLane` | **签名元素**：单个 Agent 的跑道条 |
| `DecisionCard` | 待拍板卡片（含选项按钮） |
| `RunnerDetail` | 点开跑道后的完整轨迹 |
| `Settings` | 设置（沿用现有逻辑，重排视觉） |

## 6. 实施顺序

**核心原则：新旧并存，不破坏现有功能。**

| 步骤 | 做什么 | 产出 |
| --- | --- | --- |
| 1 | 旧界面复制到 `apps/web-legacy`，`apps/web` 清空重建 | 可随时回退 |
| 2 | 新设计令牌 + AppShell + 空架子 | 能跑起来，只有头部 |
| 3 | Transcript + Composer（能对话） | 主流程可用 |
| 4 | RunnerPanel + RunnerLane（看 Agent） | 签名元素出现 |
| 5 | DecisionCard（能拍板） | 闭环 |
| 6 | Settings 迁移 | 完整 |
| 7 | 逐页截图审计 + 对比度 | 验收 |

**每步都能跑、能截图**，不允许"写完一整套再验证"。

## 7. 验收标准

```
[ ] 头部只出现一次项目名
[ ] 无 Agent 时右栏自动收起，主区变宽
[ ] 青色只出现在"正在执行"的元素上
[ ] 正文行高 1.65，单行不超过 75 字符
[ ] 每页截图，两套主题，`audit-live-contrast` 0 处不达标
[ ] 所有入口：Ctrl+K 能找到任何功能
[ ] 键盘可达：Tab 顺序合理，焦点可见
```

## 8. 数据可用性核实（已确认）

### 8.1 有真实数据的

`ExecutorDto` 实际字段（读自 `apps/web/src/api.ts`）：

| 字段 | 可用于界面 |
| --- | --- |
| `label` / `goal` | 跑道标题 |
| `status` | 状态（running/done/failed…） |
| `access` | 只读 or 读写（写域互斥的参与者） |
| `metrics.steps` | **已执行步数** |
| `metrics.turns` | 已进行轮次 |
| `metrics.durationMs` | **已耗时** |
| `metrics.tokensIn/Out` | 用量 |
| `acceptance` | 验收结果（含逐条判定） |
| `summary` / `blockedReason` | 结论 / 卡点 |
| `createdAt` / `endedAt` | 起止时间 |

### 8.2 没有的（所以不做）

**没有进度百分比。** 系统不知道 D 还要多久。

因此跑道条**不画百分比**，改为显示：
```
登录页重构  ● 12 步 · 2m18s  [读写]
```
- `●` 是 `--signal-run` 青色（运行时呼吸动画）
- 步数与耗时是真实数据
- 方括号是权限范围

> **宁可少一个数字，也不编一个假的。** 百分比会让人误判"快好了"，而系统根本不知道。

### 8.3 待拍板数据的来源

`blockedReason` + `acceptance` 里 `verdict === 'unverified'` 的条目。
如果两者都没有，**不显示待拍板区**——不做空壳。
