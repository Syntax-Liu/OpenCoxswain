# 开源共建方向：前提变了，什么该做、什么不该做

> 日期：2026-11-11
> 前提：**本项目不以盈利为目标。** 目标是——自己用一个好产品，尽可能推进开源社区与 Agent 产品的发展。
> 许可证：**待定，正式落地后再说**。本文不涉及许可证选型。

---

## 0. 这个前提推翻了哪些旧结论

先明确撤回，避免后面拿错依据：

| 旧结论（`competitor-verdict.md` §5 原始版） | 现判定 |
| --- | --- |
| "往团队/企业治理走才有预算" | ❌ **撤回**。没有商业化，多玩家/权限/预算审批是纯成本，只会让单人产品变重 |
| "付费意愿低的市场"作为风险 | ⚠️ **不再是风险**。我们本来就不收费 |
| "要回答卖给谁" | ❌ **不再适用** |

**仍然成立**的结论：

- 方向不是蓝海，形态已被 TRAE 宝产品化；
- 真正的差异是"系统独立复核、不采信 agent 自述"；
- Vibe Kanban 的教训改为：**死于缺收入，不死于缺用户**。它证明了需求真实。

## 1. 「不赚钱」改变的问题：从"商业模式"变成"可参与性"

一个不收费的项目，失败模式不是"没人买"，而是这两个：

| 失败模式 | 表现 | 对策 |
| --- | --- | --- |
| **烂尾** | 只有作者一个人维护，作者不写了项目就停在某个版本 | 降低维护成本；把理解成本降到别人能接手 |
| **无人知晓** | 功能再好，没人知道、没人试、没人留 | 可运行性 ×1，可讲述性 ×1 |

> **一句话：不赚钱的项目不需要商业模式，但需要"可参与性"。**

可参与性是三件事的乘积，任何一项为 0，整体为 0：

```
可参与性 = 跑得起来 × 改得动 × 看得懂
```

- **跑得起来**：别人 clone 下来能一次跑通，不踩坑；
- **改得动**：知道该改哪个文件，有测试兜底，改了不会炸；
- **看得懂**：文档说清清的是什么、为什么这样设计。

### 2.2 缺的（都是"可参与性"的硬伤）

按对可参与性的杀伤力排序：

| # | 缺失 | 后果 | 严重度 |
| --- | --- | --- | --- |
| G1 | **没有 `CONTRIBUTING.md`** | 想贡献的人不知道从哪下手，也没人告诉他怎么跑测试 | 🔴 高 |
| G2 | **没有 `CODE_OF_CONDUCT.md`** | 社区一旦有人吵架，没有依据；也显得不欢迎新人 | 🟡 中 |
| G3 | **没有 Issue / PR 模板** | 收到的报告缺关键信息（版本、环境、复现步骤），来回问三轮 | 🟡 中 |
| G4 | **没有"第一个贡献"入口**（good first issue） | 新人不知道能做什么小改动 | 🟡 中 |
| G5 | **没有 CI**（未核实是否配置） | 别人提 PR，没人自动跑测试，作者要手工验 | 🔴 高 |
| G6 | **所有包 `private: true`** | 不影响开源可用性，但会挡住"作为依赖 npm 安装"的用法 | 🟢 低（按需再改） |
| G7 | **没有架构一页纸** | 想读代码的人要从 1.8 万行里自己摸索 | 🟡 中 |
| G8 | **模型端点是硬门槛** | 没有 API Key 的人连试都试不了 | 🟡 中 |

## 3. 该做什么（按投入产出排序）

### O1：让陌生人能跑起来 —— 补 `CONTRIBUTING.md`（半天）

这是**性价比最高的第一件事**。内容不写"欢迎贡献"这种空话，只写四块：

1. **环境要求**：Node 版本、pnpm 版本、是否需要 Rust（只在构建桌面壳时需要）；
2. **最短路径**：三条命令跑起来 + 跑测试；
3. **代码地图**：想改 B/C/D/验收/记忆，分别去哪个文件；
4. **提 PR 的规矩**：测试必须跑过；一个 PR 只做一件事；改行为要带测试。

> 目标：一个没看过这个项目的人，**30 分钟内能跑起测试并看懂该改哪**。

### O2：接上 CI（半天）

在 GitHub Actions 里加一条：`pnpm install && pnpm build && pnpm test`。

- 好处不只是"保证质量"，更是**给外部贡献者信心**——他们能自己看到红绿，不用等作者回话；
- 这是我们唯一的自动化门禁，比任何文档都能提高项目可信度。

### O3：写一页架构图（半天）

`docs/architecture.md`，只讲**数据怎么流**：

```
用户输入 → C（常驻会话）→ 判断冲突 → 派 Agent（子会话）→ D 工具调用
                                              ↓
用户 ←── Assistant 汇报 ←── 结算通知 ←── 验收闸门（系统复核）
```

配上"想改 X 去看 Y"的对照表。**不要写设计哲学，写代码位置。**

### O4：准备"第一个贡献"清单（1 小时，持续维护）

在 Issue 里挂 5~10 个 `good first issue`，挑**真的小、真的不涉及核心逻辑**的：

- 文档错字、README 示例过期；
- 某个错误提示不够清楚（改成能指导用户下一步的）；
- 某个工具的参数描述不准确；
- 加一个测试（现有代码没覆盖的分支）。

**不要**把"重构调度器"这种挂成 good first issue——会劝退新人。

### O5：降低试用门槛（1 天）

现在必须有自己的 API Key 才能试。建议两种兜底之一：

- **离线演示模式**：内置一个假模型端点（`mock-llm.ts` 看起来已有），跑 `pnpm runtime --demo` 就能看到四层结构怎么运作，不需要 Key；
- 或 README 里给出**一个 5 分钟录屏**，让人先看到效果再决定要不要配 Key。

> 这一条直接决定"看过的人里有多少真的试了"，是转化率的瓶颈。

## 4. 不该做什么（同样重要）

不赚钱的项目最容易犯的错是**把精力花在不产生可参与性的地方**。

| 不做 | 理由 |
| --- | --- |
| **不做多用户 / 权限 / 组织** | 无商业化的纯成本；单人产品加了这些会变重且难用 |
| **不做云端托管** | 本地优先是身份，也是与闭源产品拉开的理由 |
| **不做付费功能** | 前提已定，不引入任何账号体系 |
| **不追求功能数量对齐竞品** | 竞品的团队协作、org chart、connectors 都不该跟。我们守"单人 + 多 agent + 可核验" |
| **不为了 star 做增长手段** | star 是结果，不是目标。Vibe Kanban 有 2.56 万 star 仍然关停，说明热闹不等于价值 |

**特别提醒**：上一轮我建议"往上走团队治理"，在这个前提下是错的。**现在正确的方向是往下走——把单人体验做深。**

## 5. 我们要在开源生态里扮演什么角色

既然是"推进 Agent 产品发展"，就值得想清楚**我们贡献的是什么**，而不只是一个能用的软件：

| 我们可能有价值的贡献 | 为什么有价值 |
| --- | --- |
| **一个"不采信 agent 自述"的验收实现** | 几乎所有 agent 产品都靠"agent 说完成就算完成"。我们做了系统独立复核，**这套实现本身对别人有用** |
| **四层角色拆分的工程实现** | TRAE 宝有产品无代码；我们有一个可读的开源实现，别人能照着改 |
| **写域互斥与并行安全的具体做法** | 多 agent 并行最容易出的事故就是互撞，这块经验稀缺 |
| **本地白盒记忆的文件结构** | 比向量库简单，但足够用——这是"可解释 agent"的一个样本 |

如果只做一件事：**把验收闸门讲清楚并保持可复用**。这是一个闭源产品不会给、而开源社区真正缺的东西。

## 6. 建议的执行顺序

```
第 1 周：O1 CONTRIBUTING + O2 CI            ← 让别人能接手的前提
第 2 周：O3 架构页 + O5 离线演示模式         ← 让别人能看懂并能试
持续  ：O4 good first issue、issue 模板      ← 让别人能留下
```

**判断成功的标准不是 star 数**，而是这三条：

1. 有没有**外部的人**提了第一个 PR；
2. 有没有人**照着 CONTRIBUTING 跑通**了（问一次"卡在哪"）；
3. 作者停更两周，项目**还能被看懂**吗。

---

## 7. 一句话总结

> 不赚钱让我们**不必**往商业化方向变形；
> 但也不会自动带来用户。
> **要推进开源、要推进 agent 产品，唯一的杠杆是"可参与性"：跑得起来 × 改得动 × 看得懂。**
> 这三项我们目前缺的是前两项的基础设施（CONTRIBUTING、CI、架构页），而不是功能。
