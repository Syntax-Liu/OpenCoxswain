## 1. 建议的执行顺序

原则：**先把"已经做完的东西"确认清楚，再补最大的功能缺口。**
不要在一个还没验证完的基础上叠新功能。

### 阶段一：收口（1～2 天）

**目标：让"已完成"这件事可信。**

| 步骤 | 做什么 | 验收 |
| --- | --- | --- |
| 1.1 | **逐页视觉审计**：把 6+ 个视图加入截图脚本，两种主题各跑一遍 | 每个视图都有截图；`audit-live-contrast` 与 `audit-layout-structure` 全部通过 |
| 1.2 | **修掉审计发现的视觉问题** | 无对比度不足、无重复文字、无溢出遮挡 |
| 1.3 | 把这些审计脚本接进 `pnpm test` 或单独的 `pnpm ui:audit` | 一条命令跑完所有视觉检查 |
| 1.4 | 更新 `roadmap.md` 到真实状态 | 文档里的事实与代码一致 |

**为什么先做这个**：五轮 UI 改造改的是全局样式，影响面覆盖整个界面，但只看了两个页面。**在没确认之前就加飞书，等于在没验收的基座上盖楼。**

### 阶段二：补最大缺口（3～5 天）

**目标：进入国内用户的实际工作流。**

| 步骤 | 做什么 | 验收 |
| --- | --- | --- |
| 2.1 | **飞书入站**：Webhook 验签 + 事件去重 + 转给 Assistant | 在飞书里发一句话，Assistant 收到并开始派 Agent |
| 2.2 | **飞书出站**：Assistant 的汇报推回飞书 | Agent 完成时飞书收到汇报 |
| 2.3 | **卡片按钮**：继续 / 暂停 / 看详情 | 点"暂停"能真的停掉任务 |
| 2.4 | 复用 Telegram 的桥接结构 | 两套通道共用 `bridge.ts`，不写第二套逻辑 |

**为什么是飞书**：这是与 TRAE 宝差距最大的一格（它已接飞书+微信）。而且飞书 API 有完善文档，比微信（需公众号/企微）成本低得多。

> 如果时间有限，**只做 2.1 + 2.2**（能派活、能收汇报）就已经可用；卡片按钮可以后置。

### 阶段三：可参与性（2～3 天）

**目标：让别人能接手，而不只是你能用。**

| 步骤 | 做什么 |
| --- | --- |
| 3.1 | `CONTRIBUTING.md`：环境要求、三条命令跑起来、代码地图、提 PR 规矩 |
| 3.2 | 接 CI：`pnpm build && pnpm test`，PR 自动跑 |
| 3.3 | 一页架构图：数据怎么流 + "想改 X 去看 Y" |
| 3.4 | 整理 `docs/`：把已封存的方案移进 `docs/archive/`，索引只留有效的 |

## 2. 不做什么（同样重要）

| 不做 | 理由 |
| --- | --- |
| **不再做 UI 大重构** | 五轮已经收敛到 9 个控件基类、0 裸色值。再动容易把成果推翻 |
| **不做多用户 / 权限分级** | 不盈利前提下的纯成本 |
| **不做云端托管** | 本地优先是身份 |
| **不追竞品功能数量** | 守住"单人 + 多 agent + 可核查" |
| **不为了 star 做增长** | Vibe Kanban 有 2.56 万 star 仍关停 |

---

## 3. 如果只做一件事

**做阶段一（收口）。**

理由：你现在同时有两个 Agent 在改这个仓库，冲突已经发生过一次。
**唯一能防止"改了 A 坏了 B"的，是一套跑得起来、覆盖得全的自动检查。**

具体就是：
1. 把全部视图纳入截图审计；
2. 把审计脚本串成一条命令；
3. 每次合并前跑一遍。

这比加任何功能都更能提升项目的可持续性——**包括多 Agent 并行改代码这个场景本身**。

## 4. 时间与依赖

```
阶段一（1~2 天）  ──→  阶段二（3~5 天）  ──→  阶段三（2~3 天）
     ↑                      ↑                     ↑
  无依赖              依赖阶段一的环境        依赖阶段二稳定
  （现在就能开始）    （应用要能跑起来）      （功能定型再写文档）
```

**阶段一必须在前**：阶段二的飞书开发会频繁改动运行时，如果视觉审计没接上，改了什么都看不见。

| # | 问题 | 我的建议 |

| **D1** | 先做收口还是直接上飞书？ | **收口**。理由见 §3 |

## 6. 一句话总结

> 产品主线已经成形，**现在缺的不是功能，是把"已完成"变成"可验证"。**
> 先用 1~2 天把视觉审计做全、做成一键可跑，再花 3~5 天补飞书入口。
> 这样两个 Agent 并行改代码时，才有一套共同的检查作为底线。
