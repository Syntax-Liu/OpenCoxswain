## 零、先说来源

| 来源 | 是什么 | 为什么可信 |
| --- | --- | --- |
| [Developer Experiences with Cursor AI-native IDE](https://arxiv.org/abs/2610.20618) | 14714 条官方论坛帖、跨两年多的纵向研究 | 大规模真实用户抱怨，不是问卷 |
| [Design for agents（Microsoft Learn）](https://learn.microsoft.com/en-us/agents/design-guidelines/overview) | 微软的 Agent 设计指南 | 平台方的一手规范 |

那篇 Cursor 研究最值钱的结论：

> 讨论**71% 集中在工作流关键机制**（上下文索引、模型路由、Agent 工作流），
> 而这些既是价值来源，也是挫败来源。负面体验集中在
> **可用性、价格、可靠性**——安装设置、用量限制、崩溃、延迟。

**对我们直接有用的判断**：用户抱怨的不是"功能不够"，而是
**"功能在关键时候不好用"**。这和上一轮结论一致——能力面已经够了。

## 一、我们交互上最缺的（按伤害排序）

### P0：等待时看不见发生了什么

**现状**：Assistant 思考时，界面上只有一个"思考中"的隐式状态。
用户不知道它是**在推理**、**在等模型**、还是**已经卡住了**。

**Cursor 研究里的对应抱怨**：延迟和可靠性是负面体验的核心。
但**延迟无法消除，只能让它可理解**。

**该做的**：
- 明确显示"正在等模型响应（已 12 秒）"
- 派出 Agent 后显示"3 个 Agent 在跑，最快的一个已跑 40 秒"
- 超过合理时间（比如 30 秒无输出）显示"可能较慢，可以继续等或按停止"

**为什么这是 P0**：这是**用户对"它有没有在工作"的不确定性**，
比任何功能缺失都伤害体验。

### P0：出错时看不出错在哪

**现状**：错误显示在底部一行 `state.error`，几秒后可能被顶掉。

**该做的**：
- 错误卡片保留在对话流里，不自动消失
- 分三类显示：**能自己重试的** / **需要你决定的** / **环境问题**
  （我们的 Agent 已经有这三分类 `BlockKind`，但界面没体现）

### P1：Agent 在跑时，用户不知道能不能继续说话

**现状**：技术上允许连发，但**界面上没有暗示**。
输入框和在跑的任务之间没有视觉关系。

**该做的**：
- Agent 在跑时，输入框上方显示"它还在跑，你可以继续说"
- 不要禁用输入框（我们已经没禁用，但也没告诉用户）

### P1：批次线只在对话里，不在侧栏

**现状**：批次线（签名元素）在对话流里看得出来，
但**侧栏看不出"这一批是同一轮派的"**。

**该做的**：侧栏里同一批的 Agent 加一个视觉分组。

### P2：状态栏信息过载

**现状**：`76 轮 · 151 步 | 145 tok/s | 1.71M tok | 缓存命中 96% | 31%`

**用 DSH 的"注意力成本"标准审视**：这五个数字里，
**有几个真的帮用户做决定？**

| 指标 | 帮什么决定 | 判断 |
| --- | --- | --- |
| 轮次步数 | 知道它干了多少 | 有用，但可以合并 |
| tok/s | 速度 | **几乎没用**——快慢不由用户控制 |
| 总 token | 用量 | 有用 |
| 缓存命中 | 省钱 | **对用户没意义**——我们不做计费 |
| 上下文 % | 该不该开新会话 | **最有用** |

**建议**：删掉 tok/s 和缓存命中，保留三个：**轮次步数 / 总 token / 上下文**。

## 二、可以抄的具体做法

### 1. Prompt starters（微软）

微软的 Agent 首页有 **prompt starters**——几个可以直接点的例子。

我们已经在 v0.34.0 做了（首次引导的三条示例），**但只在首次显示**。
建议：**空对话时永远显示**，不只是首次。

### 2. 显式的"等待"状态文案

不是转圈，而是**说出在等什么**：
- `正在等模型响应…`
- `正在执行 run_command…`
- `正在读 12 个文件…`

### 3. 错误分级展示

微软强调"透明"和"用户可控"。错误不该只有一句红字，
应该说明：**发生了什么 / 你能做什么 / 什么都不做会怎样**。

---

## 三、不该抄的

| 做法 | 为什么不做 |
| --- | --- |
| Chat-first 极简界面 | 我们是任务指挥软件，不是聊天软件——侧栏的项目树和批次是核心 |
| 自动重试不告诉用户 | 静默重试会让用户以为"变快了"，实际是掩盖问题 |
| 流式打字机效果 | 已有，但不为速度牺牲可读性 |
| 隐藏在设置里的关键开关 | 用户找不到等于没有 |

---

## 四、优先级

| 优先级 | 项 | 不做的后果 | 工作量 |
| --- | --- | --- | --- |
| **P0** | 等待状态说清楚在等什么 | 用户以为卡死 | 小 |
| **P0** | 错误卡片保留 + 三分类 | 出错了不知道怎么办 | 小 |
| **P1** | 在跑时提示"可以继续说" | 用户不敢发 | 很小 |
| **P1** | 侧栏批次分组 | 分不清哪几个是同一批 | 小 |
| **P2** | 状态栏精简到 3 个指标 | 信息过载 | 很小 |
| **P2** | 空对话永远显示示例 | 老用户想不起来能点什么 | 很小 |

---

## 五、和 DSH 指导方案的关系

DSH 的"注意力成本"原则直接支撑上面两条判断：

> 每一项都必须给出多于这份消耗的价值，否则就会被去掉。

状态栏的 tok/s 和缓存命中，就是**消耗注意力但不帮做决定**的典型。
按这条原则应该删。

## 六、一个自我审视

我们上一轮做了 9 项易用性改进。现在回看，**有几项值得重新评估**：

| 项 | 重新评估 |
| --- | --- |
| 附件 | ✅ 刚需，保留 |
| 快捷键 | ✅ 每天用 |
| 命令面板 | ✅ 项目多了必需 |
| @ 引用 | ✅ 明确告诉它看哪个文件 |
| 消息重试/编辑 | ✅ 基本盘 |
| 草稿保存 | ✅ 防丢东西 |
| 全文搜索 | ⚠️ **还没真正用起来**，等会话多了才知道 |
| 上下文预警 | ✅ 但要配合"等待状态"，否则用户不知道何时该开新会话 |
| 首次引导 | ⚠️ 应该改成"空对话永远显示" |

**没有一项是该删的**，但两项的形态要调整。
