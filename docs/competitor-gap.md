# 竞品调研：我们的 Agent 框架差在哪

> 调研时间：2026-11-12
> 对象：主流开源 Agent harness（Claude Code / Codex CLI / Gemini CLI / OpenCode /
> OpenHands / Aider / Mini-SWE-Agent / Hermes / Pi / Mistral Vibe / OpenClaw）
> 一手来源：DSH 官方子系统文档、[Harness Engineering 论文](https://arxiv.org/abs/2609.00006v1)（解剖 11 个系统约 400 万行源码）

---

## 零、先说结论

**我们的"骨架"不落后，缺的是"器官"。**

- **架构方向是对的**：论文最有说服力的发现是——**11 个系统里，没有一个导入通用 agent 框架**，
  全靠手写循环。我们"零依赖自研"的路线和整个行业一致，不是偏执。
- **但我们只实现了 7 个子系统里的 3 个**，缺的 4 个（上下文压缩、Skill、沙箱、LSP）
  都是"真用起来才会痛"的地方。
- **差距最大的一项：上下文压缩**。我们没有。这意味着**长任务跑到一定长度必然崩**。

---

## 一、行业基准：7 个标准子系统

论文把 harness 拆成 7 个子系统。这是公认的结构，可以拿来当检查表。

| # | 子系统 | 行业做什么 | 我们 | 差距 |
| --- | --- | --- | --- | --- |
| 1 | **循环 (Loop)** | 异步循环，轮次/步骤状态机 | ✅ 有 | 无 |
| 2 | **工具 (Tools)** | 注册表 + 执行流水线 + 权限拦截 | ✅ 有（基础） | 工具数少 |
| 3 | **上下文管理** | **压缩、剪枝、token 计量** | ❌ **无** | **致命** |
| 4 | **安全 (Safety)** | 审批、沙箱、权限预设 | ⚠️ 审批有，**沙箱无** | 大 |
| 5 | **编排 (Orchestration)** | 子 Agent、并发、生命周期 | ✅ 强（我们更细） | 我们领先 |
| 6 | **扩展面 (Extension)** | Skill、MCP、插件、hook | ⚠️ 只有 hook | 大 |
| 7 | **协议 (Protocol)** | MCP / ACP / SKILL.md | ❌ 无 | 中 |

## 二、逐项差距

### 2.1 上下文压缩 —— 最大缺口

**行业做法**（DSH `compaction` 子系统）：不是简单的"截断前 N 条"，而是完整机制：

| 机制 | 说明 |
| --- | --- |
| 三档触发 | `pressure`（接近上限）/ `context-overflow`（真溢出）/ 手动 |
| 摘要替换 | 把选中的历史区间替换成一条摘要消息，`surfaceOp: replace` |
| 工具结果剪枝 | 先对超长工具结果做"头/尾保留"，不够再摘要 |
| 事务性 | `compaction/start` → `summary` → `end`，**崩溃可检测遗留锁** |
| 配对保护 | 压缩边界必须保持「工具调用 ↔ 结果」成对，不能拆开 |

**我们**：0。代码里搜不到任何 `compact` / `summariz`。只有 14 处 `truncate`
（那是截断长字符串，不是上下文管理）。

**后果**：一个跑 40 步的 Agent，每步工具返回几千 token，
**跑到二十几步就会超模型上下文窗口然后整轮失败**。
用户看到的是"跑到一半突然报错"。

这是**能不能跑长任务**的分水岭，不是锦上添花。

### 2.2 沙箱 —— 第二大缺口

**行业做法**：命令执行的隔离层。DSH 有专门的 `sandbox` 子系统，
Windows 上有 `sandbox-windows-acl`（用 ACL 限制可写路径）。

**我们**：代码里 0 处 `sandbox`。目前靠两件事兜底：
- 写域互斥（谁改哪个目录）
- 危险动作审批（删/推/发 之前问）

**问题**：这两条都是**规则层**，不是**强制层**。
模型跑一条 `rm -rf /` 或者改 `C:\Windows\...`，只要没被分类成"危险动作"，
就真的会执行。审批是"事前问"，沙箱是"根本做不到"。

### 2.3 Skill —— 扩展面缺位

**行业做法**：`SKILL.md` 已是事实标准（论文数据：**9/11 系统支持，普及率超过 MCP 的 8/11**）。
DSH 的实现相当完整：
- 多层注册表（项目 / 用户 / 内置，按 rank 优先级合并）
- 两种调用策略：`modelInvocable` / `userInvocable`
- 文件监听自动失效
- 目录只注入 name + description，正文按需加载（**省 token**）

**我们**：0。只有 `extensions/` 的 `beforeTool` / `afterTool` 两个 hook。

**差距的本质**：hook 只能"拦一下"，Skill 能"教会它做事"。
比如"如何写这个项目的测试"这种知识，现在只能塞进系统提示词——**每条消息都在付费**。

### 2.4 LSP —— 代码理解

**行业做法**：接 LSP 做跳转定义、找引用、类型诊断。

**我们**：0。`search_files` 是文本搜索（grep 级别）。

**影响**：重构类任务准确率明显低于有 LSP 的 harness。
"把这个函数改名"这种活，我们靠字符串匹配，会漏掉动态引用。

### 2.5 工具数量

| 系统 | 工具数 |
| --- | --- |
| DSH | 数十个（read/write/edit/bash/lsp/web/skill/job/pty/plan…） |
| Claude Code | 十余个 + MCP 扩展 |
| **我们** | **5 个**：read_file / write_file / list_dir / search_files / run_command |

5 个工具能干活，但**没有 `edit`（精确替换）**是明显短板——
改一行要重写整个文件，token 消耗和出错面都大。

### 2.6 MCP

**行业**：8/11 支持。所有工具生态都往 MCP 走。

**我们**：0。

**影响**：用户没法接自己的工具（数据库、内部 API、公司里的服务）。

## 三、我们领先的地方

不是全盘落后，有三处我们做得比多数产品细：

### 3.1 四层编排（Supervisor / Assistant / Agent）

多数 harness 是"一个 Agent + 子 Agent"，我们是显式的四层。
尤其 **Supervisor 的跨项目能力**（全局视图、跨项目写冲突、优先级裁决）——
论文里 11 个系统**都没有**跨项目冲突检测。

这一条是真实的差异化：**两个项目同时改同一个共享文件，别人不管你，我们拦**。

### 3.2 可信性三件套

| 能力 | 我们有 | 多数竞品 |
| --- | --- | --- |
| 危险动作审批（执行前拦住） | ✅ | 部分有 |
| 验收标准 + 系统独立复核 | ✅ | ❌ 少见 |
| 副作用台账（可补偿/不可补偿分类） | ✅ | ❌ 少见 |

**"验收复核"特别少见**：D 说完成，系统真的去跑命令验证，不看它自己怎么说。
论文的 29 个模式里没有对应项。

### 3.3 批次机制

不落后——大部分 harness 是单 Agent，压根没有"并发派活"这个概念。

## 四、按"多痛"排序的建议

不是按工作量，是按**不做会出什么事**排：

| 优先级 | 缺口 | 不做的后果 | 工作量 |
| --- | --- | --- | --- |
| ~~**P0**~~ | ~~**上下文压缩**~~ | **已完成**（v0.24.0）：双层策略 | 已完成 |
| ~~**P0**~~ | ~~**`edit` 工具**~~ | **已完成**（v0.24.0）：精确替换 + 缩进容忍 | 已完成 |
| ~~**P1**~~ | ~~**Skill（SKILL.md）**~~ | **已完成**（v0.25.0） | 已完成 |
| **P1** | **沙箱** | 模型真能删你的文件，审批只是"问一句" | 大 |
| ~~**P2**~~ | ~~**MCP**~~ | **已完成**（v0.26.0）：stdio 传输 | 已完成 |
| ~~**P2**~~ | ~~**LSP**~~ | **已完成**（v0.27.0）：词法级符号查找 | 已完成 |

### 为什么压缩排第一

其它缺口是"能力不够强"，压缩是"**跑不完**"。

现在的实际情况：我们用 13px 字号、820px 宽的内容区、40 步上限。
一旦某个任务真的需要 30+ 步、每步返回大段文件内容，**必然撞上下文上限**。
这是我建议立刻做的。

## 五、一个诚实的判断

**我们的进度大致相当于 2024 年底的 harness 水平。**

理由：
- 骨架（循环 + 工具 + 编排）齐了，而且编排更细
- 但基础设施（压缩、沙箱、扩展面、协议）都没做

参考论文的说法：2026 上半年 harness "从工具变成了平台"。
我们还在"工具"阶段——**但工具阶段是绕不过去的，先把工具做扎实是对的**。

**不该做的事**：为了"像平台"而先上 Cordis 那套 DI 框架。
论文的数据支持我们：**11 个系统没有一个用通用框架**，都是手写循环
+ 各自的扩展点。我们的 `capabilities/` 纯类型接口方向是对的。
