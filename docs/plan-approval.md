## 一、先纠正一个说法：那不是"排队"

早先对 C（Assistant）的描述用了"消息排队"，容易让人以为 C 在串行地一件件等。实际不是。

| 用户说的 | 实际含义 | 代码现状 |
| --- | --- | --- |
| "连发不打断" | C 正在说话时发消息，消息进 Inbox，等**当前这一轮**跑完才被看到 | ✅ `inbox.ts` |
| "交给 C" | 用户只对 C 说话；C 拆解后**派 D**（Agent）去干 | ✅ `spawn_executor` |
| "C 时时刻刻盯着" | 每个 D 结算都作为 `【Agent结算】` 事件回到 C，C 据此决定下一步 | ✅ `orchestrator.ts` |
| "一直做到完" | 跨**多个轮次**的目标推进，不是一轮对话 | ❌ **没有承载物** |

**核心结论：我们缺的不是"排队"，是一个跨轮次活着的"方案"。**
没有它，C 不知道自己还剩哪几步，断电重开接不上，用户也看不出"它是做完了还是忘了"。

## 二、目标流程

以用户原话为例："帮我开发一个 XXX 样的软件"。

```
① 调研         只读 Agent（writeScope: ["readonly"]），零排队，不和后续任务抢
② 出方案       目标 + P0/P1/P2/P3（每步做什么、每步怎么验）
③ 停工等你      ← 唯一的一次审批。没有批准，第一步不许开工
④ 批准后       P0 → P1 → P2 … 每步做完由系统自己验，验过自动派下一步
                 中途只有两种事再找你：真卡住了 / 真要你选方向
⑤ 中途新需求    与当前无关 → 另起一条，走 ①②③④
                 与当前相关 → 并入当前方案，从当前进度接着做
⑥ 全部完成     每一步都有验收结论，才叫做完
```

一句话概括行为契约：

> **方案批一次，执行不再逐步问。** 小改动要报但不停；大改动要停并重批；真卡住才叫人。

## 四、三者怎么区分：小改动 / 大改动 / 卡住

这是整套设计里唯一需要精确判定的地方。**判据是"结果有没有变"，不是"动作大不大"。**

> **验收标准就是"结果"的可执行定义。**
> 改完之后原验收标准仍然成立 → 结果没变 → 小改动。
> 原验收标准不再成立，或要新增要做的事 → 结果变了 → 大改动。

| 情形 | 举例 | 判定 | 行为 |
| --- | --- | --- | --- |
| 换了更好的做法，产出效果一致 | 原本逐文件复制，改用一个脚本一次完成 | **小改动** | 提示，不中断 |
| 现有做法有已知且无法规避的漏洞，换个绕法达到同样效果 | 某个库在 Windows 上有缺陷，换另一个等价库 | **小改动** | 提示，不中断 |
| 实现细节变了，但每步的验收命令照样能过 | 组件拆分方式调整 | **小改动** | 提示，不中断 |
| 原验收标准不再成立 | "支持 1000 并发"改成"支持 5000 并发" | **大改动** | 停工，重批 |
| 新增了原方案没有的步骤或产出 | 发现需要先做数据迁移 | **大改动** | 停工，重批 |
| 某步连续失败 **2** 次 | 命令一直挂、依赖装不上 | — | 第 3 次**卡住**，交人 |

**关键机器判据**：把"验收标准是否被修改或新增"作为大改动的触发器。
C 提出改方案时，必须显式标注 `changes: [{kind: 'small'|'big', where, what, why}]`，
其中 `kind` 由"是否触碰验收标准"决定，**不允许 C 自己说"我觉得这个改动不大"**。

## 五、失败与重试

```
D 失败
 └─ 失败次数 < 2 ？
      ├─ 是 → C 重派：
      │        · 读结算里的卡点分类（可自行重试 / 环境问题 / 需用户决定）
      │        · 改指令（message_executor 已不适用——D 已终态）→ 重新 spawn_executor
      │        · 或换写域、缩小目标重派
      │        · 计数 +1，记进时间线
      └─ 否（第 3 次） → 卡住：该链停住，把「哪一步 / 试过什么 / 卡在哪」交给人
```

- **计数载体**：方案里每个步骤有 `attempts`。计数跟着**步骤**走，不跟着 Agent 走——
  重派会换新 Agent，如果计数挂在 Agent 上，重试就会无限循环。
- **不打扰用户的边界**：只有"可自行重试"类才自动重试；"需用户决定"类**第一次就上报**（重试无意义）。
- **环境问题**：只重试一次就上报（同一环境错误重试三次是浪费）。

## 六、大改动时的冲突判定与停工范围

### 6.1 判据

```
大改动 M 的范围 = 该改动将触碰的路径集合
某个在跑的 D    = 它的 writeScope

相交 → 停下；不相交 → 让它跑完
只读 D（writeScope: ["readonly"]）**永远不算冲突**
```

这正是现有的写域互斥机制（`spawnClaim.ts`），不需要新造判定逻辑。

### 6.2 用户给的例子（作为回归用例）

> 用户要做 XX 软件。
> **A** 是执行软件制作的，它发现需要大改动；**B** 是做软件界面的。
> 这两个没有冲突 → **B 不该中断**。
> 除非这个大改动牵扯到界面大改，否则不应该中断——"这样会影响效率"。

### 6.3 一项技术边界（必须诚实写下来）

写域是**路径前缀**判断（`["src/auth"]` vs `["src/ui"]`）。
真实项目里两个 Agent 改同一棵目录树的不同文件并不少见，纯路径会**误判成冲突**、多停一次。

所以：**路径相交之后，再由 C 结合每个 D 的 `label` / `goal` 复核一次**——
路径相交但实际改的是不同文件，判为不冲突。比纯机械判断多一步推理，换来不做无谓的停工。

### 6.4 停工时的状态命名

不能叫"已停止"（用户会以为是叫停），叫 **「等方案重批」**。
主区顶部给它一条明确的横条，列出**哪些因为冲突停了、哪些因为不冲突还在跑**。

## 七、"小改动"的提示形态

要求：**要提醒用户，但不中断。**

| 项 | 做法 |
| --- | --- |
| 存在形式 | 写进**时间线**；并在对应跑道旁加一个灰色小标「该步骤做过调整」 |
| 不做什么 | 不弹窗、不响铃、**不进"待你处理"计数**、不抢焦点、不要求点确认 |
| 汇报时 | 下一次 C 的汇报里带一句"期间做过的调整"，保证你回头看得到 |
| 为什么这样 | 你随时能查，但不替你制造新任务；这与"小改动不中断"是同一个决定的两面 |

> 说明：你原话是"还是要提示一下的，只是不中断，但是仍要提醒用户"。
> 如果觉得灰色小标不够显眼，可以升级成顶部不消失的细提示条——**这一步待你选，默认先做灰色小标**。

## 八、大改动挂起期间能否派新活：用户设置

你明确说"不能一刀切，由用户设置"。所以做成一个设置项：

| 取值 | 行为 | 适合谁 |
| --- | --- | --- |
| `allow-unrelated` | 可以派，但只能派**与挂起中的大改动写域不相交**的活 | 习惯了随时插活的人 |
| `block-all` | 一律不派，等重批完 | 希望方案定下来再动手的人 |

- 默认值 **`allow-unrelated`**（更符合"不影响效率"的整体取向），**但这是待确认项**。
- 该设置与 `settings/permission.ts` 的权限档位分开放：那是"要不要问你"，这是"能不能派新活"，两件事。

## 九、方案（Plan）的数据形状

```ts
interface PlanStep {
  readonly id: string;            // 'P0' | 'P1' | ...
  readonly title: string;          // 人话："调研竞品与现有架构"
  readonly goal: string;           // 给 D 的完整目标（D 看不到 C 和用户的对话）
  readonly writeScope: readonly string[];
  readonly criteria: readonly Criterion[];   // 见 §十
  readonly acceptancePolicy: 'auto' | 'unverified_only' | 'always_human';
  readonly status: 'pending' | 'running' | 'done' | 'failed' | 'blocked';
  readonly attempts: number;       // 重试计数的载体，跟着步骤走
  readonly dependsOn?: readonly string[];    // P2 依赖 P0，用于排程
}

interface Plan {
  readonly id: string;
  readonly projectId: string;
  readonly goal: string;                    // 用户最初那句话
  readonly steps: readonly PlanStep[];
  readonly status: 'draft'          // C 正在写
                 | 'awaiting-approval'  // ← 唯一的人为关卡
                 | 'approved'           // 一路执行，不再逐步问
                 | 'superseded'         // 大改动后作废，需重批
                 | 'done' | 'blocked';
  readonly approvedAt: number | null;
  readonly approvedBy: 'user' | null;
  readonly amendments: readonly Amendment[];  // 小改动与大改动的全部记录
}

interface Amendment {
  readonly id: string;
  readonly kind: 'small' | 'big';
  readonly where: readonly string[];   // 涉及哪几个步骤
  readonly what: string;               // 改了什么
  readonly why: string;                // 为什么必须改
  readonly criteriaTouched: boolean;   // **大改动的机器判据**
  readonly decidedAt: number;
}
```

### 9.1 状态机

```
draft ──C 写完──> awaiting-approval ──用户批准──> approved ──全部步骤 done──> done
                        │                          │
                    用户驳回                    big amendment
                        │                          │
                        v                          v
                     draft(改)               superseded ──重批──> awaiting-approval
                                                  │
                                             步骤连续失败 3 次
                                                  v
                                               blocked ──人处理──> approved
```

### 9.2 一个硬约束

**`approved` 之外的状态，一律不许 `spawn_executor` 派"方案内"的步骤。**
这是"方案给用户看完才开工"（D1）在代码里的唯一落点；没有这一条，审批就只是摆设。

## 十、"批一次就够"的技术前提：验收必须是硬的

这是整条链能否成立的关键，必须写清楚：

现状默认验收策略是 `unverified_only`——只要有一条标准判不了，就 `needsHuman: true`，
而 `decisionRules.ts` 又只把这类标成"需要你拍板"。
**结果就是：方案批过了，每做完一步还可能因为"这条我验不了"再问你一次，直接违反 D2。**

解决办法：**方案里的每一步都必须带 `command` 或 `diff` 类验收**，由系统自己跑、自己判，
`needsHuman` 因此恒为 false，流程自然一路推到底。

| 标准类型 | 由谁判 | 能否支撑"不逐步问" |
| --- | --- | --- |
| `command` | 系统重跑命令，看退出码 | ✅ 能 |
| `diff` | 系统统计改动 | ✅ 能 |
| `human` | 只能人看 | ❌ 不能 |

**待确认项**：有些步骤天然写不出命令（例如"调研竞品"）。
处理方式建议：这类步骤**允许人工复核点自动放行但仍记录在案**，
不让它变成卡断整条链的例外。**这一条尚未拍板，施工前需确认。**

## 十二、验收标准（做完怎么算过）

- [ ] C 收到"开发 XXX"时，**先调研、再出方案**，而不是直接派第一个执行任务
- [ ] 方案未批准时，**一个方案内的 Agent 都不会被派出去**（有测试断言）
- [ ] 批准后，P0→P1→P2 自动推进，**中途不出现"是否开始"的确认**
- [ ] 某步连续失败 3 次 → 停下并说明"哪一步、试过什么、卡在哪"
- [ ] 前两次失败**不打扰用户**，且重试痕迹在时间线里可查
- [ ] 换一个等价做法（不动验收标准）→ 出现"小改动"提示，**流程不中断**
- [ ] 改掉验收标准或新增步骤 → **停工**，并逐条列出改动位置
- [ ] 大改动时，写域不相交的 Agent **继续跑完**（用 §6.2 的 A/B 例子做回归）
- [ ] 大改动时，写域相交的 Agent 停下，状态显示「等方案重批」而不是「已停止」
- [ ] 设置项 `allow-unrelated` / `block-all` 都能生效
- [ ] 断电重开，方案与进度都在，接着往下做

## 十三、边界（做不到什么）

| 做不到 | 原因 | 目前的应对 |
| --- | --- | --- |
| 保证"方案一次批完永远不用再问" | 真卡住、真方向性选择，机器判不了 | 收敛成"只有卡住和方向选择才找人" |
| 写域判断 100% 准确 | 路径前缀是近似；运行时才算出的路径看不到 | C 复核 + 台账可查 |
| 自动判定"这个改动确实不影响结果" | `criteriaTouched` 是必要条件，不是充分条件 | C 需要给出 `why`；用户可以改判 |
| 承诺任何失败都能自己扛过去 | 环境问题、权限问题不在模型控制内 | 重试一次即上报环境问题 |
| 方案审阅页的视觉设计 | 属界面层，本文只定数据与行为 | 见 §十一 第 8 项 |
